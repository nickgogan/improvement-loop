### Prompt Templates and Persona Files

The `translations/en.json` file is the central prompt engineering artifact. It contains:

1. **Agent personas**: The `hierarchical_manager_agent` definition (role, goal, backstory)
2. **Execution prompts**: ReAct format instructions (`tools`, `task`, `format` slices)
3. **Memory integration**: How memories are injected into agent context
4. **Error handling**: Recovery prompts when agents get stuck
5. **Delegation prompts**: Inter-agent communication format
6. **Guardrail prompts**: Validation error retry instructions
7. **Summarization prompts**: Context window management (summarizer system message)
8. **Human-in-the-loop prompts**: Feedback distillation and pre-review
9. **Knowledge search prompts**: Query rewriting for vector retrieval

**Key observation**: CrewAI uses a single centralized prompt registry (en.json) rather than scattered prompt strings. This is a deliberate i18n-ready architecture, though only English is currently implemented at the prompt level.

### AGENTS.md Design Pattern

The AGENTS.md file is notable for its **version freshness protocol** -- it instructs AI coding assistants to:
1. Check installed version against PyPI
2. Read the changelog before writing code
3. Consult live docs for current API
4. Cross-check against AGENTS.md (live docs win if conflict)

This is a sophisticated approach to combating training data staleness.

## 3. Workflow Topology

### Execution Modes

CrewAI has two primary orchestration models:

#### Crews (Task-Agent Orchestration)

```
Crew.kickoff(inputs) --> Process Router --> Task Execution Loop --> CrewOutput
                              |
              ┌───────────────┼───────────────┐
              v               v               v
         Sequential      Hierarchical    (Consensual - TODO)
```

**Sequential Process**: Tasks execute in definition order. Each task's output becomes context for the next.

**Hierarchical Process**: A manager agent (auto-created or custom) delegates tasks dynamically based on agent capabilities.

#### Flows (Event-Driven Orchestration)

```
Flow.kickoff() --> @start methods (parallel) --> @listen/@router chain --> Final output
                                                      |
                                         ┌────────────┼────────────┐
                                         v            v            v
                                    @listen(method)  @router      @listen(or_/and_)
                                                   /     \
                                              labels      conditional routing
```

**Flow decorators**:
- `@start()` -- Entry points; multiple starts run in parallel
- `@listen(method)` -- Triggers when method completes
- `@router(method)` -- Conditional branching returning string labels
- `or_()` / `and_()` -- Parallel trigger composition

### State Management

| Layer | Mechanism | Persistence |
|-------|-----------|-------------|
| Flow state | Pydantic model (typed) or dict (unstructured) | SQLite via `@persist` decorator |
| Crew state | Task outputs chain via `context` parameter | In-memory per execution |
| Agent memory | Unified Memory (LanceDB/Qdrant Edge + embeddings) | Persistent across sessions |
| Checkpoints | Event-driven state snapshots | JSON or SQLite providers |

### Human Gates

1. **Task-level `human_input=True`**: Pauses task execution for human review before finalizing
2. **Flow-level `@human_feedback` decorator**: Collects feedback with emit routing (approved/rejected/custom labels)
3. **Async feedback providers**: Non-blocking human feedback via custom providers (Slack, email, etc.)
4. **Guardrails**: Function-based or LLM-based output validation with retry loops (up to `guardrail_max_retries`)

### Lifecycle Hooks

```
@before_kickoff --> Crew execution --> @after_kickoff
                        |
            before_llm_call hooks --> LLM call --> after_llm_call hooks
            before_tool_call hooks --> Tool call --> after_tool_call hooks
```

### Agent Execution Loop

```
Agent receives task
    --> Knowledge retrieval (if knowledge_sources)
    --> Memory retrieval (if memory enabled)
    --> Build prompt (role_playing + task + tools + context + memory)
    --> LLM call (with ReAct format or native tool calling)
    --> Parse response (AgentAction or AgentFinish)
        --> If AgentAction: execute tool, loop back
        --> If AgentFinish: validate against guardrails
            --> If validation fails: retry with error message
            --> If passes: return TaskOutput
    --> Context window management (auto-summarize if exceeding limits)
```

## 5. Cross-Agent Protocol

### Agent Roster (Runtime Agents)

CrewAI agents are defined by users, not hardcoded. The framework provides:

| Component | Role | Defined By |
|-----------|------|-----------|
| User-defined agents | Task execution | YAML config (`agents.yaml`) + Python decorators |
| Manager agent | Hierarchical delegation | Auto-generated or custom (`hierarchical_manager_agent` in en.json) |
| Planner agent | Pre-execution planning | Activated by `reasoning=True` or crew `planning=True` |

### Inter-Agent Communication

1. **Delegation Tool**: `delegate_work` -- Assigns sub-tasks to coworkers with full context transfer
2. **Ask Question Tool**: `ask_question` -- Queries colleagues for specific information
3. **Context passing**: Task output chains via `context=[other_task]` dependencies
4. **Hierarchical routing**: Manager agent dynamically selects which agent handles each task

### A2A Protocol (Agent-to-Agent, Google Standard)

CrewAI implements the Google A2A protocol for cross-system agent communication:

| Component | Purpose |
|-----------|---------|
| `a2a/wrapper.py` | Wraps agent classes with A2A delegation capabilities |
| `a2a/utils/agent_card.py` | Agent card fetch/signing (identity advertisement) |
| `a2a/utils/delegation.py` | Remote agent task execution |
| `a2a/updates/` | Three update mechanisms: polling, push notifications, streaming |
| `a2a/extensions/a2ui/` | Agent-to-UI rendering protocol (custom extension) |
| `a2a/auth/` | Client and server authentication schemes |

### Agent Adapters (Interoperability)

| Adapter | Purpose |
|---------|---------|
| `agents/agent_adapters/langgraph/` | Run LangGraph agents within CrewAI crews |
| `agents/agent_adapters/openai_agents/` | Run OpenAI Agents SDK agents within CrewAI crews |

These adapters implement tool translation, structured output conversion, and protocol bridging.

### Shared State Mechanisms

| Mechanism | Scope | Implementation |
|-----------|-------|----------------|
| Crew-level memory | Shared across all agents in a crew | `Memory` class with LanceDB/Qdrant storage |
| Task context chaining | Sequential output passing | `context` parameter on Task |
| Flow state | Shared across flow methods | Pydantic model or dict, persisted via `@persist` |
| Event bus | Global observable state | `crewai_event_bus` singleton with typed events |
| Knowledge | Agent or crew scoped | RAG retrieval from configured sources |
| Execution context | Thread-local state | `ContextVars` for task_id, flow_id, event tracking |

### Coordination Patterns

1. **Sequential orchestration**: Tasks execute in order, output passes forward
2. **Hierarchical delegation**: Manager agent distributes tasks dynamically
3. **Flow event-driven**: Decorator-based DAG with parallel execution and conditional routing
4. **A2A remote delegation**: Cross-system agent communication via HTTP/SSE/polling
5. **Human-in-the-loop**: Feedback collection with outcome routing
6. **Checkpoint/resume**: Event-driven state persistence for crash recovery

### Findings Candidates

#### FC-1: Centralized Prompt Registry with i18n Architecture
**Pattern**: All agent prompts (system messages, ReAct format, error recovery, tool descriptions, summarization) stored in a single translations JSON file, keyed by purpose-based "slices". Enables prompt versioning, A/B testing, and future localization without code changes.
**Dimension**: Prompt Craft
**Why notable**: Contrasts with scattered prompt strings; provides a single audit point for all LLM-facing text.

#### FC-2: Progressive Disclosure Skills Standard
**Pattern**: Agent skills loaded at three disclosure levels -- METADATA (frontmatter only), INSTRUCTIONS (full body), RESOURCES (cataloged files). SKILL.md frontmatter includes name, description, allowed-tools, version, compatibility constraints.
**Dimension**: Agent Design, Context Engineering
**Why notable**: Addresses context budget management by loading skill information incrementally based on need.

#### FC-3: Flow-Based Orchestration with Decorator DAG
**Pattern**: `@start`, `@listen`, `@router` decorators define an implicit DAG. `or_()` and `and_()` compose parallel triggers. State management via typed Pydantic models. `@persist` decorator adds crash-recovery. `@human_feedback` adds non-blocking human gates.
**Dimension**: Orchestration, Agentic Systems
**Why notable**: Elegant decorator-based workflow DSL that composes crews as nodes in larger pipelines.

#### FC-4: Agent-to-Agent (A2A) Protocol Implementation
**Pattern**: Full implementation of Google's A2A standard with agent cards (identity/capability advertisement), three update mechanisms (polling, push, streaming), A2UI extension for rendering, and authentication schemes.
**Dimension**: Agentic Systems, Agent Design
**Why notable**: One of the first frameworks to implement the A2A interoperability standard for cross-system agent communication.

#### FC-5: AGENTS.md Version Freshness Protocol
**Pattern**: Scaffolded context file instructs AI coding assistants to: (1) check installed version, (2) check PyPI for latest, (3) read changelog, (4) consult live docs, (5) cross-check against file. Establishes that live docs win over the static file.
**Dimension**: Context Engineering
**Why notable**: Systematic approach to training data staleness -- acknowledges that static context files become outdated and builds in self-correction instructions.

#### FC-6: Multi-Provider LLM Abstraction with Agent-Scoped Assignment
**Pattern**: `crewai.LLM` class wraps 6 native providers (Anthropic, OpenAI, Azure, Bedrock, Gemini, OpenAI-compatible) plus LiteLLM fallback. Agents accept string shorthand (`"provider/model"`), LLM objects, or separate `function_calling_llm` for tool routing. Provider routing via prefix parsing.
**Dimension**: Model Selection
**Why notable**: Clean separation between model identity (string) and model configuration (object), with per-agent flexibility and a dedicated tool-calling LLM option.

#### FC-7: Unified Memory with LLM-Analyzed Encoding
**Pattern**: Single `Memory` class uses an LLM to infer scope, categories, and importance when saving. Recall uses adaptive-depth retrieval. Supports scope/slice views and pluggable storage backends (LanceDB default, Qdrant Edge).
**Dimension**: Context Engineering
**Why notable**: Memory analysis at write-time rather than read-time; the LLM classifies what it stores rather than relying on retrieval alone.

#### FC-8: Context Window Management via Auto-Summarization
**Pattern**: `respect_context_window=True` (default) triggers automatic summarization when token limits approach. Uses a dedicated summarization prompt with structured sections (Task Overview, Current State, Important Discoveries, Next Steps, Context to Preserve).
**Dimension**: Context Engineering, Prompt Craft
**Why notable**: Structured summarization template preserves task continuity across context resets; addresses a common failure mode of long-running agents.

#### FC-9: Event-Driven Observability with Typed Event Bus
**Pattern**: Singleton `crewai_event_bus` with 17+ typed event categories (agent, task, crew, flow, memory, knowledge, LLM, tool, A2A, checkpoint). Listeners subscribe to specific event types. OpenTelemetry-based tracing built on top.
**Dimension**: Evaluation, Orchestration
**Why notable**: Comprehensive observability layer that enables external monitoring, debugging, and evaluation without modifying core logic.

#### FC-10: Guardrails as Output Validation Loops
**Pattern**: Tasks accept `guardrail` (function or LLM-prompt string) or `guardrails` (list). Functions return `(bool, feedback_or_result)`. Failed validation injects the error back into the agent with retry context. Max retries configurable.
**Dimension**: Intent Engineering, Evaluation
**Why notable**: Composable validation that combines programmatic checks with LLM-based quality assessment in a retry loop.

## Summary

CrewAI is a mature, feature-rich multi-agent orchestration framework with two complementary orchestration layers (Crews for task-agent coordination, Flows for event-driven pipelines). Its architecture demonstrates several patterns of high interest to the Improvement Loop:

1. **Context engineering depth**: Unified memory, knowledge RAG, context window management, and progressive skill disclosure
2. **Orchestration sophistication**: Sequential + hierarchical + event-driven + A2A remote coordination
3. **Developer ergonomics**: YAML-first config, decorator-based patterns, string shorthand for models
4. **Interoperability focus**: A2A protocol, LangGraph adapter, OpenAI Agents adapter, MCP support
5. **Evaluation infrastructure**: Experimental but structured framework with typed metrics

The codebase is well-governed with strict typing (mypy strict), comprehensive linting (20+ ruff rules), security scanning (pip-audit, CodeQL), and conventional commit enforcement. The monorepo structure with 6 workspace members reflects maturity in separating concerns while maintaining cohesion.
