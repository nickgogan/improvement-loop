## 4. Governance Model

### Constraint Expression
| Mechanism | Location | Enforcement | Example |
|-----------|----------|-------------|---------|
| seccomp:unconfined | docker-compose.yaml | Hard (Docker requirement) | Required for Chrome browser sandbox — disables all syscall filtering |
| Resource limits | docker-compose.yaml | Hard (Docker) | `mem_limit: 8g`, `cpus: 4`, `shm_size: 2gb` |
| JWT authentication | Auth backend (8081) | Hard (code, optional) | Enabled via `JWT_PUBLIC_KEY` env var; RSA-2048 |
| One-time tickets | POST /tickets | Hard (code) | Short-lived tickets for WebSocket/VNC paths |
| DNS over HTTPS | Container config | Hard (infra) | All DNS via DoH (Cloudflare default) — prevents local DNS leakage |
| Execution timeout | OpenAPI schema | Hard (schema) | Shell: `hard_timeout` + `no_change_timeout`; Code: max 300s |
| User isolation | Container | Hard (OS) | Runs as `gem` user, workspace at `/home/gem` |
| No auth by default | Docker config | N/A | Without `JWT_PUBLIC_KEY`, sandbox runs **fully open** |

### Guardrail Patterns
- **Container-boundary security only**: No per-session isolation (no cgroup, no AppArmor, no seccomp per session)
- **Shared filesystem**: All agent sessions share the same `/home/gem` filesystem — no session isolation
- **Optional auth**: Authentication is opt-in via environment variable. Default is fully open.
- **Resource caps**: Docker-level memory and CPU limits prevent runaway processes
- **DoH by default**: DNS-over-HTTPS prevents local DNS inspection/leakage

### Permission Model
- No role-based access within the sandbox
- All sessions run as the same OS user (`gem`)
- Auth is binary: either JWT-validated or fully open
- No file access restrictions beyond OS-level user permissions

### Security Trade-offs
The core trade-off is `seccomp:unconfined` — required for Chrome browser sandbox but disables all Docker-level syscall filtering. This means the sandbox relies entirely on container boundaries and OS user permissions for security, not kernel-level syscall restrictions.

## 5. Cross-Agent Protocol

### SDK Architecture
All three SDKs auto-generated by Fern from OpenAPI spec:

| SDK | Package | Status |
|-----|---------|--------|
| Python | `agent-sandbox` (PyPI) | Feature-complete |
| TypeScript | `@agent-infra/sandbox` (npm) | Feature-complete |
| Go | `sandbox-sdk-go` | Stub (README only) |

Both feature-complete SDKs expose sync + async clients with resource-group sub-clients (shell, browser, file, jupyter, code, mcp).

### MCP Server Architecture
MCP Hub at `/mcp` aggregates 4 named sub-servers:

| Server | Tools |
|--------|-------|
| `browser` | navigate, screenshot, click, type, scroll, extract, tab management |
| `file` | read, write, list, search, replace |
| `shell` / `terminal` | exec, create_session, kill |
| `markitdown` | convert, extract_text, extract_images |

Two access modes:
1. REST proxy: `POST /v1/mcp/{server_name}/tools/{tool_name}`
2. Streamable HTTP MCP: `/mcp` endpoint (JSON-RPC 2.0)

### Multi-Agent Interaction Patterns

**Pattern 1: Direct SDK** — One agent, one sandbox. Agent calls sandbox APIs as tool functions. Simplest pattern.

**Pattern 2: Protocol adapter** — `AIOSandboxBackend` implements `deepagents.backends.protocol.BaseSandbox`. Drop-in compatibility with any framework supporting the DeepAgents sandbox protocol. Maps protocol verbs (`execute`, `upload_files`, `download_files`, `read`, `write`, `edit`) to sandbox API calls.

**Pattern 3: Multi-agent group** (AG2 integration) — `GroupChat` with 3 agents (UserProxy, Coder, Reviewer). Sandbox tool functions registered with `@proxy.register_for_execution()`. Sandbox is shared state — both Coder and Reviewer operate against the same sessions.

### Session Multiplicity
Multiple agents can hold concurrent sessions within a single container. Each shell session identified by UUID. No per-session OS isolation — all sessions share the `gem` user's filesystem.

### Cloud Provider Abstraction
TypeScript SDK exposes a `providers/` layer:
- `BaseProvider` (abstract): `createSandbox`, `deleteSandbox`, `getSandbox`, `listSandboxes`
- `VolcengineProvider`: concrete implementation targeting Volcengine VEFAAS API

### Coordination Pattern
**None (infrastructure)**. The sandbox is a passive execution environment. All coordination logic lives in the consuming agent framework.
