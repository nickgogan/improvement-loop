# Add Mermaid diagram diffing as a structural validation layer for high-blast-radius agent tasks

## Current State
The system uses human-in-the-loop Review Gates at milestone boundaries in the six-step development pipeline (Brainstorm -> Document Architecture -> Map to Backlog -> Human Review -> Agent Swarm -> Learn/Improve). Currently, reviewing structural changes requires Nick to mentally reconstruct the impact from scattered file diffs, DD references, and Build Spec outputs. There is no standardized "before/after" structural summary for architecture or workflow changes. Some Mermaid diagrams exist in Notion documentation, but they are not systematically maintained as canonical validation artifacts.

## Proposed Change
Three-part implementation:

1. **Canonical diagrams as DD artifacts.** Each Design Decision that affects architecture (structure) or workflows (function) includes a Mermaid diagram as part of its body. These become the "before" snapshots. Two diagram types map to the two concerns:
   - **Architecture (structure):** Flowcharts, class diagrams, or architecture-beta diagrams showing component relationships, system boundaries, and data flows
   - **Workflows (function):** Sequence diagrams and flowcharts showing operational processes, agent handoffs, and decision points

2. **Agent-generated "after" diagrams as Review Gate inputs.** When an agent completes a Build Spec that touches structure or workflow, it must produce an updated Mermaid diagram of the affected area. The diff between the DD's canonical diagram and the agent's output becomes a Review Gate artifact -- a structural summary rather than raw file diffs.

3. **Cross-model validation.** For high-blast-radius changes, use a different model (or separate agent persona) to independently regenerate the diagram from the changed artifacts. Compare against the executing agent's claimed diagram. Discrepancies surface potential misunderstandings.

## Rationale
This proposal synthesizes insights from the emerging spec-driven development movement and production reports from teams using Mermaid as agent context:
- **Token efficiency:** The Elba team documented that one Mermaid diagram gives equivalent structural understanding to reading 10-20 source files, at a fraction of the token cost
- **LLM compatibility:** Mermaid's constrained ABNF grammar produces lower hallucination rates than any other diagram language when generated by LLMs
- **Human review efficiency:** Jacqui Read's principle -- "The diagrams aren't necessarily for the AI. They're for humans to validate what the AI produced." Humans spot visual mismatches faster than they spot code mismatches across files
- **Git-native:** Because Mermaid is text, standard `git diff` applies, making it compatible with existing revision control workflows
- **Existing ecosystem:** Mermaid renders natively in Notion, GitHub, Obsidian, and VS Code -- all tools already in use

## Door Type Assessment
**Two-Way.** This is purely additive -- adding diagram artifacts to DDs and requiring them in Build Spec outputs. No existing schema is modified. No data is dropped. Rollback = stop requiring diagrams and optionally remove them from DD bodies. Time to rollback: minutes. The only sunk cost would be the effort spent creating the canonical diagrams, which retain documentation value regardless.

## Implementation Assessment
**Medium complexity.** Touches multiple system surfaces but all changes are additive:
- DD page body template (add Mermaid diagram section)
- Build Spec schema (add "structural diagram" output requirement for architecture/workflow-affecting specs)
- Review Gate checklist (add before/after diagram comparison step)
- CLAUDE.md or agent instructions (add requirement to produce updated diagrams after structural changes)

Prerequisites: None. Can be implemented incrementally -- start with a few high-value DDs, expand over time.

Testing: Validate on 2-3 existing DDs by having an agent generate the canonical diagrams, then simulating a change and checking the diff quality.

**Estimated effort:** 2-3 hours for initial setup (diagram template, 3-5 pilot DDs with canonical diagrams, Build Spec schema update). Ongoing effort is minimal -- agents generate diagrams as part of their normal output.

## Operational Impact
**Reduces Ops Burden.** The primary operational improvement:
- Review Gates become faster -- Nick reviews a visual structural diff instead of reconstructing impact from file changes
- Drift detection becomes passive -- if a diagram diverges from reality, it surfaces automatically when the next Build Spec touches that area
- Cross-model validation catches agent misunderstandings before they reach production

Known limitations to manage:
- Mermaid diagrams degrade past ~30 nodes -- complex system areas need hierarchical diagrams (overview -> detail), not monoliths
- Agents occasionally generate syntactically valid but semantically imprecise diagrams -- the cross-model validation step mitigates but doesn't eliminate this
- Diagrams validate structure and flow, not behavior -- race conditions, error handling paths, and edge cases still need other validation methods

## Implementation Steps
1. Define the Mermaid diagram conventions for the system: which diagram types for which concerns, naming conventions, max complexity per diagram
2. Add a "Canonical Diagram" section to the DD page body template
3. Pilot: Create canonical Mermaid diagrams for 3-5 high-value DDs that govern architecture and workflows (candidates: DD-04 OODA, DD-12 Owner/Assignee, DD-15 Triage)
4. Update the Build Spec schema to include a "Structural Diagram Output" section for specs that affect architecture or workflows
5. Update CLAUDE.md / agent instructions to require before/after diagram production for structural changes
6. Add a "Diagram Diff Review" step to the Review Gate checklist
7. Optionally: set up a Mermaid validator agent (render to PNG, visually inspect) as a quality gate on generated diagrams
