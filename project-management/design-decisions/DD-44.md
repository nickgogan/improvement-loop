# DD-44

> **For agents:** DD-44 establishes the lifecycle rules for Design Decisions. Before changing a DD's status or creating a DD that replaces an existing one, read this.

---

## The Three Statuses

| Status | Meaning | When to Use |
|---|---|---|
| **Binding** | Active, authoritative | Default for all new DDs after Nick approves |
| **Proposed** | Under consideration, not yet authoritative | Draft DDs awaiting Nick's approval |
| **Superseded** | Replaced by a newer DD or no longer applicable | When a new DD covers the same ground with broader or updated scope |

The **active DD set** = all DDs with Status: Binding. Agents should filter by this when making design decisions.

---

## Supersession Rules

1. **Never delete or renumber a DD.** DD numbers are permanent identifiers.
2. **Explicit successor.** A superseding DD must reference what it supersedes in its Cross-References section (e.g., "Supersedes: DD-32").
3. **Explicit predecessor.** The superseded DD gets a note at the top of its body: "Superseded by DD-XX" and its Status property changes to Superseded.
4. **Partial supersession is valid.** A new DD may supersede only specific aspects of an older DD. In this case, the older DD remains Binding but its body gets a note identifying which sections are superseded and by which DD.
5. **Chains are traceable.** If DD-50 supersedes DD-32, the chain must be followable through cross-references.

---

## When to Supersede vs. Amend

| Situation | Action |
|---|---|
| Minor refinement, same scope | Amend the existing DD (update body, log to System Log) |
| Broader scope that absorbs an older DD | Create new DD, supersede the old one |
| Fundamental direction change | Create new DD, supersede the old one |
| DD no longer applies, no successor needed | Mark as Superseded with body note explaining why |

---

## Approval and Authorship

Nick's role in the DD lifecycle is **content review**, not file authorship. The system Owner (or the active agent) drafts DD text, presents it for Nick's acceptance or redirect, and — on acceptance — executes filing mechanics: creating the DD file, updating the DD index, logging to the System Log, propagating cross-references.

"Nick approves" throughout this document refers to content-level gating, not to who physically writes the markdown. The same model applies to amendments and supersessions: Nick approves the change; the Owner executes the rollout.

This matches the MetaSystem's operating principle that the AI executes while Nick gates content (session 52 clarification, 2026-04-22). Specs that would require Nick to physically author files or supply runtime data are drift and should be refactored so the AI can execute autonomously once content is approved.

---

## Rollout Steps for Supersession

1. Create the new DD following the DD Rollout Checklist in Design Decision Guidelines
2. Update the superseded DD's Status property to Superseded
3. Add "Superseded by DD-XX" callout to the top of the superseded DD's body
4. Log both changes to the System Log
5. Update any cross-references in other Binding DDs that pointed to the superseded DD
