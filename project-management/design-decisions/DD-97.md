# DD-97

> **For agents:** Before drafting a new rule or skill artifact, `/extract-artifacts` scans `extracts/rules/` or `extracts/skills/` for semantically similar artifacts. On match, surface the candidate + the existing artifact + a diff sketch — propose extension, don't create new. Nick gates every proposal. Templates and agents are out of scope (templates version per future DD-X8; agents never auto-create per spec §2.3).

---

## The Constraint

**Trigger.** When `/extract-artifacts` is about to draft a new rule or skill artifact from a finding, the skill first performs a corpus scan:

- **For rules:** scan `extracts/rules/*.md` for semantic overlap with the candidate finding.
- **For skills:** scan `extracts/skills/*.md` for skill variants — same I/O contract, different mode.

**Calibration — LLM judgment, loose.** The semantic-similarity check is performed by the LLM, using its judgment over titles, summaries, ContractSpec content, and body language. No structured threshold (e.g., ContractSpec invariant overlap by N fields). The threshold is intentionally loose: the cost of a false-positive proposal is one Nick-gated read; the cost of missing a real overlap is duplication that compounds at corpus scale.

**Response — propose, don't decide.** On match, the skill emits a structured extension proposal containing:

- The candidate finding's relevant content (what would have been the new artifact).
- The existing artifact in `extracts/{rules,skills}/` that overlaps.
- A diff sketch — what the existing artifact would look like *after* extending it (rule: appended Evidence row; skill: added mode flag with the new variant's behavior).
- Codifier's recommendation (one of: `extend existing` | `create new (false positive)` | `parameterize as mode variant`).

The skill does NOT auto-merge. It does NOT auto-create on match. Nick rules per proposal — accept the extension, override to create-new, redirect to a different existing artifact, or defer.

**Per-class extension shape:**

- **Rule extension.** Append a row to the existing rule's "Evidence" section. The new evidence cites the new source finding alongside the original. Body content of the rule is updated only if the new evidence shifts the rule's wording (Codifier proposes wording delta; Nick gates).
- **Skill parameterization.** Add a mode flag to the existing skill's invocation contract. The new variant is documented as a mode option (e.g., `--strict` / `--loose`); the original behavior remains the default. Body documents both modes; ContractSpec invariants account for the new mode.

## Why

**Corpus scale is the forcing function.** Today: 12 rules, 12 skills. Manageable manually. Past 50 of either, two costs grow:

1. **Discovery cost.** A consumer querying "is there a rule about X?" must scan more artifacts. Duplicates increase noise.
2. **Drift cost.** Two rules saying the same thing in slightly different words drift apart over time. Their `invariants` diverge. Audits surface contradictions.

Spec §2.2 frames the gap directly: "1:1 finding:artifact for non-pattern classes creates duplication. Two findings describing 'require absolute paths' become two rule artifacts instead of one. This is fine at small scale but will not scale past ~50 rules."

DD-97 codifies the discipline before the volume forces a retrofit. Same logical pattern as DD-94 (companion changelogs) — install the mechanism while the corpus is small enough that backfill is cheap, before drift makes consolidation expensive.

**Why LLM-loose over ContractSpec-structured (Open Q5 resolution).**

Three calibrations were considered:

- **(i) LLM judgment, loose** — selected. Reads candidate + corpus, judges similarity by title, summary, body language, ContractSpec content. Higher false-positive rate; better recall.
- **(ii) ContractSpec-overlap structured** — rejected. Trigger fires only on ≥N invariant overlap. Tighter; lower recall. Brittle when invariants are written in different vocabularies for genuinely-similar rules. Strict triggers under-fire on real cases.
- **(iii) Hybrid (name AND invariants both fire)** — rejected. Strictest. Lowest false-positive rate but worst recall.

Selection rationale: starting strict and loosening on observed under-firing is harder than starting loose and tightening on observed false-positive volume. The Nick gate is the structural backstop — false positives cost one read, not a corpus violation. If false-positive volume becomes burdensome (Nick rejects >X% of proposals), DD-97 can be amended to a stricter calibration in a follow-up session.

**Why propose, don't decide.** The Codifier's match-judgment is fuzzy (per (i)). The Nick gate is structural (per DD-29). Auto-merge would (a) bypass the gate, and (b) fold structurally-distinct artifacts into one when the LLM was confused. Same-pattern reasoning as DD-96's no-autonomous-regen invariant.

## Rules for `/extract-artifacts`

1. **Scan before draft.** When the form classification of an incoming finding is `rule` or `skill`, `/extract-artifacts` performs a corpus scan over the matching `extracts/{rules,skills}/` directory before drafting the artifact.

2. **LLM-loose similarity check.** The skill uses LLM judgment to identify candidate matches. No structured threshold. False-positive volume is acceptable; the Nick gate catches them.

3. **Propose, don't decide.** On match, emit a structured extension proposal (candidate + existing artifact + diff sketch + Codifier recommendation). Do NOT auto-merge. Do NOT auto-create the new artifact.

4. **Nick gates merge.** Re-running `/extract-artifacts` on a flagged finding to apply the extension requires Nick's explicit ruling on the proposal. Codifier may queue proposals in batches, but does not act without ruling.

5. **No-match path unchanged.** If the corpus scan returns no semantic match, `/extract-artifacts` proceeds to create a new artifact per current behavior. The DD does not change the no-match path.

## Acceptance Criteria

| Test | Expected |
|---|---|
| New rule candidate semantically overlaps with one existing rule | Skill emits extension proposal naming the existing rule; no new artifact written. |
| New skill candidate is a mode variant of an existing skill (same I/O, different mode) | Skill emits parameterization proposal naming the existing skill + the proposed mode flag; no new artifact written. |
| New candidate has no semantic match in the corpus | Skill proceeds to create new artifact per pre-DD-97 behavior. |
| Multiple existing artifacts plausibly match | Skill surfaces the strongest match + flags secondary candidates in the proposal; Nick rules on the merge target. |
| Codifier auto-merges without Nick ruling | Procedural violation; flagged in next governance audit. |
| Template or agent classification | DD-97 does not fire; templates/agents are out of scope per spec §2.3. |

## Scope and Non-Goals

- **In scope:** `/extract-artifacts` runs on `rule`-classified or `skill`-classified findings. Both extension-existing and create-new paths are governed.
- **Out of scope:** Templates. Spec §2.3 routes template variants through versioning (future DD-X8 — side-file regen with version bump). Versioning and extension are different mechanisms.
- **Out of scope:** Agents. Spec §2.3: "Never auto-create. Agent creation is a system-level decision (DD-82 governs the 4-agent architecture). Codifier flags agent-classified findings for Nick's review. No extraction without explicit Nick approval." Extension is moot.
- **Out of scope:** Patterns. Pattern findings route to guides per DD-81; the extension path for pattern content is `/synthesize-guide` absorbing them into existing guide clusters, not the rule/skill extension rubric.
- **Out of scope:** Calibration tightening. v1 is calibration (i). Promotion to (ii) or (iii) requires a follow-up DD if false-positive volume justifies it.
- **Out of scope:** Cross-form extension. A rule-classified finding does not extend a skill, and vice versa. Form classification (per DD-77 / DD-80 / DD-81) precedes DD-97; the extension scan operates within the assigned form only.
