# DD-112

> **For agents:** Concept docs live by **what they are**, not by which altitude reads them.
> `knowledge/reference/` = engine **self-knowledge** (fractal-pattern, vocabulary, dbdo-pipeline);
> `operations/references/` = **operational reference** the engine consults (all concept docs, rubrics,
> maps). The harness concept doc moved into `operations/references/librarian/harness.md` (whole-system
> unit); the runtime sense was renamed `runtime-environment.md`.

---

## Core Decision

IB-170 flagged concept docs split across two homes — every concept doc unified §Composition+§Construction
in one file under `operations/references/librarian/`, **except** the harness concept, whose §Construction
sat in `knowledge/reference/harness.md` while a separate `librarian/harness.md` held its §Composition
substrate. Investigation (session 126) found two issues, not one:

1. **A split home** for the harness concept (the rule-12 anomaly).
2. **A name collision:** "harness" denoted two distinct concepts —
   - the **whole-system unit** the engine composes/audits (`/audit-artifacts`, `/design-harness`), and
   - the **runtime environment** an agent runs *inside* (the CLI/IDE/API).

### The home rule

A concept doc's home is determined by **what it is**, not by which altitude's operation consumes it:

| Home | Holds |
|---|---|
| `knowledge/reference/` | **Engine self-knowledge** — how *this* engine is built/operates: `fractal-pattern.md`, `vocabulary.md`, `dbdo-pipeline.md`, curated engine patterns/schematics. |
| `operations/references/` | **Operational reference** the engine's skills/agents consult at runtime — all concept docs (what a skill/agent/prompt/harness *is*), rubrics, routing tables, dimensions, the consumer-abstractions-map. |

Concept docs describe **external abstractions** the Librarian audits/designs *consumer* artifacts
against; they are not "how this engine is built." By the rule they belong under
`operations/references/librarian/`, not `knowledge/reference/`. This applies the two-bodies frame
(DD-111) to the concept-doc layer.

## Changes executed (session 126)

1. **Relocated** `knowledge/reference/harness.md` → `operations/references/librarian/harness.md`
   (`git mv`, history preserved). All concept docs now share one home; `knowledge/reference/` holds
   only self-knowledge.
2. **Renamed** the runtime-sense doc `operations/references/librarian/harness.md` →
   `operations/references/librarian/runtime-environment.md` (`git mv`). It keeps the audit-time
   §Composition substrate and is the "runtime sense of harness."
3. **Repointed** all live consumers: `consumer-abstractions-map.md` (×4), both `_index.md` files
   (added a `runtime-environment` catalog row + reframed the harness row in librarian/; removed the
   harness row from `knowledge/reference/_index.md`), and the moved doc's own internal §Composition
   pointers.

## What this does NOT change

- **Agent helper files** under `agents/{name}/` stay agent-scoped and agent-private — not shared
  concept-doc substrate. No change (Rule 11 — no concrete confusion observed).
- It does **not** merge the two harness senses into one file — they are read by different operations
  and conflating them re-creates the ambiguity. Two clearly-named docs instead.
- It does **not** rewrite immutable DD-110, which cites the pre-move `knowledge/reference/harness.md`
  path — that citation denotes the doc **now at** `operations/references/librarian/harness.md`.
- Residual (rule-12, separate): the whole-system `harness.md` is §Construction-primary and points to
  `runtime-environment.md` for the shared runtime audit aspects; a whole-system-specific §Composition
  backfill is existing rule-12 debt, not a blocker.
