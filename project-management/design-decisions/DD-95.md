# DD-95

> **For agents:** Every non-guide extract (rule, skill, template, agent) carries two frontmatter fields: `last_change_session` (the session number of the most recent change) and `last_change_sl` (the bare filename stem of that session's System Log entry). `/extract-artifacts` writes both fields on every create or update. Guides do NOT receive these fields — they use the companion changelog file pattern from DD-94.

---

## The Constraint

Two new frontmatter fields, both required on non-guide extracts:

```yaml
last_change_session: 46
last_change_sl: "session-46-codifier-session-45-identification"
```

**Field semantics:**

- `last_change_session` — **integer**. The session number of the most recent regen, drift-update, or Nick-edit that landed in this artifact. Updated on every write to the artifact. The field is the answer to "when did this last change in IL session terms?"

- `last_change_sl` — **string**. The bare filename stem of the SL entry that narrates that change (no path, no `.md` extension). Example: `"session-46-codifier-session-45-identification"`. The field is the answer to "where do I read the why?"

**Validation at write time.** `/extract-artifacts` MUST verify that `operations/system-log/<last_change_sl>.md` exists before writing the artifact. A non-existent SL stem is a write-abort: the artifact is not written, and the skill emits a structured error naming the missing SL file. This guarantees the pointer is never broken at write time. (It can become stale if the SL file is later renamed; that's a separate hygiene concern handled outside this DD.)

**Both fields are required.** Neither may be null on a non-guide extract. An extract written without a binding SL session is a process violation — every artifact change happens in some session, and that session has (or will have) an SL entry. If the SL entry doesn't exist yet at write time, the workflow is to write the SL first, then the artifact.

## Why

**Asymmetric mechanism by stability profile.** Per spec §3.3 / §4.1, change-log mechanism diverges by class:

| Class | Stability | Update driver | Mechanism |
|-------|-----------|---------------|-----------|
| Guide | Low (high churn) | New findings, Nick tuning | Companion `.changelog.md` (DD-94) |
| Rule | High | Occasional rubric clarification | Frontmatter `last_change_*` + SL (this DD) |
| Skill | Medium | Practice evolution | Frontmatter `last_change_*` + SL (this DD) |
| Template | High but versioned | Schema/vocab changes | Frontmatter `last_change_*` + SL (this DD) |
| Agent | Very high (stable) | System-level decisions only | Frontmatter `last_change_*` + SL (this DD) |

The query rate on non-guide change history is low (most rules / skills / templates / agents change quarterly or less). Building companion files for ~26 low-churn artifacts is net-negative file proliferation. The frontmatter pointer pays off because the *cost* is two fields, and the *capability* is "follow the pointer to read the why."

**Why both fields, not one.** A single field would force a tradeoff:

- Just `last_change_sl`? Numeric session ordering is lost; sorting and filtering become text operations.
- Just `last_change_session`? You'd have to grep SL by session number; non-deterministic if a session has multiple SL entries.

Two fields preserve deterministic navigation: integer for ordering/filtering, stem for direct lookup.

**Why guides are excluded.** Guides change frequently enough that the per-guide narrative belongs in a per-guide artifact. A frontmatter pointer that updates weekly loses its archival value — by the time you want to know "why did G7 change in February," `last_change_sl` already points to April. The companion changelog file (DD-94) accumulates entries; the frontmatter pointer overwrites. Different tools for different stability profiles.

**Schema implication.** `_schema.yaml` defines the frontmatter contract for IL artifacts. Adding two required fields to the non-guide extract types is a schema change; the schema file is updated as part of this DD's landing. Findings, sources, authorities, and guide-class extracts are unaffected.

## Rules for `/extract-artifacts`

1. **Write on create.** When `/extract-artifacts` creates a new non-guide extract (rule, skill, template, or agent), it populates both fields with the current session's values: `last_change_session` = the active IL session number; `last_change_sl` = the SL stem for that session.

2. **Write on update.** When `/extract-artifacts` updates an existing non-guide extract (drift regen, Nick-requested re-extraction, dimension rebalance), it overwrites both fields with the current session's values. Prior values are not preserved in frontmatter — the SL chain is the history, not these fields.

3. **Validate SL stem.** Before writing the artifact, the skill checks for `operations/system-log/<last_change_sl>.md`. Missing → write-abort with structured error naming the missing file.

4. **Abort on missing session number.** If the active session number is unknown to the skill, the write aborts. The session number is required.

**Out of scope for `/extract-artifacts`.** This DD does not modify the skill's classification logic, ContractSpec generation (DD-78), or ContextSpec generation (DD-92). It adds two more frontmatter fields to the write step and one validation check.

## Schema Update

`_schema.yaml` is updated as part of this DD's landing to add `last_change_session: integer` and `last_change_sl: string` to the frontmatter contract for non-guide extracts (rule, skill, template, agent). Guide-class extracts and findings/sources/authorities are unchanged.

## Retroactive Backfill (executed in session 70)

The ~26 existing non-guide extracts in `extracts/{rules,skills,templates,agents}/` were authored before this DD existed and lack both fields. Backfill is executed **in this session** (not deferred to an IB) per Nick's directive on 2026-04-26.

**Backfill procedure:**

1. Enumerate every artifact under `extracts/rules/`, `extracts/skills/`, `extracts/templates/`, `extracts/agents/` (top-level files; recurse if subdirectories exist). Skip `_index.md`.
2. For each artifact, infer `last_change_session` and `last_change_sl` from:
   - The artifact's `created` or `updated` frontmatter (if a session can be matched).
   - The git log of the artifact (the commit that last touched the artifact, mapped to its session).
   - Fallback: the originating session per the artifact's `source_finding` extraction trail.
3. Validate every inferred `last_change_sl` resolves to a real SL file. If the inferred SL doesn't exist, log the artifact as a backfill-gap and skip (do not write a broken pointer).
4. Write the two fields to each successfully-resolved artifact's frontmatter, preserving all other frontmatter content.
5. Backfill-gap artifacts (if any) are listed in this session's SL entry; they will be populated on next regen.

The backfill is one-time. Going forward, `/extract-artifacts` maintains the fields on every write per the rules above.

## Scope and Non-Goals

- **In scope:** Non-guide extracts in `extracts/rules/`, `extracts/skills/`, `extracts/templates/`, `extracts/agents/`. Both fields, required, validated.
- **Out of scope:** Guides. They use the companion changelog file pattern from DD-94.
- **Out of scope:** Findings, sources, authorities. These are KB primary records, not artifact extracts. Their lifecycle is governed separately (and partially by spec §What This Spec Does NOT Resolve, finding-level lifecycle).
- **Out of scope:** Live-location artifacts. Once an extract deploys to its enforcement location (`.claude/rules/`, `meta-system/knowledge/`, etc.), the fields travel with it but are not maintained at the deploy boundary by this skill. Live-location lifecycle is governed by DD-29.
- **Out of scope:** Drift detection itself (Phase 2 / DD-X2). This DD captures *that* a change happened in IL session terms; it does not detect *that source content drifted*.
