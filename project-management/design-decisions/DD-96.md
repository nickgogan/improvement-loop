# DD-96

> **For agents:** Codifier scans non-guide extracts on-demand to detect source drift. When a source finding's `last_updated` post-dates the artifact's `extraction_date`, a drift report entry is emitted under `operations/drift-reports/<YYYY-MM-DD>-source-drift.md`. The scan **never** autonomously re-extracts. Nick reads the report and rules whether to re-run `/extract-artifacts` on the flagged set.

---

## The Constraint (amended 2026-04-26 per session-71 ratification)

**Trigger condition.**

For every artifact `a` in `extracts/{rules,skills,templates,agents}/` with a `source_finding`:

```
let f = the source finding referenced by a.source_finding
if f.last_updated > a.extraction_date:
    emit drift report entry for (a, f)
```

The scan is run on-demand (Nick request, Codifier-initiated as part of routine maintenance, or as a precondition to a new `/extract-artifacts` run). It is NOT embedded in `/extract-artifacts` and NOT periodic — explicit invocation only.

**Response — report only; never autonomous re-extract.**

The scan emits a per-run report at `operations/drift-reports/<YYYY-MM-DD>-source-drift.md`. The report contains one entry per drift hit, no entries for drift-clean artifacts. The scan never modifies an artifact's content. It never re-runs `/extract-artifacts`. The Nick gate is invariant — drift detection produces visibility, not action.

**Drift report entry shape.**

Each entry is ~5 lines, fixed structure:

```markdown
### <artifact-stem>
- Source: [[<finding-stem>]]
- Source updated: <YYYY-MM-DD> (post-extraction)
- Artifact extracted: <YYYY-MM-DD>
- Recommendation: re-run /extract-artifacts on this finding | dismiss as cosmetic | reclassify
```

The Recommendation field uses a closed three-value enum:

- **`re-run /extract-artifacts on this finding`** — Codifier's default suggestion when source content has materially changed.
- **`dismiss as cosmetic`** — for source updates that don't affect the artifact's substance (typo fixes, tag changes, trivial edits).
- **`reclassify`** — when source drift suggests the finding's form may have changed (e.g., a rule-classified finding now reads more like a pattern; calls for `/identify-artifacts` re-run before `/extract-artifacts`).

The entry is the Codifier's recommendation; Nick's ruling on the report is what changes state.

**Report top matter.** Each report file opens with a one-paragraph scan summary: total artifacts scanned, drift hits, clean artifacts, scan invocation context (manual vs. routine sweep).

## Why

**Producer/consumer pairing with DD-95.** The Phase-1 lifecycle bundle gives non-guide artifacts a session-pointer (DD-95): `last_change_session` + `last_change_sl` record *when* an artifact last changed in IL session terms. DD-96 closes the loop on the producer side: it detects *when source content has changed* and surfaces the gap. The drift window is the time between source update and artifact absorption. DD-95 makes the absorption visible; DD-96 makes the divergence visible.

**No-autonomous-regen is an invariant, not a default.** A natural temptation is for Codifier to re-extract on detected drift — the source has new evidence, the artifact should reflect it. This temptation is rejected:

- Source updates are not always artifact-relevant (cosmetic edits, tag adjustments, evidence additions that strengthen but don't change the artifact's claim).
- Re-extraction may surface form-classification questions that weren't relevant at original extraction.
- Nick's gate at every stage boundary (DD-29) is structural; bypassing it for "drift seems obvious" erodes the contract.

The report-only invariant matches DD-29's stage-boundary gate: every state change crosses the gate.

**On-demand vs. embedded vs. periodic.** Three trigger options were considered:

- **Embedded in `/extract-artifacts`:** The skill scans the existing corpus before drafting new artifacts. Couples drift detection to extraction work; no separate skill cost. **Rejected:** drift detection is a separate concern from extraction; coupling produces noisy `/extract-artifacts` runs and slows the new-extraction path with old-state scanning.
- **Periodic (cron / calendar):** Owner sweeps drift periodically. **Rejected:** adds operational discipline cost; the IL doesn't yet have enough drift volume to justify a recurring sweep; mechanism cost > current observable benefit.
- **On-demand (selected):** Codifier runs a dedicated skill when sweep value is real (large finding intake, dimension rebalance, pre-extract sanity check, Nick request). Lowest mechanism cost; matches the existing IL operational rhythm.

If drift volume grows past on-demand viability, the trigger can be promoted to periodic in a follow-up DD.

## Rules for Drift Detection

1. **Scan scope.** Only artifacts in `extracts/rules/`, `extracts/skills/`, `extracts/templates/`, `extracts/agents/`. Guides are excluded (their lifecycle is governed by DD-93 + DD-94). Patterns are excluded (they route through guides per DD-81; pattern findings update via guide regeneration).

2. **Comparison logic.** Compare `source_finding.last_updated` (frontmatter field on the finding) against `artifact.extraction_date` (frontmatter field on the artifact). Both fields are date strings (`YYYY-MM-DD`). Drift = source updated strictly post-dates artifact extraction. Equal dates are NOT drift.

3. **Report-only invariant.** The scan never modifies an artifact's content, frontmatter, or `pipeline_status`. It never invokes `/extract-artifacts`. It never re-runs `/identify-artifacts`. Output is exclusively the drift report file.

4. **Nick gates re-extraction.** Re-running `/extract-artifacts` on a flagged artifact requires Nick's explicit ruling on the drift report. The Codifier may propose batches (e.g., "re-run on these 5 artifacts; dismiss these 3 as cosmetic; reclassify these 2") but does not act without ruling.

## Acceptance Criteria

| Test | Expected |
|---|---|
| Scan run on a corpus where one artifact's source finding `updated` post-dates the artifact's `extraction_date` | Drift report entry for that artifact only; report file at `operations/drift-reports/<YYYY-MM-DD>-source-drift.md`. |
| Scan run on a clean corpus | Report file written with summary noting 0 drift hits; no entries below the summary. |
| Source finding updated on the same date as artifact `extraction_date` (not after) | No drift entry. Equal dates are not drift. |
| Scan attempts to modify an artifact's frontmatter or content | Procedural failure; the scan is a read-only operation by contract. |
| Guide artifact's source finding `updated` post-dates guide synthesis | Not in scope; DD-96 scan excludes guides. |
| Codifier re-runs `/extract-artifacts` on a flagged artifact without Nick ruling | Procedural violation; flagged in next governance audit. |

## Scope and Non-Goals

- **In scope:** Non-guide extracts (rules, skills, templates, agents) and their source-finding pointers. Drift means source content has changed; the artifact has not absorbed it.
- **Out of scope:** Guides. Their lifecycle is governed by DD-93 + DD-94 (preservation + companion changelog). Guide source-finding sets evolve through `/synthesize-guide` re-runs, not through this drift mechanism.
- **Out of scope:** Patterns. They route to guides per DD-81; their drift surfaces through guide re-synthesis.
- **Out of scope:** Reverse drift — when an artifact's content changes (Nick edit, manual update) without a corresponding source-finding change. That's an artifact-side integrity concern handled outside this DD.
- **Out of scope:** Live-location artifacts. Once deployed from `extracts/` per DD-29, drift detection at the live location is a separate question — DD-96 scans only the staging directory.
- **Out of scope:** Periodic invocation. On-demand only for v1. Promotion to periodic requires a follow-up DD if drift volume justifies it.
