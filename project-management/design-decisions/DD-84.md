# DD-84

> **For agents:** MetaSystem is a private monorepo on GitHub (`nickgogan/MetaSystem`). Individual systems can be published to separate repos via `git subtree push` for selective sharing. Never push directly to published repos — they are one-way mirrors of the monorepo.

## The Constraint

### Repository Architecture

| Repo | Visibility | Purpose | Sync Mechanism |
|------|-----------|---------|----------------|
| `nickgogan/MetaSystem` | Private | The monorepo — single source of truth | Direct push |
| `nickgogan/improvement-loop` | Private | Published subset of IL for selective sharing | `git subtree push --prefix=systems/improvement-loop il-published main` |
| *(future)* `nickgogan/{system}` | Private | Any system needing isolated sharing | Same subtree pattern |

### Key Design Choices

1. **Monorepo is the daily driver.** Nick works exclusively in the monorepo. All commits happen here. The hierarchical CLAUDE.md structure, cross-system skills, and Obsidian vault integrity depend on a single repo.

2. **Published repos are one-way mirrors.** `git subtree push` syncs content from monorepo to published repos. Published repos never push back. Collaborators with write access to published repos should fork + PR if they want to contribute.

3. **Governance snapshot for cross-references.** Systems that reference meta-system governance docs (constitution, vocabulary, etc.) include a `_governance/` snapshot directory. This allows the published repo to function standalone without access to the monorepo. Refresh quarterly or when governance docs change.

4. **Git has no path-level access control.** This architecture exists because git cannot restrict access to subdirectories within a repo. Selective sharing requires separate repos. CODEOWNERS provides review workflow, not access control.

5. **Branch strategy: main only.** This is a knowledge vault, not a code repo. No feature branches or PRs for the owner's work.

### Access Model

| Person | MetaSystem (monorepo) | Published system repos |
|--------|----------------------|----------------------|
| Nick | Owner (full access) | Owner (full access) |
| JR | Collaborator (push) | N/A (has monorepo access) |
| Selective collaborators | No access | Read-only on specific system repos |

### Remotes

```
origin       → nickgogan/MetaSystem (monorepo)
il-published → nickgogan/improvement-loop (published IL)
```

Future system publishing follows the same pattern: `{name}-published` remote + `git subtree push --prefix={path}`.

### .gitignore

Key exclusions:
- `.claude.json` — local API keys
- `.claude/settings.local.json` — machine-specific MCP configs and paths
- `.obsidian/workspace.json` — personal workspace state
- `.obsidian/workspace-mobile.json` — mobile workspace state

`settings.json` (base permissions) IS committed and shareable.

## Why

Perplexity deep research across production agentic coding setups confirmed that context fragmentation across repos degrades agent reasoning quality, while monorepos preserve coherent architectural context. The hybrid approach — monorepo for unified context + subtree publishing for selective sharing — is the emerging production consensus. Git's fundamental lack of path-level access control makes separate repos the only mechanism for true access isolation.
