# DD-83

> **For agents:** The IL has two research intake pathways. Periodic scanning via `/research-loop` and on-demand queries via `/research-query`. Both feed the same downstream pipeline (Identify → Extract → Deploy). The persistence gate is user-driven: findings are only written to the KB if the user explicitly opts in. Reports are always written regardless.

## The Constraint

The Improvement Loop supports **two intake pathways** into the research knowledge base:

| Pathway | Skill | Trigger | Output | Persistence |
|---------|-------|---------|--------|-------------|
| **Periodic scan** | `/research-loop` | User invokes on a cadence | Delta report + findings + sources | Always persists findings |
| **On-demand query** | `/research-query` | User asks a research question | Research report + optionally findings + sources | User chooses at persistence gate |

### On-Demand Pathway Flow

```
User asks question
    ↓
Researcher persona activates
    ↓
Check: Does topic fit existing research dimensions?
    ├── YES → Research via Perplexity/WebFetch
    │         → Produce report (always written)
    │         → Ask user: persist findings to KB?
    │         ├── YES → Extract findings + sources (normal pipeline)
    │         └── NO  → Report only, no KB writes beyond the report
    │
    └── NO  → Flag to user:
              "This topic doesn't map to current dimensions."
              ├── User wants persistence → Propose new dimension + mappings, 
              │   get approval, then research + persist
              └── User doesn't want persistence → Research + report only
```

### Key Design Choices

1. **The persistence gate is user-driven.** The Researcher never autonomously writes findings from on-demand queries. This respects DD-29 (human-gated pipeline) and prevents low-quality reactive findings from diluting the KB.

2. **Dimension check is the routing mechanism.** If the topic fits existing dimensions, findings slot into existing guide clusters. If it doesn't, that's a signal — either the question is out of scope for the IL, or the dimensions need to grow. Both are valid outcomes decided by the user.

3. **Reports always written to `operations/research-reports/`.** The research always produces a durable report artifact. Only the findings extraction is gated. This means even ephemeral queries leave an audit trail.

4. **Same downstream pipeline.** Findings created via on-demand queries have the same `pipeline_status: raw` as periodic scan findings. They flow through the same Identify → Extract → Deploy pipeline with the same human gates.

## Compatibility with DD-36

DD-36 establishes that "system evolution is driven by periodic external research, not ad-hoc decisions." DD-36 explicitly does not prevent:
- **Human-initiated improvements** — Nick can propose changes outside the IL
- **Experimentation** — two-way door changes can be tried without waiting for a research cycle

On-demand research is human-initiated. The user asks a question, the system researches it, and findings optionally enter the periodic pipeline with the same gates. DD-36's intent — preventing the system from evolving through reactive one-offs — is preserved because findings still flow through the full pipeline before deployment.

## KB Evidence

The **Dual Ingestion Funnel** finding (`dual-ingestion-funnel-human-clip-plus-llm-research`) predicted this need: two intake paths (human-reactive + LLM-directed) feeding the same pipeline. It flagged deduplication and cross-referencing as the coordination problems to solve.

The **KAIROS** and **Heartbeat Execution Model** findings document the infrastructure primitive: event-driven triggers (reactive) complementing cron triggers (periodic) on the same pipeline.

## Why

The existing `/perplexity-research` skill produces reports only — it cannot persist findings. The `/research-loop` skill persists findings but requires a full periodic scan workflow. There was no pathway for "I have a specific question, research it, and optionally add what you find to the KB." This gap was surfaced during a Librarian test-drive session when the Librarian's KB coverage gaps triggered a need for targeted research.
