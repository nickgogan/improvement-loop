> **For agents (historical):** DD-72 defined what happens to findings at each priority level. P1 and P2 get proposed; P3 stays in the KB as a tracked pattern. Priorities only go up, never down. "Not Flagged" means untriaged — do not treat it as a priority level.

## The Constraint

Research findings follow a strict lifecycle governed by `priority`:

| Priority | Label | Meaning | Next Action |
|----------|-------|---------|-------------|
| **P1** | Implement Now | High-value pattern with clear implementation path | Queue for `/research-proposer` — immediate proposal generation |
| **P2** | Design Required | Valuable pattern that needs design analysis before implementation | Queue for `/research-proposer` with additional design work |
| **P3** | Monitor | Interesting pattern worth tracking but not ready for action | Remains in KB indefinitely. No proposal unless upgraded. |
| *Not Flagged* | Untriaged | Finding has not been assessed for priority | Awaits initial triage during next review pass |

### Priority Upgrade Rules

- Priority can only be **upgraded**: P3 to P2, P2 to P1.
- Priority is **never downgraded**. If a finding loses relevance, it stays at its current priority with a frontmatter note explaining why action is deferred.
- Upgrade requires evidence: a new source confirming the pattern, production validation, or an explicit user decision.

### Lifecycle Exits

A finding leaves the active KB only by:
1. Being consumed into an approved proposal (P1/P2 path)
2. Being archived after the proposal it fed is codified
3. Explicit user decision to archive

## Why

Sessions 1-9 accumulated 318 findings but never ran `/research-proposer`. The implicit rule was "P1 and P2 get proposed, P3 stays" — but this was never formalized. Without explicit lifecycle semantics, there is no clear answer to "what happens to P3 findings?" or "when does a finding leave the KB?" This ambiguity creates two risks:

- **Zombie findings.** P3 findings accumulate indefinitely with no review trigger.
- **Priority inflation.** Without a no-downgrade rule, priorities oscillate based on recency bias rather than evidence strength.

Formalizing the lifecycle makes the pipeline deterministic: every finding has exactly one priority, and that priority maps to exactly one next action.
