# DD-99

> **For agents:** When the Unrouted Bucket holds ≥5 findings sharing `same-problem` links, Codifier emits a graduation proposal at `operations/graduation-proposals/<YYYY-MM-DD>-<theme>-graduation-proposal.md`. The proposal recommends PROMOTE (new dimension + guide cluster, gated by a per-graduation DD) OR ABSORB (route into an existing dimension, gated by a routing-table update + Nick ruling). Promotion uses a fresh `theme-graduation` changelog entry on the new guide; absorption uses the existing `dimension-rebalance` trigger when the rebalanced findings flow through their next regen.

---

## The Constraint

**Trigger.**

A theme in the routing table's Unrouted Bucket qualifies for graduation review when:

1. **Finding-count threshold.** ≥5 unrouted findings cluster by category, tag, or `same-problem` link.
2. **Linkage threshold.** The findings share `same-problem` relationships (per the four-relationship type system codified by `/finding-crosslink`). At least one `same-problem` link spans the cluster — the cluster is not just a category co-occurrence.

Both conditions are required. Five unrouted findings without `same-problem` linkage is a categorical accident, not a graduation candidate.

**Detection.** Codifier checks the trigger when `/identify-artifacts` reads the routing table for unrouted-bucket review (Step 6 of the identification pipeline). When the trigger fires, `/identify-artifacts` flags the cluster in its report's "Candidate Cluster" section per spec §2.4. Codifier then emits a graduation proposal as a separate artifact.

**Response — propose with explicit recommendation.**

On trigger, Codifier emits a structured proposal at `operations/graduation-proposals/<YYYY-MM-DD>-<theme>-graduation-proposal.md`. The proposal contains:

- **Theme identity** — proposed theme name, current Unrouted Bucket entries, total finding count.
- **Linkage map** — the `same-problem` relationships among the findings; cross-category or cross-dimension links called out explicitly.
- **Path recommendation** — one of:
  - **`PROMOTE — new dimension + guide cluster`**: the cluster is structurally distinct enough to warrant its own dimension (research-dimensions.md addition) and its own guide cluster (routing table addition).
  - **`ABSORB — into existing dimension`**: the cluster is a sub-theme of an existing dimension; folding it into that dimension's primary guide via `/dimension-rebalance` is sufficient.
  - **`DEFER — sub-threshold linkage`**: 5 findings present but `same-problem` links are weak (single connector, peripheral cluster); recommend monitoring through one more research-loop cycle before proposing.
- **Per-path execution sketch** — what artifacts the executing path would touch (research-dimensions.md, routing-table rows, new-guide stub, dimension-rebalance scope).
- **Cross-dimension flag** — if findings span ≥2 existing dimensions, this disqualifies the absorption path (absorbing into one dimension loses the cross-dimension nature). Codifier's recommendation in that case is PROMOTE or DEFER, never ABSORB.

**Per-graduation DD required for PROMOTE.** A new dimension is a structural addition — research-dimensions.md is the IL's dimensional contract, and adding a row materially expands the system's scanning scope. Promotion requires Nick to approve a per-graduation DD that codifies:

- The new dimension's name, definition, and category-mapping rules.
- The new guide cluster's title, practitioner question, and lifecycle stage.
- The findings being graduated (which Unrouted Bucket entries move into the new cluster).
- Any existing guides whose dimension mapping changes (typically none, but possible).

**Routing-table update + Nick ruling for ABSORB.** Absorption is procedurally lighter — the dimension mapping is updated, findings get reclassified by `/dimension-rebalance`, and they flow into the existing guide's next regen via the standard `dimension-rebalance` trigger (already in DD-94's enum, no amendment needed). Absorption does NOT require a per-graduation DD because no new structural artifacts are created.

**The asymmetry is intentional.** Promotion creates a new dimension (DD-level structural change); absorption only routes findings into existing infrastructure (operational change). Same-DD weight on both would over-burden the absorption path; same-operational-weight on both would under-protect the promotion path.

## Why

**Mass alone is misleading.** Five findings sharing nothing but a category label is a tag mistake, not an emerging theme. The `same-problem` link requirement filters categorical accidents from genuine clusters: when findings independently identify the same practitioner problem, that's evidence of a coherent surface; when they share only a category, it's just folder hygiene.

**The two-path split is corpus-driven.** Per session 73's routing table:

- **Governance graduation (2026-04-19):** 2 P1 + 8 P2 findings → G9 (Agent Governance and Trust). PROMOTE path. Findings spanned multiple existing dimensions (oversight is its own concern); absorption would have lost the cross-dimension nature.
- **Memory Architecture as sub-dimension (planned via IB-153 / `/dimension-rebalance`):** Memory findings absorbed into Context Engineering parent. ABSORB path. Findings have natural home; new dimension would over-fragment.

DD-99 codifies the procedure both informal precedents already used; the asymmetric DD/operational weight matches the asymmetric blast radius.

**Why a separate proposal artifact rather than inline in `/identify-artifacts` reports.** The identification report flags the cluster (per spec §2.4); the proposal artifact is the separate, durable, citable record of what Codifier recommends and why. Identification reports are session-scoped (one per `/identify-artifacts` run); a graduation proposal must persist independently of the identification cycle that surfaced it. Same separation pattern as DD-96 (drift reports) and DD-98 (split proposals): detection in the natural read flow; proposal as a standalone file.

**Why DEFER is an explicit recommendation, not an absence.** Codifier emitting a proposal with no recommendation is a process gap — the proposal artifact would exist without telling Nick what to do with it. DEFER closes that gap: "5 findings present, linkage weak, hold for more evidence" is itself the recommendation, written down so the cluster's history is auditable.

**Why ABSORB skips the per-DD requirement.** A per-graduation DD on the absorption path would file ~1 DD per dimension-rebalance cycle. The mechanism cost (DD authorship, Nick read, governance overhead) exceeds the structural change (one routing-table edit + a `/dimension-rebalance` run). DD-29's stage-boundary gate is satisfied by Nick's ruling on the proposal artifact directly — the proposal IS the gate document, not a precursor to one.

## Rules for Codifier

1. **Detect on `/identify-artifacts` Step 6.** When `/identify-artifacts` reads the routing table to flag candidate clusters, Codifier evaluates the Unrouted Bucket against the trigger. Flagging in the identification report is the heads-up; emitting the graduation proposal is the follow-up artifact.

2. **Both thresholds, no shortcuts.** ≥5 findings AND `same-problem` linkage. Categorical co-occurrence without `same-problem` link does NOT trigger graduation. Codifier may surface the categorical observation in the identification report's narrative but does not emit a graduation proposal.

3. **One proposal, one recommendation.** The proposal artifact carries exactly one path recommendation: PROMOTE | ABSORB | DEFER. If Codifier cannot decide between PROMOTE and ABSORB, the recommendation is DEFER with an explanation; ambiguous proposals are a defect.

4. **Cross-dimension findings disqualify ABSORB.** If the cluster's findings span ≥2 existing dimensions per the routing table's Dimension → Guide mapping, ABSORB is not a valid recommendation. Codifier must choose between PROMOTE or DEFER.

5. **Never auto-execute either path.** Codifier never edits research-dimensions.md, never updates the routing table, never creates new guide stubs, and never invokes `/dimension-rebalance` based on its own proposal. Execution requires Nick's ruling — DD for PROMOTE, ruling-on-proposal for ABSORB.

6. **Stale-proposal hygiene.** If between proposal emission and Nick's ruling, the cluster's finding count drops below 5 (a finding gets reclassified, the bucket gets repaired by `/linkage-repair`, etc.), Codifier flags the proposal as stale on next detection cycle. A new proposal supersedes the stale one; the stale proposal is retained for audit (not deleted).

## Graduation Execution (Post-Approval)

### PROMOTE path

After the per-graduation DD lands:

1. **research-dimensions.md.** Add the new dimension entry per the DD's specification. Update the dimension count; preserve existing dimension order (append-only by default).

2. **Routing table.**
   - Add new row to "Active Clusters" with the new guide's ID, title, practitioner question, lifecycle stage, and dimensions.
   - Add new row to "Synthesis Status" — initially with no synthesis date (the new guide has no body yet).
   - Update "Dimension → Guide Mapping" with the new dimension's primary guide entry.
   - Remove the graduated findings from the "Unrouted Bucket" subsection.
   - Append a "History" entry naming the graduation date, the per-graduation DD, and the moved findings.

3. **New guide stub.**
   - Create `extracts/guides/<new-guide-stem>.md` via `/synthesize-guide` running on the graduated findings. The first synthesis is the guide's birth.
   - Open companion changelog at `extracts/guides/changelog/<new-guide-stem>.changelog.md`.
   - First changelog entry uses trigger tag **`theme-graduation`** with body line citing the source-bucket cluster and the per-graduation DD.

### ABSORB path

After Nick rules ABSORB on the proposal:

1. **Routing table.**
   - Update "Dimension → Guide Mapping" to reflect the absorbed theme as a sub-theme of the chosen existing dimension. The "Notes" column documents the absorption.
   - Remove the graduated findings from the "Unrouted Bucket" subsection.
   - Append a "History" entry naming the absorption date, the proposal file, and the destination guide.
   - No new "Active Clusters" row is added (the existing cluster absorbs the findings).

2. **`/dimension-rebalance` run.**
   - Reclassify the affected findings to the destination dimension per the standard dimension-rebalance flow.
   - Findings flow into the destination guide on its next `/synthesize-guide` regen, using the existing `dimension-rebalance` trigger tag (already in DD-94's enum — no amendment).

3. **No new guide created; no new changelog opened.** The destination guide's existing changelog accumulates the next entry on regen; that entry's trigger is `dimension-rebalance`.

## Trigger-Tag Enum Amendment to DD-94

DD-94's closed trigger-tag enum is amended to add one tag:

- **`theme-graduation`** — used only on the **PROMOTE path**, only on the new guide's first changelog entry. Body line: "First synthesis from graduated theme [[<theme-name>]] per [[DD-XXX]]" where DD-XXX is the per-graduation DD.

The ABSORB path uses the existing `dimension-rebalance` tag — no amendment needed for that path.

## Failure Modes and Recovery

| Failure mode | Detection | Recovery |
|---|---|---|
| 5 findings present in Unrouted Bucket but no `same-problem` links | Codifier's linkage check returns no qualifying relationships | NO proposal emitted. The bucket retains the findings; they are categorical co-occurrences awaiting evidence. |
| 5 findings with weak linkage (one connector, peripheral cluster) | Codifier emits proposal with recommendation DEFER | Nick rules: defer (continue monitoring), force PROMOTE (override Codifier's caution), or reclassify some findings out of the bucket. |
| Findings span ≥2 existing dimensions; Codifier's recommendation is PROMOTE | The cross-dimension flag is set on the proposal | Per-graduation DD codifies the cross-dimension nature into the new dimension's definition; routing-table dimension-mapping reflects the cross-dimension origin. |
| Codifier emits ABSORB recommendation but findings actually span dimensions | Caught at proposal review by Nick | Nick rejects ABSORB; Codifier re-emits with PROMOTE or DEFER. The defective proposal is retained for audit. |
| `/dimension-rebalance` (ABSORB execution) reclassifies findings into a dimension whose guide is at split-trigger threshold | DD-98's split trigger fires on the receiving guide | Two proposals stack: a graduation proposal (the original) and a split proposal (the absorption-driven). Nick rules sequencing: ABSORB first, then split; or defer ABSORB until the receiving guide is split. |
| Per-graduation DD lands but the routing-table update and new-guide creation diverge from DD's specification | Post-execution audit | Procedural violation; flagged in next governance audit. Recovery: revert via git; re-execute against DD's spec. |
| Stale proposal: cluster drops below 5 findings between emission and Nick gate | Codifier's next detection cycle finds finding count <5 | Codifier appends a "stale-as-of-<date>" header to the proposal artifact. The stale proposal is not deleted (audit trail); a new proposal is emitted if the cluster re-crosses threshold later. |

## Acceptance Criteria

| Test | Expected |
|---|---|
| Unrouted Bucket holds 4 findings with `same-problem` links | NO proposal emitted. Sub-threshold count. |
| Unrouted Bucket holds 5 findings with NO `same-problem` links | NO proposal emitted. Linkage threshold not met. |
| Unrouted Bucket holds 5 findings with `same-problem` links, all in one existing dimension | Proposal emitted; recommendation may be ABSORB or PROMOTE based on Codifier's read of structural distinctness. |
| Unrouted Bucket holds 5 findings with `same-problem` links, spanning 2 existing dimensions | Proposal emitted; recommendation MUST be PROMOTE or DEFER. ABSORB is invalid. |
| Per-graduation DD approved (PROMOTE); execution skill creates new dimension + guide | research-dimensions.md updated; routing table has new row; new guide stub created with first `theme-graduation` changelog entry. |
| Nick rules ABSORB on proposal | Routing-table dimension-mapping updated; `/dimension-rebalance` run; affected findings reclassified; destination guide's next regen uses `dimension-rebalance` trigger; no new DD filed. |
| Codifier auto-creates a new dimension based on its own proposal | Procedural violation; flagged in next governance audit. The proposal is read-only by contract. |
| Cluster crosses threshold; proposal emitted; one finding gets reclassified out before Nick gates | Codifier flags proposal as stale on next detection cycle; proposal artifact retained with stale header. |

## Scope and Non-Goals

- **In scope:** The Unrouted Bucket section of the routing table. Themes graduate from this bucket via DD-99's procedure.
- **In scope:** The DD-94 trigger-tag enum amendment adding `theme-graduation`.
- **Out of scope:** De-graduation — the inverse, where a guide's findings are returned to the Unrouted Bucket because the cluster has dispersed. Not codified; if a cluster genuinely fragments, the path is via `/dimension-rebalance` reclassifying findings out, not a procedural reversal.
- **Out of scope:** Auto-detection of `same-problem` link strength. Codifier's judgment of "weak linkage" is LLM-loose — no structured threshold for what counts as a strong vs. weak `same-problem` cluster. Calibration in line with DD-97's loose-trigger philosophy. False-positives caught at Nick's gate.
- **Out of scope:** Numeric tuning of the 5-finding threshold. Spec-defined; if observed corpus dynamics show wrong, amend in follow-up DD with evidence.
- **Out of scope:** Cross-DD batch graduation. Each graduation cluster is one proposal, one ruling. Two simultaneous graduation candidates produce two proposals, two rulings (or one combined DD if Nick chooses to bundle for the PROMOTE path).
- **Out of scope:** Live-location lifecycle. New guides created via PROMOTE deploy from `extracts/guides/` to live locations per DD-29; DD-99 only addresses staging.
- **Out of scope:** Researcher-side bucket management. The Unrouted Bucket is fed by `/identify-artifacts`'s routing logic per DD-81; DD-99 operates on the bucket contents, not on the bucket-feeding logic.
