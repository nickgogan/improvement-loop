# DD-100

> **For agents:** When a template's source finding evolves, `/extract-artifacts` writes `<name>-v2.md` next to the existing `<name>.md`. Each version is independent — its own frontmatter, its own contract, its own `last_change_*`. Never overwrite an existing version's body. For agents, the same shape applies but Nick must approve before any version bump (DD-82 invariant). Nick's deployment to the live location is what makes a version canonical; the staging directory accumulates the version history.

---

## The Constraint

**Filename convention.**

For a template at `extracts/templates/<name>.md`, additional versions live as siblings:

```
extracts/templates/<name>.md           ← v1 implicit (no suffix)
extracts/templates/<name>-v2.md        ← v2
extracts/templates/<name>-v3.md        ← v3
```

For an agent at `extracts/agents/<name>.md`, the same pattern:

```
extracts/agents/<name>.md              ← v1 implicit
extracts/agents/<name>-v2.md           ← v2
extracts/agents/<name>-v3.md           ← v3
```

**Version is an integer N starting at 2.** No decimals, no semver, no minor versions. The unsuffixed filename is v1 by convention; explicit suffixes start at `-v2`. This matches the spec's `<name>-v<N>.md` shape and avoids a `--v1.md` filename for the implicit baseline.

**Each version is an independent artifact.** Every version carries its own frontmatter, distinct from sibling versions:

- Own `source_finding` — typically the same finding as the prior version (the source whose evolution drove the version bump), but can be a different finding if Nick directs.
- Own `extraction_date` — the date this version was extracted; never inherited from prior versions.
- Own DD-95 `last_change_session` and `last_change_sl` — the session that created this version (or last updated it if the version is later edited).
- Own DD-78 `contract` (ContractSpec) — versions may carry materially different contracts; cross-version contract continuity is NOT guaranteed by DD-100.
- Own DD-92 `context` (ContextSpec) — same; ContextSpec evolves with the version.
- Own `version` field — see schema update below.

**A new `version` frontmatter field.**

```yaml
version: 2
```

- Field type: integer.
- Field requirement: **optional on v1** (legacy artifacts predate DD-100; absence is treated as `version: 1`); **required on v2+**.
- Field semantics: matches the suffix in the filename. `<name>-v2.md` carries `version: 2`. `<name>-v3.md` carries `version: 3`. The unsuffixed `<name>.md` either omits the field (legacy) or carries `version: 1` (explicit).

**Triggers for version bump.**

- **Templates.** `/extract-artifacts` may auto-bump a template's version when the form classification of an incoming finding is `template` AND the corpus scan identifies the candidate as an evolution of an existing template (rather than a genuinely new template). The "evolution vs. new" judgment is LLM-loose, mirroring DD-97's extension-rubric calibration. Codifier emits a structured proposal naming the existing template, the candidate evolution, and a diff sketch — Nick gates the bump (the Nick gate is per DD-29 and matches DD-97's propose-don't-decide pattern).
- **Agents.** Version bumps require **Nick's prior approval** per DD-82 (agents are never auto-created or auto-modified). Codifier flags an agent-classified finding as a candidate for Nick's review; if Nick approves, regen writes `<name>-v<N+1>.md`. No `/extract-artifacts` auto-bump path.

**Promotion = deployment.**

A version becomes canonical when Nick deploys it from `extracts/{templates,agents}/<name>-v<N>.md` to the live location (e.g., `meta-system/knowledge/templates/<name>.md`, `.claude/agents/<name>.md`). Deployment is governed by DD-29 (manual; human gate). The live location holds exactly one canonical version at a time; the staging directory holds the version history.

DD-100 does NOT add a `promoted: true` frontmatter marker — promotion is observable from the live-location filesystem, not from staging metadata. Coupling staging metadata to live deployment would create a drift surface (the marker could go stale relative to the deploy state).

**No autonomous overwrite.** `/extract-artifacts` never writes to an existing `<name>-v<N>.md` once it exists. Once written, a version is immutable from the skill's perspective — only Nick may edit a deployed version's content (and even then, the typical path is a fresh version bump, not an in-place edit).

## Why

**Versioning matches the stability profile.** Per spec §4.1: templates are "high but versioned" — schema or vocabulary changes break every rendered instance, so explicit version coexistence is industry-standard (compare: schema migrations, language versions). Agents are "very high (stable)" — system-level decisions only, rare changes, high stakes. Both classes are downstream-coupled: template consumers render against a specific schema; agent consumers invoke against a specific persona. Silent in-place modification breaks consumers; side-file versioning preserves the prior version while letting the new one accumulate review.

**Why side-file over in-place.** Three alternatives were considered (per spec §1.2):

- **Option A — full regenerate (overwrite v1):** clobbers the deployed version's content. If Nick has tuning in place, lost without warning. Fails for templates (consumers break) and agents (persona drift untraceable).
- **Option B — merge-diff:** complex, expensive, and unjustified for the low change volume of these two classes. The merge-cost dwarfs the version-coexistence cost.
- **Option D — side-file regenerate (selected):** the prior version stays intact, the new version is fully independent, Nick chooses which to deploy. Lowest mechanism cost; cleanest semantics.

**Why per-version frontmatter independence.** A single artifact-with-history pattern (e.g., `version_history: [...]` array on one file) would couple versions in-place — every update touches one file. DD-95's `last_change_*` semantics, DD-78 ContractSpec, DD-92 ContextSpec all assume one frontmatter set per artifact. Per-version files preserve those invariants without exception. Adding a new version is a fresh file write; old versions are read-only.

**Why integer N rather than semver.** Templates and agents in IL are not externally-versioned APIs — they are internal artifacts whose consumers are governed by DD-29's manual deployment gate. Semver's major/minor/patch distinction encodes consumer-impact information that DD-29 already mediates structurally; the integer suffix is sufficient for "which version is which." If external versioning surfaces in the future (e.g., agents distributed as a package), a follow-up DD can map integer N to semver retroactively.

**Why agents require Nick approval, templates don't (as strictly).** DD-82 makes agent identity a system-level concern: the 4-agent architecture is fixed; new agents would be system-level design decisions, not Codifier output. A template version bump is a content evolution within an existing slot — Codifier can propose; Nick gates. An agent version bump is a persona evolution that may shift IL behavior in ways the existing skills depend on — Nick's approval-before-proposal is the right calibration. The asymmetry mirrors DD-97 (templates out of scope for extension; agents never auto-create).

**Why DD-96 scope spans all versions.** DD-96 scans non-guide extracts for source drift. With versioning, multiple versions of a template or agent coexist in `extracts/`. DD-96 reports drift per-version — each version's `source_finding.last_updated > extraction_date` comparison is independent. This produces some noise (older versions may show drift the deployed version doesn't), but Nick's gate filters; aggregated drift across versions is informative for the version-history record. A future amendment may scope DD-96 to "promoted version only" if noise becomes burdensome — but DD-100 does not add a `promoted` marker, so that amendment would require its own structural work.

## Rules for `/extract-artifacts`

1. **On template-classified finding, scan for evolution.** When the form is `template`, before drafting a new artifact, perform a corpus scan over `extracts/templates/` for candidates the new finding is an evolution of. The scan logic is LLM-loose, calibrated like DD-97 (false-positives caught at Nick's gate).

2. **Propose version bump on evolution match.** On match, emit a structured proposal — same shape as DD-97's extension proposal, but the recommendation is `version-bump existing` rather than `extend existing`. The proposal cites:
   - The existing template's current version (highest `version: N` among versions of that template stem).
   - The candidate evolution's diff sketch.
   - The proposed `<name>-v<N+1>.md` filename.
   - Codifier's recommendation (`version-bump` | `create new (false positive)` | `defer`).

3. **Nick gates the bump.** No auto-write. Once Nick rules `version-bump`, `/extract-artifacts` writes `<name>-v<N+1>.md` with full independent frontmatter (per DD-95, DD-78, DD-92, and the new `version: N+1` field).

4. **On agent-classified finding, never auto-bump.** When the form is `agent`, DD-82's never-auto-create invariant fires first. `/extract-artifacts` flags the finding for Nick's review and exits without drafting. If Nick approves a version bump (typically as a separate, manually-scoped action), `/extract-artifacts` is invoked with explicit version-bump intent — same write mechanics as templates, but the prior approval is structural, not skill-resolvable.

5. **Compute next N.** When writing a new version, the skill enumerates `<name>.md` and `<name>-v*.md` siblings in the directory; computes `N = max(existing versions) + 1`. If the unsuffixed file is missing (deleted in error), the skill aborts the write and surfaces the gap — never silently re-create v1 from a non-v1 source.

6. **Filename collision check.** Before writing `<name>-v<N>.md`, the skill verifies the filename is unused. Collision aborts the write with a structured error. The likely cause is N-computation drift; recovery is human review.

7. **No in-place version overwrite.** Once `<name>-v<N>.md` exists, `/extract-artifacts` never overwrites it. Subsequent regen produces `<name>-v<N+1>.md`, not a re-write of `<name>-v<N>.md`.

## Schema Update

`_schema.yaml` is updated as part of DD-100's landing (Phase-3 IB sweep, future session) to add:

- `version: integer` to the frontmatter contract for `template` and `agent` extract types.
- Field requirement: optional on v1 (legacy), required on v2+.

Other extract types (rule, skill) and other frontmatter classes (guide, finding, source, authority) are unaffected by this schema change.

## Backfill (Phase-3 IB sweep, NOT session 74)

The ~12 existing templates and ~5 existing agents in `extracts/{templates,agents}/` predate DD-100 and lack the `version` field. Backfill is deferred to the Phase-3 IB sweep (session 75+); it is NOT in scope for session 74's DD filing.

Backfill semantics when executed:

- v1 implicit artifacts (no version suffix in filename): backfill writes `version: 1` to frontmatter. Optional, but adding it makes DD-100's contract explicit.
- No new files are created during backfill; backfill is frontmatter-edit only.

The backfill does NOT retroactively create `<name>-v2.md` for any artifact — versioning starts forward from DD-100's landing.

## Failure Modes and Recovery

| Failure mode | Detection | Recovery |
|---|---|---|
| `/extract-artifacts` writes `<name>-v2.md` while v1 has been deleted | Skill's pre-write enumeration finds no `<name>.md` baseline | Write aborts; structured error names the missing baseline. Recovery: restore v1 from git, then re-run. |
| Filename collision: `<name>-v3.md` already exists when skill tries to compute N=3 | Pre-write filename check | Write aborts; error names the collision. Likely cause: N-computation race or manual file creation. Recovery: human review. |
| Multiple versions exist; DD-96 reports drift on a non-deployed version | Drift-report entry for `<name>-v2.md` while live location runs `<name>-v3.md` | Codifier's recommendation in the drift report carries context "non-canonical version"; Nick may rule `dismiss as historical` or batch the older version for cleanup. |
| Template version bump proposed; Nick rules `create new (false positive)` instead | Nick's ruling on the proposal | Skill writes a brand-new template (different stem) on next invocation; the existing template's version chain is unchanged. |
| Agent version bump attempted via `/extract-artifacts` without prior Nick approval | Skill flags agent-classified finding and exits without drafting | Skill never writes; Codifier surfaces the candidate to Nick separately. If Nick approves, the bump is performed via explicit version-bump invocation (manual scoping). |
| Live location holds a version not present in `extracts/` | Manual audit | Live-location/staging divergence; flagged in next governance audit. Recovery: copy the live version back to `extracts/` with appropriate `version` field, then resume. |
| Two simultaneous version bumps proposed (e.g., two findings each evolving the same template) | Two proposals targeting the same `<name>` stem with N+1 collision | First-write-wins on N+1; the second proposal is re-emitted with N+2 if Nick rules to bump it after the first. Codifier may bundle the two evolutions into a single bump if the diffs are compatible — same propose-then-Nick-gates pattern. |

## Scope and Non-Goals

- **In scope:** Templates and agents in `extracts/templates/` and `extracts/agents/`. Versioning conventions, schema field, write rules, and DD-96 interaction.
- **Out of scope:** Rules and skills. They use DD-97's extension rubric; versioning is not the right mechanism for those classes (they extend or parameterize existing artifacts, they don't fork). DD-100 explicitly does NOT version rules or skills.
- **Out of scope:** Guides. Guides regen in-place with DD-93 preserved sections + DD-94 companion changelog. Versioning is the wrong mechanism for high-churn guide content (would produce `<guide>-v50.md` over a year).
- **Out of scope:** Findings, sources, authorities. KB primary records, not extracts; their lifecycle is governed separately.
- **Out of scope:** Pruning / archiving older versions. Open question per spec §Open Question 6: "is there an upper bound on how many versions coexist before we archive old ones?" Not codified by DD-100. If the staging directory accumulates >5 versions of a single artifact, a follow-up DD addresses the pruning policy. Default: keep all versions until explicitly directed otherwise.
- **Out of scope:** A `promoted: true` or similar canonical-version marker. Promotion is observable from the live-location filesystem; staging metadata does not duplicate it.
- **Out of scope:** Cross-version content migration. If a template's invariants change between versions in ways that break consumers, the migration is a manual operation handled at the consumer (per DD-29 deployment), not codified here.
- **Out of scope:** Semver mapping. Integer N is the only versioning vocabulary in IL; if a future deployment context requires semver, a follow-up DD maps it.
- **Out of scope:** Live-location lifecycle. Once Nick deploys a version to its live location, the live artifact's drift, edits, and updates are governed by DD-29 — not by DD-100, which only addresses staging.

## Open Questions (Surfaced for Future Sessions)

- **Pruning/archiving threshold.** Open Q6 from spec — at what version count or staleness should older versions be archived from `extracts/` to `archive/`? No data yet to calibrate. Defer until staging accumulation justifies a rule.
- **Cross-version contract continuity.** If `<template>-v2.md` carries materially different ContractSpec invariants than `<template>.md`, downstream consumers may break silently on deployment. DD-29 mediates this manually, but a structured "version delta" report (showing contract changes between v_N and v_{N+1}) may be useful — not codified here. Candidate for future sibling DD if consumer breakage manifests.
- **DD-96 scope refinement.** DD-96 currently scans all versions. If "non-canonical versions" become a reporting noise source, scope to canonical-only — but that requires a `promoted` marker (see Out of Scope above). Address jointly when both pressures emerge.
