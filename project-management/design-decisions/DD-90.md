# DD-90

> **For agents:** Every graduated system's SL entries include a `telemetry:` block at session close. Fields are harness-portable by design. When the current harness can't supply a field, the Owner either estimates it (flagged `estimated`) or writes `"unknown"` — SL entries are not held back, and Nick is not a telemetry source. Capture quality is disclosed as `measured` / `estimated`. When evaluating a harness change, compare capture-layer disclosures against this requirement layer.

## The Constraint

### Requirement layer (harness-portable)

Every SL entry carries a `telemetry:` block with these fields:

| Field | Intent |
|---|---|
| `model` | Model(s) driving the session (multi-value if switched) |
| `tokens_consumed` | Total tokens (input + output + cache read + cache write) |
| `context_window_size` | Max context for the session's primary model |
| `context_window_pct_peak` | Highest context fill reached during the session |
| `turns` | User↔assistant exchange count |
| `tool_calls` | Total tool invocations |
| `subagents[]` | Per-subagent-type: count, avg tokens, total tokens |
| `capture_quality` | `measured` / `estimated` — fidelity disclosure |
| `harness` | Runtime identifier — which harness hosted the session |

These express *what a system wants to know about a session*, independent of the runtime. They survive harness substitution.

### Capture layer (harness-specific)

For each field, the system's Owner documents what the current harness supplies:
- **Measured** — direct telemetry API, reliable
- **Estimated** — Owner's best guess from observable session signals, flagged as such

`"unknown"` is a first-class value when a field is neither measurable nor reasonably estimable. A field with value `"unknown"` is a valid and meaningful record. SL entries are not held back waiting for unknown data.

**Nick is not a telemetry source.** The spec deliberately does not include a "reported" tier — if a field cannot be measured or estimated by the AI/harness, it lands as `"unknown"`. The long-term goal is harness substitution toward richer measurement, not sustained human-in-the-loop reporting.

### Minimum viable harness

A graduated system's harness must expose as **measured** at minimum: `model`, `tokens_consumed`, `context_window_pct_peak`. Subagent-granular token breakdown is a strong preference but not required — Claude Code CLI does not expose it reliably today.

### Harness evaluation criterion

When a system considers substituting harnesses, the prior harness's capture-layer disclosures become the baseline. A candidate harness that exposes richer observability (more fields `measured`, fewer `"unknown"`) is a known upgrade; one that exposes less is a known regression. Regressions are decided explicitly, not accidentally.

### Scope

- **Applies to:** Graduated systems under `systems/` that produce SL entries (IL from session 52 onward; Meta-System if/when it emits SL entries).
- **Applies at graduation to:** Household OS, Claude Build, future systems.
- **No backfill required.** Historical SL entries without `telemetry:` remain schema-valid.
- **Out of scope:** non-SL artifacts (handoffs, reports, etc.) — potential future extension.

## Why

Every graduated system writes SL entries (DD-59). Every system's reflections and drift detection benefit from session-level observability. Codifying the requirement at MetaSystem level delivers three benefits:

1. **Uniform observability across systems.** Owners across systems can run the same drift-detection heuristics because the schema is uniform.
2. **Harness decisions made once.** Re-harnessing work evaluates against a single requirement spec, not N system-specific specs.
3. **`_schema.yaml` amendment lands once.** The workspace-root schema serves all systems — additive, low-risk.

The two-layer architecture (harness-portable requirement + harness-specific capture) separates *what we want to know* from *what today's harness can give us*, so evolution doesn't destabilize the audit trail.
