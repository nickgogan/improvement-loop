# DD-121

> **For agents:** Before creating a `knowledge/` doc that restates a DD, apply the four cache criteria and three exclusions below. The default is NOT to cache — ~88% of DDs correctly have no separate agent-readable copy. Every existing cache must anchor to a Binding `source_dd` and be the only home for that wisdom.

---

## The Constraint

### Cache a DD's wisdom into `knowledge/` only when ALL four hold

1. **Cross-cutting** — applied by multiple skills/agents (or humans+agents broadly), not owned by one skill's procedure.
2. **Reference-shaped** — an agent *reads and judges against* it (a heuristic, model, vocabulary, pattern), rather than *executes* it as steps.
3. **Engine self-knowledge** — about how *this* engine is built/operates (the `knowledge/` body), distinct from external best-practice (the `extracts/` body, DD-111).
4. **Stable** — the wisdom is settled, not still-churning process detail (which stays in its owning skill so it evolves in one place).

### Exclude (do NOT cache) when ANY hold

- It is a **governance / structural fact** → CLAUDE.md / `governance/` / the DD itself.
- It is **operationalized inside one owning skill** → that SKILL.md is the single source of truth; the remedy for traceability is the skill citing its source DD, not a parallel copy.
- It is **external best-practice** → `extracts/` substrate (Librarian-composed), not DD-derived.

### Anti-redundancy invariant

Every cached `knowledge/` doc must (a) carry a `source_dd` that is **Binding** (never Superseded), and (b) be the **single** agent-readable home for that wisdom. A cache anchored to a superseded DD, or one that duplicates a skill's procedure, is debt — re-anchor or delete.

### Ownership

Cached DD-wisdom is **Owner-owned** (DD-86): it derives from governance the Owner stewards, and the Owner's drift tooling (`/maintain-docs`, `/translate-governance`, `/system-health`) maintains it. The Librarian consumes caches but does not author or steward them — the `extracts/` + concept-doc boundary stays Librarian-side.

### No mechanism

There is no cache-every-DD process. Caching is a per-item exception justified against the four criteria at the moment demand appears (Rule 11).

## Why

The policy was ratified in practice (session 125): `governance/agent-rules.md` justifies its DD-37 cache "per the DD-wisdom caching policy" — but the policy's only carrier was a `stage: draft` design note. A Binding rule should not anchor to a draft note (substrate audit, gate G6). This DD is the decision-shaped distillation per DD-116 routing; the note's coverage map and per-DD survey remain in the archived note as evidence.
