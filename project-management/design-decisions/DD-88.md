# DD-88

> **For agents:** DD-88 defines what happens to findings at each priority level in the post-DD-80 pipeline. P1 and P2 get classified (`/identify-artifacts`) and then extracted or synthesized depending on form. P3 stays in the KB as a tracked pattern and enters the pipeline only on priority upgrade. Priorities only go up, never down. "Not Flagged" means untriaged — do not treat it as a priority level. The field is `priority` (renamed from `proposer_priority`).

---

## The Constraint

Research findings follow a strict lifecycle governed by the `priority` frontmatter field:

| Priority | Label | Meaning | Next Action |
|----------|-------|---------|-------------|
| **P1** | Implement Now | High-value pattern with clear implementation path | Queue for `/identify-artifacts`. Non-pattern forms route to `/extract-artifacts`. Pattern forms route to `/synthesize-guide`. |
| **P2** | Design Required | Valuable pattern that needs design analysis before implementation | Same classification path as P1. Extraction or synthesis may surface design questions for Nick at review. |
| **P3** | Monitor | Interesting pattern worth tracking but not ready for action | Remains in KB indefinitely. No classification pass unless upgraded. Eligible for `/reassess-priorities` if evidence accumulates. |
| *Not Flagged* | Untriaged | Finding has not been assessed for priority | Awaits initial triage during next Researcher intake or reassessment pass. |

### Priority Upgrade Rules

- Priority can only be **upgraded**: P3 → P2, P2 → P1.
- Priority is **never downgraded**. If a finding loses relevance, it stays at its current priority with a frontmatter note explaining why action is deferred.
- Upgrade requires evidence: a new source confirming the pattern, production validation, convergent implementation across ≥3 independent repos, or explicit user decision. See `/reassess-priorities` criteria for the thresholds.

### Lifecycle Exits

A finding leaves the active "raw" state only by:

1. Being consumed by `/extract-artifacts` into a staged artifact in `extracts/{form}/` (non-pattern forms). Frontmatter transitions to `pipeline_status: extracted` with `consumed_by` populated.
2. Being consumed by `/synthesize-guide` into a guide in `extracts/guides/` (pattern forms). Frontmatter transitions to `pipeline_status: synthesized`.
3. Explicit user decision to archive.

A finding may be consumed by both an extraction and a synthesis — in which case `pipeline_status` reflects the later transition and `consumed_by` lists both artifacts.

## Why

DD-72 governed this lifecycle under the Proposer pipeline (`Research → Propose → Codify`). DD-80 eliminated the Proposer stage and replaced it with `/identify-artifacts` + `/extract-artifacts` — but left DD-72 orphaned, describing a workflow that no longer exists. DD-88 restates the lifecycle in the current pipeline's terms.

Two substantive changes beyond DD-72:

1. **Pattern findings route to guide synthesis, not individual extraction** (DD-81). DD-72 treated all P1/P2 findings as proposal candidates. DD-88 splits the path by form: non-pattern forms extract individually, pattern forms aggregate into end-directed guides.
2. **P3 findings can now re-enter the pipeline via `/reassess-priorities`.** DD-72 implied P3 was terminal unless upgraded by fiat. DD-88 makes the upgrade path explicit: evidence-driven reassessment with defined thresholds.

The field rename (`proposer_priority` → `priority`) is a cosmetic consequence of removing the Proposer from the model. The neutral field name matches the pattern of other finding frontmatter fields (`category`, `evidence_strength`, `adoption_status`, `pipeline_status`).
