# DD-101

> **For agents:** When `/synthesize-guide` runs on pattern findings, it scans each finding's body for embedded artifact-shaped content (a rule, a skill procedure, a template scaffold). On detection, it appends a row to `extracts/guides/<guide-stem>.harvest-queue.md` — never auto-extracts. The original pattern finding remains pattern-classified; the harvested candidate is held in queue until Nick rules. Nick-approved rows feed `/extract-artifacts` with `source_finding` = the original pattern finding and target form = the harvested form. DD-97 then fires for rule/skill targets to govern extend-vs-new. Agents are never harvested (DD-82 invariant).

---

## The Constraint

**Trigger.**

When `/synthesize-guide` is in the absorption phase of regen (reading pattern findings to build the guide body), the skill performs a per-finding co-occurrence scan:

1. For each pattern finding being absorbed, examine the finding's body for prose that reads as artifact-shaped content of a non-pattern form:
   - **Rule shape** — imperative directive ("never X", "always Y"), machine-enforceable, fits the rule artifact form per the form-classification rubric.
   - **Skill shape** — a procedure with input/output, invocation contract, step-by-step structure.
   - **Template shape** — a structural scaffold meant for rendering (frontmatter blocks, placeholder fields, structural form).
2. The detection is **LLM-loose**, calibrated to match DD-97's extension-rubric philosophy: false-positives are tolerable (cost = one Nick gate per row); false-negatives are tolerable (cost = the embedded artifact stays embedded until next regen surfaces it, or another consumer discovers it per DD-77).

**Agents are excluded.** DD-82's never-auto-create invariant for agents extends to harvest. The harvest queue never produces an agent-form row; if the LLM would propose one, the row is suppressed and the observation is logged inline in the synthesis report (not the queue) for Nick's separate review.

**Response — append to per-guide harvest queue.**

For a guide at `extracts/guides/<guide-stem>.md`, the harvest queue lives at:

```
extracts/guides/<guide-stem>.harvest-queue.md
```

One harvest queue per guide. The path mirrors DD-94's companion changelog convention (`<guide-stem>.changelog.md`) — same structural pattern, different file purpose.

**Queue file shape.**

```markdown
# Co-occurrence Harvest Queue — <Guide Title>

Embedded artifact candidates surfaced during `/synthesize-guide` runs. Per DD-101.
Nothing here is auto-extracted; rows feed `/extract-artifacts` only after Nick rules.

| Date queued | Status | Target form | Source finding | Suggested headline | Recommendation |
|---|---|---|---|---|---|
| 2026-04-XX | queued | rule | [[<finding-stem>]] | <one-line title> | extract via `/extract-artifacts` |
| 2026-04-XX | nick-dismissed | skill | [[<finding-stem>]] | <one-line title> | dismiss as inline |
| 2026-04-XX | extracted | template | [[<finding-stem>]] | <one-line title> | (extracted to [[<artifact-stem>]]) |

## Per-row details

### <finding-stem>::rule::<headline-slug>

**Date queued:** 2026-04-XX
**Status:** queued
**Source finding:** [[<finding-stem>]]
**Source excerpt:**
> <short verbatim excerpt of the embedded prose, ≤8 lines>

**Codifier's reading:** <1–3 lines on why this looks rule-shaped>
**Suggested headline:** <proposed artifact title>
**Recommendation:** `extract via /extract-artifacts` | `dismiss as inline` | `merge into existing [[<artifact-stem>]]`
**Resolution:** (filled when Nick rules)
```

The summary table at the top is for scanning; the per-row details below carry the substance. New rows append to both surfaces; existing rows are updated in place when status changes.

**Per-row content fields (required):**

- **Date queued** — ISO date when the row was first appended.
- **Status** — closed enum: `queued` | `nick-approved` | `nick-dismissed` | `extracted` | `superseded`.
- **Target form** — closed enum: `rule` | `skill` | `template`. (Pattern is excluded — patterns route to guides, not the harvest queue. Agents are excluded — DD-82 invariant.)
- **Source finding** — the pattern finding whose body contained the embedded prose.
- **Source excerpt** — verbatim quote of the embedded prose, ≤8 lines, sufficient to identify the candidate. Long candidates use ellipsis with the structural anchor preserved.
- **Codifier's reading** — 1–3 lines explaining why this prose reads as the target form (cites form-rubric criteria when relevant).
- **Suggested headline** — Codifier's proposed artifact title.
- **Recommendation** — closed enum: `extract via /extract-artifacts` | `dismiss as inline` | `merge into existing [[<artifact-stem>]]`.
- **Resolution** — filled when Nick rules; closed enum: `extracted to [[<artifact-stem>]]` | `dismissed` | `merged into [[<artifact-stem>]]` | `superseded`.

**Append-only across regen cycles.** Each `/synthesize-guide` regen scans pattern findings for the (now-current) guide cluster. New rows append. Existing rows persist with their current status — status transitions are by Nick's ruling, not by regen activity. Rows are never deleted; superseded rows are marked `superseded` (e.g., when the source finding is removed from the cluster on a later regen).

**Duplicate suppression at write.** Before appending a new row, the skill checks for an existing row with the same (source_finding, target_form) tuple. If a row exists with status `queued` or `nick-dismissed`, no new row is appended (the prior row stands). If a row exists with status `extracted` or `superseded`, no new row is appended (the candidate is already resolved). This prevents queue-bloat from regen cycles re-detecting the same embedded prose.

**Promotion to `/extract-artifacts`.**

Nick-approved rows (status: `nick-approved`) feed `/extract-artifacts` directly:

- The harvested artifact's `source_finding` = the original pattern finding (the row's source finding pointer).
- The harvested artifact's `assigned_form` = the row's target form.
- DD-97's extension rubric fires for `rule` and `skill` targets — `/extract-artifacts` performs its corpus scan and may emit an extension proposal instead of creating a new artifact. The extension proposal is a separate artifact from this DD's queue; the queue row's eventual resolution captures the outcome.
- DD-100's versioning rubric fires for `template` targets — the corpus scan may identify the harvested candidate as an evolution of an existing template, triggering version bump rather than new template creation.
- On successful extraction, the queue row's status is updated to `extracted` with a pointer to the new (or extended/version-bumped) artifact.

The original pattern finding remains pattern-classified throughout. Its `consumed_by[]` array gains the new harvested artifact's pointer alongside the original guide's. DD-77's "Router picks one form, full stop" is preserved — the Router never assigned a secondary form; the harvest is an extract-time consumer-side resolution.

## Why

**Embedded artifacts disappear into guide bodies otherwise.** Without DD-101, a pattern finding whose body contains an embedded rule (or skill, or template) gets absorbed into the guide and the embedded content is rendered as part of the guide's prose. The rule never gets independently codified; consumers who would benefit from a standalone rule artifact don't see one. DD-77 says co-occurrence is "resolved at read time by downstream consumers" — but without an explicit mechanism for one specific consumer (`/synthesize-guide`) to surface what it sees, the resolution is implicit and fragile.

**DD-77 said the WHAT; DD-101 says the HOW for one consumer.** DD-77's negative design decision (no Router-side co-occurrence flagging) was correct: forward-flagging creates stale maintenance edges. But "resolved at read time by downstream consumers" only works if downstream consumers actually do the resolving. `/synthesize-guide` is a downstream consumer of pattern findings; DD-101 is its codified resolution path. Other consumers (e.g., Nick reading a deployed guide and noticing an embedded rule) remain the implicit DD-77 path.

**Why a per-guide queue rather than centralized.** A central harvest queue across all guides would force grep-by-guide for review; a per-guide queue lets Nick review in the context of the guide that surfaced the candidates. Same per-class locality argument as DD-94 (per-guide changelog vs. centralized log) — locality wins where review is per-context.

**Why append-only across regen.** Each regen of a guide re-scans the same (or evolved) pattern findings. Without append-only semantics, a regen would either: (a) re-emit the same row (bloat), or (b) silently drop dismissed rows (audit-trail loss). Append-only with duplicate suppression captures both: dismissed rows stay (audit), and re-detection doesn't re-emit (no bloat).

**Why Nick gates per-row, not per-batch.** Co-occurrence judgment is artifact-by-artifact. A guide's regen may surface 5 candidates; one is a clear rule, two are edge cases, one is a false positive, one is a duplicate of an existing rule. Per-row review respects the per-candidate analytical work; per-batch approval would force coarse rulings that lose precision. Same calibration as DD-97's per-proposal Nick gate.

**Why DD-97 fires downstream.** When a queue row is approved and `/extract-artifacts` runs, DD-97's extension rubric for rules/skills already governs the extend-vs-new question. DD-101 doesn't duplicate that logic — it produces the candidate; DD-97 governs the candidate's absorption. This separation respects DD-97's existing discipline; DD-101 is a NEW feeder, not a replacement.

**Why agents are excluded.** DD-82 makes agent creation a system-level decision; agents are never auto-created. Even if a pattern finding's body contains agent-shaped content, the harvest queue would not surface it as a candidate (it would only reach the inline narrative in the synthesis report). Surfacing agent candidates in the queue would imply a path-to-agent-creation that contradicts DD-82.

**Why templates land in the queue (not auto-versioned).** A pattern finding's body may contain template-shaped content (a structural scaffold). The harvest queue surfaces it; on Nick's approval, `/extract-artifacts` runs with target form `template`, and DD-100's version-bump path fires if the candidate is an evolution of an existing template. This is symmetric with the rule/skill path — the queue feeds; the consumer DD (DD-97 for rule/skill, DD-100 for template) governs absorption.

## Rules for `/synthesize-guide`

1. **Scan during absorption phase.** For each pattern finding the skill is absorbing into the guide body, perform a co-occurrence scan over the finding's body. Detect prose that reads as rule, skill, or template shape per the form-classification rubric.

2. **LLM-loose calibration.** No structured threshold for "looks like a rule." LLM judgment, calibrated like DD-97. False-positives caught at Nick's gate.

3. **Suppress agent candidates.** If detection would surface agent-shaped content, the candidate is logged inline in the synthesis report (not the queue) and DD-82 governs separately. The queue NEVER carries agent-form rows.

4. **Append to per-guide queue.** Detected candidates append to `extracts/guides/<guide-stem>.harvest-queue.md`. Create the queue file if absent (with the title heading and the explanatory note).

5. **Duplicate suppression.** Before appending, check for an existing row with the same (source_finding, target_form) tuple. Suppress the new row if a prior row exists with status `queued`, `nick-dismissed`, `extracted`, or `superseded`.

6. **Append-only across regen.** Existing rows persist with their current status; new rows always append below the existing entries (most-recent-last in the queue file's table; per-row details append in document order). Status transitions are not made by `/synthesize-guide` — only by Nick's rulings and downstream `/extract-artifacts` runs.

7. **Never auto-extract.** The skill never creates a rule, skill, or template artifact based on a queue row. Extraction requires Nick's ruling and a separate `/extract-artifacts` invocation.

8. **Mark superseded on cluster departure.** If a regen of the guide finds that a previously-absorbed pattern finding is no longer in the cluster (e.g., dimension-rebalance moved it elsewhere), the skill marks every queued or nick-approved row sourced from that finding as `superseded` (not `nick-dismissed`). Extracted rows remain `extracted`. The supersession annotation cites the regen's session; the row is not deleted.

## Rules for `/extract-artifacts` (Promotion Path)

1. **Read queue rows on explicit invocation.** `/extract-artifacts` does not automatically poll harvest queues. When invoked with a queue row as input (Nick's deliberate scoping), it runs as if the queue row's source excerpt were a regular finding's content, with the original pattern finding as `source_finding`.

2. **DD-97 fires for rule/skill targets.** The extension rubric runs against `extracts/rules/` or `extracts/skills/` per the row's target form. Outcome: `version-bump` (DD-100) for templates, or `extend existing` / `create new` / `parameterize` (DD-97) for rules/skills.

3. **Update queue row on extraction.** After successful extraction (whether new artifact, extension, or version bump), the originating queue row's status is updated to `extracted` with a pointer to the resulting artifact (or to the existing artifact that was extended/bumped).

4. **Update queue row on dismissal.** If Nick rules `dismiss as inline` on a queued row, the status is updated to `nick-dismissed`. The row is retained in the queue for audit; no artifact is created.

5. **Update queue row on merge.** If Nick rules `merge into existing [[<artifact-stem>]]`, the row's status is updated to `nick-approved` first, then to `extracted` after `/extract-artifacts` runs the merge (which is structurally an extension under DD-97). The resolution captures the merge target.

## Failure Modes and Recovery

| Failure mode | Detection | Recovery |
|---|---|---|
| LLM false-positive: prose looks rule-shaped but is actually pattern exposition | Nick reads the row and rules `dismiss as inline` | Status: `nick-dismissed`. No artifact created. Row retained as audit trail. Cost: one Nick read. |
| LLM false-negative: genuine embedded artifact missed | Not detected by `/synthesize-guide`; surfaces only on next regen if prose changes, OR via DD-77's other consumer paths | Acceptable — DD-77 explicitly accepts read-time consumer-driven resolution. DD-101 covers one consumer well, not all consumers exhaustively. |
| Source pattern finding removed from cluster on later regen; existing queue row was `nick-approved` but not yet extracted | Regen detects the source finding is gone | Row marked `superseded` (NOT `nick-dismissed`). Audit-trail signal: the candidate was approved but rendered moot by cluster change before extraction. |
| Same embedded prose detected across two pattern findings absorbed into the same guide | Detection emits two rows with different `source_finding` pointers but similar source excerpts | Both rows queue independently. Nick may rule `merge into existing` on the second after the first is extracted, or `dismiss as inline` if the prose is duplicative. The queue tolerates correlated rows. |
| Two pattern findings in different guides both contain the same embedded rule | Detection emits one row per guide queue | Both rows queue independently in their respective per-guide queue files. On extraction, DD-97's extension rubric on `/extract-artifacts` catches the second-extraction's overlap with the first's resulting artifact and proposes extension instead of duplication. The queue does not have a cross-guide deduplication mechanism — that's DD-97's job at extract time. |
| Queue file not written (skill failure mid-regen) | Manual audit | Procedural failure — `/synthesize-guide` is expected to write the queue alongside the guide draft. Recovery: re-run synthesis with verification; flag as governance audit item if recurring. |
| Agent-shaped content detected in a pattern finding | Skill suppresses queue emission; logs inline in synthesis report | Nick reads the synthesis report's inline narrative. If the agent-shaped content warrants creation, DD-82's never-auto-create path is invoked manually (separate from this DD). The harvest queue stays clean of agent rows. |
| Codifier auto-extracts from a queue row without Nick ruling | `/extract-artifacts` runs on a `queued`-status row | Procedural violation; flagged in next governance audit. DD-101's "Nick gates per-row" invariant is structural. |

| Test | Expected |

## Scope and Non-Goals

- **In scope:** `/synthesize-guide` reading pattern findings during regen. Per-guide harvest queue files. Per-row promotion to `/extract-artifacts`.
- **Out of scope:** Agent harvest. DD-82's invariant; never surfaced to the queue.
- **Out of scope:** Pattern harvest. Patterns route to guides, not to the harvest queue. A pattern finding that contains an embedded pattern is just a pattern finding (and the embedded content is part of the pattern's exposition).
- **Out of scope:** Cross-guide deduplication of harvest candidates. DD-97's extension rubric handles cross-artifact overlap at extract time. The queue is per-guide; cross-guide consolidation is downstream.
- **Out of scope:** Automated promotion. Queue rows never feed `/extract-artifacts` without explicit Nick scoping. The "feeds /extract-artifacts" wording is operational (the row IS the input shape `/extract-artifacts` accepts), not automated (the trigger IS Nick's invocation).
- **Out of scope:** Live-location lifecycle. Harvested artifacts that get extracted, deployed, and then drift at live location are governed by DD-29 — not DD-101.
- **Out of scope:** Non-`/synthesize-guide` consumers. DD-77 says other consumers (Nick reading deployed guides, future skills) also resolve co-occurrence. DD-101 codifies one specific consumer's resolution path; other consumers' paths remain implicit until each is codified separately.
- **Out of scope:** Researcher-side findings creation from queue rows. The flow described above (queue row → `/extract-artifacts` directly with the original pattern finding as `source_finding`) bypasses creating an intermediate finding for the harvested artifact. If future work shows that intermediate findings are valuable, a follow-up DD addresses that path.
