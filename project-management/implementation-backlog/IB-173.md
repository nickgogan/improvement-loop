# IB-173: Three-bucket gate tiering — design the DD-29 gate refinement

Approved for design at session 137. Today the human gate is binary: everything
crossing a stage boundary waits for Nick. The approved direction tiers changes
*inside* the gate.

## The pattern (KB-grounded)

`three-bucket-change-approval-tiering` (P2, 3 sources — Marchese ×2 + cross-lane
HOTL convergence):

1. **Auto-approve** — low-risk mechanics (data bloat, missed linkages, obvious
   fixes) applied automatically, every change logged to a changelog for after-the-fact
   audit.
2. **Needs sign-off** — skill edits, new skills, structural changes: written to a
   dated review file as a checkbox list (approve / reject / approve-and-don't-ask-again).
3. **More context required** — items the system can't classify alone, appended to the
   same review file so Nick reviews everything in one sitting.

The don't-ask-again option is the compounding piece — it converts classes of
bucket-2 items into bucket-1 over time, shrinking Nick's review load (the standing
reduce-Nick-bottleneck direction; DD-108 trajectory).

## Adjacent KB material for the design

`human-on-the-loop-hotl-autonomy-tiering-framework` (tier by operation class upfront),
`autonomy-gradient-not-binary-delegation` (P1 — blast-radius × reversibility 2x2),
`trust-calibration-progressive-autonomy-ramp` (Strong — per-task-type promotion),
`autonomy-progression-gated-by-maturity` (promotion = removing a human touchpoint
from an already-trusted loop), `critical-call-checkpoint-gate-placement-heuristic`.
Known failure modes recorded in the finding: misclassification, bucket-1 scope creep
via don't-ask-again, changelog theater.

## How to approach

Design-first: produce a spec (bucket definitions with blast-radius/reversibility
criteria mapped to engine change classes, changelog + review-file mechanics,
don't-ask-again preference memory + its periodic audit), then Nick gates the spec,
then a DD amending/refining DD-29. Session-137 precedent worth encoding: reciprocal
link completion and authority backfill were treated as bucket-1-style mechanics with
report-as-audit-trail — the spec should formalize exactly that boundary.

## Carried from IB-103 (merged 2026-07-12, gate G7)

Original prerequisites idea worth testing in the spec: relax nothing until a track record
exists — e.g., 5+ successful pipeline runs, >90% two-way-door approval rate, and a working
rollback mechanism. Maps naturally onto the trust-calibration / progressive-autonomy-ramp
findings above (promotion earned per task type, not granted globally).
