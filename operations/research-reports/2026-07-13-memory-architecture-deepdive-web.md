Research date: 2026-07-12. Four targeted deep-dives with concrete mechanics from primary sources. OKF SPEC.md and OpenClaw docs fetched directly; the rest from practitioner reports and vendor docs, 2025-2026.

## Deep-Dive 1 — OKF v0.1 Spec Mechanics

Primary source: `github.com/GoogleCloudPlatform/knowledge-catalog/okf/SPEC.md` (fetched 2026-07-12). Published by Google Cloud Data Cloud team (Sam McVeety, Amir Hormati), 2026-06-12. Formalizes Karpathy's April-2026 "LLM wiki" pattern.

### Frontmatter fields
- **Required (the entire conformance bar): `type`** — "a short string identifying the kind of concept. Consumers use this for routing, filtering, and presentation." Must be non-empty. Unknown `type` values must be tolerated (treated as generic concepts).
- **Recommended (priority order): `title`** (display name), **`description`** ("a single sentence summarizing the concept"), **`resource`** (URI uniquely identifying the underlying asset), **`tags`** (YAML list), **`timestamp`** (ISO 8601 last-change).
- **Extensions:** producers may add arbitrary keys; consumers **must preserve unknown fields** on round-trip.

### Bundle & manifest structure
- A **bundle** = a directory tree of markdown files. No prescribed organization; git repo is the recommended distribution unit (tarball or subdirectory also fine). **There is no manifest file** — the only bundle-level declaration is optional `okf_version: "0.1"` in the root `index.md` frontmatter.
- **Reserved filenames** (not concept documents):
  - `index.md` — curated directory listing for progressive disclosure. No frontmatter allowed (root index.md may carry only `okf_version`). Body = headings grouping `[Title](url) - description` bullets. May appear at any level. Consumers may synthesize one when missing.
  - `log.md` — chronological change history, newest-first, ISO `YYYY-MM-DD` date headers, prose entries with optional `**Update**`/`**Creation**` prefixes. Optional at any level.

### Granularity & identity
- One markdown file = one concept. **Concept ID = file path minus `.md`** (`tables/orders.md` → `tables/orders`). Path is the identity mechanism; no UUIDs, no registry.

### Cross-linking
- Standard markdown links only. Bundle-absolute form starting with `/` recommended (`[customers](/tables/customers.md)`) — stable under moves. Links are **untyped directed edges**; relationship semantics live in surrounding prose. **Consumers MUST tolerate broken links** — a dangling link is not malformed.

### Versioning
- Spec versions as `<major>.<minor>`; minor = backward-compatible additions, major = breaking (field renames, reserved-filename changes). Concept-level versioning is delegated entirely to git + `timestamp` + optional `log.md`. No content-hash or schema registry.

### Consumer loading model
- Enter at bundle root → read `index.md` if present (else recurse) → parse frontmatter of each `.md` → build optional link graph → progressive disclosure via per-directory index files. Consumers **MUST NOT reject** bundles for missing optional fields, unknown types, unknown keys, broken links, or missing index files. Design intent: "remain useful as bundles grow, get refactored, and are partially generated by agents."

### Adoption (as of 2026-07)
- Shipped with 3 reference implementations: a BigQuery enrichment agent, a static HTML graph visualizer, 3 sample bundles (GA4 ecommerce, Stack Overflow, Bitcoin). Google Cloud Knowledge Catalog can ingest OKF.
- **No named enterprise adopters at launch** (aiweekly.co alert, 2026-06-16). Within days, independent devs posted migration tools for Notion/Confluence/GitHub-Wikis (techfastforward.com). No native OKF readers announced from Anthropic/Microsoft/OpenAI yet. Fair critiques: standardizes structure not semantics ("a shared way to store context, not yet a shared way to make sense of it" — honra.io); Google's own reference tools don't fully match the written spec yet; governance still Google-controlled despite vendor-neutral framing.

### Verdict input: what a rich-frontmatter Obsidian vault must CHANGE vs EXPORT
A vault like the MetaSystem's is already ~95% OKF-shaped. Gap analysis:
- **Nothing structural changes in-vault.** Conformance needs exactly: (1) parseable YAML frontmatter on every non-reserved `.md`, (2) non-empty `type` field, (3) reserved-file conventions when `index.md`/`log.md` present. Existing rich frontmatter (status, dates, custom fields) is legal as extensions — consumers must preserve it.
- **Export-time transforms, not vault changes:** (a) map/alias the vault's kind-discriminator field to `type` if named differently; (b) rewrite `[[wikilinks]]` → standard markdown links (OKF consumers parse only markdown links; wikilinks would silently vanish from the graph); (c) rename any `_index.md` → `index.md` and strip its frontmatter, or just generate fresh index.md files (note: OKF's `index.md` forbids frontmatter — Dataview-driven `_index.md` files with frontmatter must NOT be renamed, they'd violate §6; keep them as ordinary concepts or exclude them); (d) add `okf_version` to root index; (e) optionally emit `log.md` from git log.
- **Conclusion: OKF is an export target, not a redesign driver.** A ~50-line script gets a conformant bundle. The one in-vault habit worth adopting from it: every file carries a `type`, and descriptions are one sentence.

## Deep-Dive 2 — Obsidian as Agent Memory (2025-26 practice)

### The dominant pattern: dual-interface, files as truth
The converged architecture is **"human reads via Obsidian UI, agent reads via filesystem"** — the vault is a plain markdown corpus that Obsidian renders for the human while agents access it through grep/Read or an MCP server. Blake Crosley (16,894-file vault): "Obsidian is not a note-taking app. It is a local-first, plaintext, graph-structured markdown corpus that becomes an AI context reservoir when you add retrieval infrastructure" (blakecrosley.com/guides/obsidian). Tony Xu's setup is the cleanest reference architecture: private markdown repo = canonical source; GBrain = read/search acceleration layer ("not the source of truth"); Hermes agent reads canonical files, searches the index, writes back to the right place (tonyxu.io/blog/my-second-brain-setup).

### Division of labor observed in working systems
| Concern | Obsidian-side | Agent-side |
|---|---|---|
| Canonical storage | vault files | same files (filesystem/git) |
| Human browsing/serendipity | graph view, backlinks, Dataview dashboards | n/a |
| Live views/rollups | **Dataview queries over frontmatter** — but these render only in the UI; agents can't execute DQL | agent runs ripgrep over the same frontmatter fields |
| Lexical retrieval | Omnisearch (BM25-ish, in-app) | ripgrep / BM25 index |
| Semantic retrieval | Smart Connections (local 384-dim block embeddings) | the same embeddings exposed via a community MCP server, or an external index (GBrain, Nooscope-style local vector MCP) |
| Traversal | `[[wikilinks]]`/backlinks graph | agents follow links as text; skills exist for explicit graph traversal (github.com/adamtylerlynch/obsidian-agent-memory-skills — "agent orients at session start, navigates architecture through graph traversal, writes discoveries back") |
| Write path | human edits | agent writes markdown directly or via MCP write tools |

### Who does it well
- **likelymalware.com "agent-brain" pattern**: persistent files auto-read at session start; Smart Connections embeddings exposed through MCP; protocol = "semantic search by default, keyword grep only as fallback... running both every time defeats the purpose" (likelymalware.com/blog/agent-brain-obsidian). Fully local, no cloud, every memory human-inspectable.
- **bitsofchris "augi" pipeline**: explicit ETL (`augi-update`) extracts structure/embeddings/tags/links from the vault into an agent-consumable form; MCP server exposes the knowledge graph; tasks dispatched to parallel tmux Claude sessions (bitsofchris.com). Key idea: the vault is the data lake, the derived index is disposable.
- **adamtylerlynch/obsidian-agent-memory-skills**: skill-based (not plugin-based) — session-start orientation note, graph traversal, write-back conventions.

### What breaks
1. **Dataview is a UI-only computation layer.** DQL queries don't exist for the agent — anything encoded only as a Dataview view is invisible to the agent unless it re-derives it via ripgrep on frontmatter. (Crosley: Dataview "does not directly help retrieval.") Systems that lean on Dataview for governance views must keep frontmatter grep-derivable — which is exactly the MetaSystem's existing "frontmatter is the source of truth, filter with ripgrep" rule.
2. **Wikilinks are Obsidian-dialect.** Agents can follow them as strings, but standard-markdown consumers (and OKF) don't parse them; graph traversal by agents requires either convention-following prompts or a resolver tool.
3. **Embedding index staleness/cost.** Smart Connections re-indexing on large vaults takes minutes and the index drifts from the files; every practitioner treats vectors as a **derived, disposable layer** rebuilt from markdown, never authoritative.
4. **Plugin/MCP sprawl.** The Obsidian-MCP ecosystem is fragmented (obsidian-mcp-server, files-mcp, Smart Connections MCP bridge, custom Nooscope-style servers); nothing is standard. Most robust setups skip Obsidian-specific MCP entirely and give the agent plain filesystem access, because the vault is just files.
5. **Concurrent writes** (agent writing while Obsidian has the file open) are mostly benign due to Obsidian's file-watching but sync plugins can conflict; practitioners route agent writes through git commits.

### Convergent answer
The vault needs no agent-specific restructuring if (a) frontmatter is consistent and grep-derivable, (b) notes are atomic with explicit links, (c) any semantic index is derived and disposable. Obsidian features are for the *human's* read path; the agent's read path is grep + Read + (optionally) one search MCP. This is precisely the "producer/consumer independence" OKF codifies.

## Deep-Dive 3 — Grep→RAG Thresholds, Concrete

### The headline empirical result (2026)
The "Is Grep All You Need?" study wired a literal grep tool and a vector-retrieval tool into the same agents and ran a 116-question LongMemEval-S subset: **with inline delivery, grep beat vector retrieval across every harness-model pair tested** — e.g., Chronos + Gemini 3.1 Flash-Lite: inline grep 86.2% vs inline vector 62.9% (note.com/ainest summary; dev.to/pueding/is-grep-all-you-need). Caveat from the same paper: switch to programmatic delivery (results written to file for the agent to read) and rankings can flip. On codebases: agentic grep/find/cat search ~68% vs vector search ~60% on Django QA; parity (~70%) on TS/Go — vector's real cost was tokens, not accuracy (zansara.dev/posts/2026-03-15-vector-dbs-vs-grep). GrepRAG (arxiv 2601.23254): ripgrep gives the highest identifier-EM/F1 — character-level matching beats vectors for locating definitions.

### Query shapes that NEVER need embeddings
(tensorowl.dev/writing/keyword-retrieval-in-the-agent-era; r/Rag; r/ClaudeCode consensus)
- Exact/rare tokens: identifiers, error codes, DD/IB numbers, GUIDs, filenames, dates
- Frontmatter-filterable queries (status/type/tag filters) — metadata grep, no ranking needed
- Term-dense closed corpora where the answer text literally contains the query words
- Anything the agent can iterate on — an agent that can re-grep with a refined term erases most of vector search's recall advantage ("do queries benefit from iteration?" is zansara's key discriminator)

### Query shapes that DO need embeddings (or hybrid)
- Conceptual/paraphrased questions where query vocabulary ≠ document vocabulary (synonym gap)
- Cross-document synthesis over large corpora ("what do we know about X" across 150 findings phrased differently)
- One-shot retrieval (no iteration budget) — RAG pipelines, not agent loops
- Evidence "buried in paraphrasing or structure": summaries, transcripts, scientific prose (note.com analysis: "the judgment axis is not size" — even small corpora need vectors if the target is abstract)

### The threshold, as practitioners state it
- **No hard corpus-size number exists**; the strongest stated heuristic: "don't reach for embedding-index-and-vector-store if the corpus is under a few hundred MB, queries are literal-token-heavy, and the agent iterates" (dev.to/pueding). For markdown KBs in the hundreds-of-files range (the engine's ~150 findings), every source puts this **firmly in grep territory**; BM25 (SQLite FTS5) is the first upgrade when grep result sets get too large to rank by eye, not embeddings.
- Decision axis is **query shape > corpus size**: lexical-answerable → grep/BM25 baseline first, always measured before adding vectors (universal recommendation across all 10 sources).

### Hybrid mechanics as deployed
- **OpenClaw**: per-agent SQLite file (`~/.openclaw/memory/<agentId>.sqlite`) with **FTS5 + vector index over the markdown files**; retrieval = weighted fusion `finalScore = 0.7*semantic + 0.3*keyword`; below-threshold results discarded; "search first, then inject" (gaodalie.substack.com). The markdown stays canonical; SQLite is derived.
- **claude-mem**: SQLite FTS5 + Chroma vectors, 3-layer progressive retrieval (index ~50-100 tokens/result → summaries → full details by ID). Cost critique: 5 resident hook processes, ~80-150MB RAM, per-session API summarization call — the community counter-example showed a 47ms local compaction function + stdio MCP approximating most value (dev.to/zzallirog).
- **Hybrid routing policy** (bemiagent.com): exact/entity/time-bound → lexical; fuzzy/conceptual/paraphrase → vector; high-stakes → run both and cross-check. Fusion by RRF or LLM rerank (r/ClaudeCode).

### Index maintenance cost
Consensus: any index (FTS5, sqlite-vec, LanceDB, Chroma) is a **derived, disposable, gitignored artifact rebuilt from markdown** — never a second source of truth. Costs to budget: initial embed pass (minutes for thousands of files), incremental re-embed on edit (file-watcher or session-start delta), model-version invalidation (re-embed everything when the embedding model changes), and debuggability loss (grep failures are inspectable; vector misses are opaque). Zansara's closing rule: "the only way to know is a RAG evaluation pipeline" — if you can't afford to measure it, you can't afford to run it.

## Deep-Dive 4 — Lifecycle Mechanics in the Seed Systems

### OpenClaw Dreaming (docs.openclaw.ai/concepts/dreaming; fossies.org/linux/openclaw/docs/cli/memory.md; dev.to/czmilo guide)
- **Pipeline**: one cron-managed sweep (`dreaming.frequency`, default `0 3 * * *` — 3AM daily) executes phases in order **light → REM → deep**. All config under `plugins.entries.memory-core.config.dreaming`. `enabled: false` by default; `/dreaming on|off|status` from chat.
- **Light** (ingest/stage): reads daily files `lookbackDays: 2`, `limit: 100` candidates; indexes, dedupes, groups adjacent note lines into chunks.
- **REM** (reflect): `lookbackDays: 7`, `limit: 10`, `minPatternStrength: 0.75` — extracts cross-day themes and weighted associations.
- **Deep** (the ONLY phase that writes MEMORY.md): scores every candidate with six weighted signals — **relevance 0.30, frequency 0.24, query diversity 0.15, recency 0.15, consolidation 0.10, concept richness 0.06** — then applies three gates that must ALL pass: **`minScore: 0.8`, `minRecallCount: 3`, `minUniqueQueries: 3`**. Promotion budget `limit: 10` per sweep; a max-token cap per promoted snippet keeps entries small; ranking provenance stays visible.
- **Decay/retirement**: `recencyHalfLifeDays: 14` (freshness signal halves every 14 days) and `maxAgeDays: 30` (candidates older than 30 days are dropped from consideration entirely). Deep sleep also "applies aging controls... so stale information naturally fades" in MEMORY.md and is **replay-safe** (re-running reconciles instead of duplicating). Stale long-term entries are removed during distillation sweeps.
- **UP a tier**: short-term recall signal → passes 3 gates → MEMORY.md. **OUT**: age past maxAgeDays (candidates), staleness removal during sweeps (long-term), bootstrap-budget truncation as pressure signal.
- **Failure reports**: github.com/openclaw/openclaw/issues/67580 — promotion wrote raw undistilled candidate data into MEMORY.md, which flowed back into memory sources and was re-ingested (feedback loop). Docs themselves name the two failure poles the gates exist to prevent: too-aggressive (bloat/noise recall) vs too-conservative (patterns lost forever). Every phase writes human-reviewable summaries to DREAMS.md — the audit surface.

### Hermes Agent (hermes-agent.nousresearch.com/docs; glukhov.org; mem0.ai analyses)
- **Store**: exactly two files — MEMORY.md (**2,200-char hard cap**, ~800 tokens, agent's world-notes) and USER.md (**1,375 chars**, ~500 tokens, user profile) — entries separated by `§` (U+00A7). Character caps chosen over tokens so budgets don't drift across models.
- **Update rules**: a three-action `memory` tool — `add`, `replace`, `remove` (no read action; the content is already in the prompt). `target='memory'|'user'` selects file. Writes hit disk immediately.
- **Read path**: **frozen snapshot** — files injected into the system prompt once at session start and never refreshed mid-session, deliberately preserving the prefix cache ("Hermes trades freshness for speed"); new entries appear next session.
- **Promotion/decay**: there is no automated tiering — **the hard cap IS the lifecycle mechanism**. At 2,200 chars, adding requires removing; curation is forced at write time, by the agent, under instruction. Optional single external provider (Honcho, Mem0, Hindsight, etc. — one at a time) adds retrieval-based long-term memory beside, not replacing, the frozen files; session history is separately searchable via `session_search` (SQLite FTS5).
- **Failure/limits reported**: the agent cannot recall something it wrote earlier in the same session (documented, deliberate); the ~1,300-token ceiling means anything beyond preferences/environment facts must live in the external provider or not at all — mem0.ai's analysis frames this as the trade Hermes accepts to avoid OpenClaw-style noise accumulation.

### Letta / MemGPT (letta.com/blog/context-repositories, /sleep-time-compute)
- **Tiers**: recall memory (auto-written episodic conversation log, write-protected), core memory (editable blocks with explicit `append`/`replace`; size-limited — hitting the limit triggers eviction prompts pushing content to archival), archival memory (unbounded searchable store).
- **UP a tier**: agent-decided tool calls promote facts into core memory; sleep-time reflection agents review recent history in the background and persist important information into the git-backed context repo **with informative commit messages**, working in **git worktrees** and merging back via normal conflict resolution.
- **Maintenance**: a defragmentation subagent periodically backs up the memory filesystem, then splits large files, merges duplicates, and restructures into **15-25 focused files**; progressive disclosure via a `system/` directory (only files there are pinned to the system prompt) plus frontmatter descriptions on everything else.
- **OUT**: core-memory eviction to archival on limit pressure; defrag merges/deletes duplicates; nothing auto-expires — git history is the permanent episodic record.
- **Failure/limits reported**: append-without-reconcile produces contradictory core memories (the canonical "James is the boyfriend/ex-boyfriend" example — replace semantics must be prompted, they don't happen by default); the architecture's cost is machinery — init subagents, reflection subagents, defrag subagents — justified for a platform, heavy for a single operator.

### Mem0 (dev.to/sudarshangouda intelligent-forgetting analysis)
- **UP**: salience-scored extraction at write time — the pipeline extracts and consolidates only "salient" conversation facts into structured (optionally graph) memory; non-salient content is never stored.
- **OUT**: managed platform — per-memory `expiration_date` parameter on `add()`; **Mem0 OSS has no built-in TTL/expiration** — self-hosters must add importance columns + scheduled SQL cleanup themselves. Comparison points in the same analysis: LangGraph store-level TTL with `refresh_on_read` (reading refreshes expiry — a spacing effect); AWS AgentCore per-resource `eventExpiryDuration` (tier by routing content to different resources, e.g., preferences 365d vs casual 7d).
- **Failure reported**: the OSS no-TTL default is the named graveyard generator — store-everything-forever unless the operator builds decay.

### Gbrain (100user.com; youtube -fSjdYzrFvA; tonyxu.io)
- **Structure**: one markdown file per entity (person/company/project) in a git repo; **"compiled truth + timeline"** layout — top of file = current best judgment (mutable, replaced in place), bottom = append-only dated evidence timeline (never modified). Garry Tan's own corpus: 10,000+ markdown files, 3,000+ contact profiles, 13 years of calendar data.
- **UP**: nightly **"dream cycle"** scans the day's conversations/meetings/emails and appends new entities/facts to the matching pages; the compiled-truth header is re-synthesized from the timeline when it drifts. Ingestors (Gmail, Calendar, Circleback transcripts, social) feed the timeline automatically.
- **Read**: markdown synced to a local in-process PGlite database; hybrid keyword + vector + graph search exposed as 30+ MCP tools; a **zero-LLM knowledge graph** (deterministic entity linking) maps connections; answers are cited back to pages. Operating habit (per the Hermes+Gbrain integration): "search the brain first, write decisions back, keep world-facts out of chat memory."
- **OUT**: no documented decay — retirement is editorial (the compiled-truth section supersedes; the timeline is the archive). Failure surface flagged by users: index-vs-file drift (PGlite is derived; markdown is truth), and the same no-expiry graveyard risk as any append-forever timeline.

### A-MEM (NeurIPS 2025; deep-research synthesis)
- **UP**: every accepted memory becomes a structured Zettelkasten note (contextual description + keywords + tags), and the system runs link generation against historical notes — meaningful similarity creates edges. Writing is deliberately expensive: a memory only enters the network if judged worth structuring.
- **Evolution instead of tiers**: new notes can **trigger updates to the contextual representations and attributes of existing linked notes** — the network refines itself as understanding deepens; there's no episodic staging layer, semantic structuring happens at write time.
- **OUT**: no explicit decay published; retirement is implicit via link/relevance dynamics. Failure/limits: research prototype — each write costs LLM calls for description/tagging/linking, and no production failure reports exist yet; the write-cost profile is the inverse of OpenClaw's (curation up front vs curation on a schedule).

### Cross-system lifecycle summary
| System | Promotion trigger | Decay/retirement | Documented failure |
|---|---|---|---|
| OpenClaw | 3 gates: score≥0.8, recalls≥3, unique queries≥3, in nightly sweep | halfLife 14d, maxAge 30d, stale-entry removal, replay-safe | raw-candidate promotion feedback loop (#67580) |
| Hermes | agent judgment at write time, forced by 2,200-char cap | displacement (cap) only | no same-session recall (by design); tiny ceiling |
| Letta | agent tool calls + sleep-time reflection subagents (git commits) | core→archival eviction on limit; defrag merge/split | contradictory cores without replace discipline; machinery cost |
| Mem0 | salience extraction at write | platform: expiration_date; OSS: none (DIY SQL) | OSS graveyard-by-default |
| Gbrain | nightly dream cycle appends to entity timelines; compiled-truth resynthesis | editorial supersession only | index/file drift; no expiry |
| A-MEM | LLM structuring + linking at write | implicit via network evolution | write-cost; prototype-only evidence |

Convergence: **promotion is evidence-gated and scheduled (or cap-forced); decay is the least-solved part everywhere** — only OpenClaw ships numeric decay defaults; two of six systems have no deletion story at all and rely on supersession/editorial pruning, which is also what a git-backed vault gets for free.
