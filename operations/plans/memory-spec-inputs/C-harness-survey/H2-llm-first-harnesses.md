# LLM-First Harnesses — Claude Code, Codex, opencode

Dossier for the harness-landscape survey feeding the E1 memory-spec and E4 harness epic (Track C). Scope: the **harness layer** — loop ownership, extension surfaces, enforcement, scheduling, build-on-top contract, and sentiment — for the three canonical LLM-first coding harnesses. Memory mechanics are deliberately excluded; they're covered in the companion Track B dossiers (`B-framework-survey/claude-code.md`, `B-framework-survey/codex.md`) and cross-referenced only where the memory *attach point* is itself a harness mechanism (a hook, a config toggle). Written 2026-07-16.

**Working definition tested throughout:** "LLM-first" means the model owns the control loop — it decides when to invoke skills, spawn subagents, call tools — while skills/hooks/rules ride along as extensions and guardrails. The class-level section at the end evaluates this hypothesis directly against the evidence gathered per harness, and finds it holds for control flow but not for enforcement.

---

## Claude Code

### 1. Loop ownership & turn structure

The agent loop is exactly what the Agent SDK docs describe: the harness passes conversation + context (skills, rules, CLAUDE.md) + tool spec to the model; the model either replies directly or requests tool calls; the harness executes them, appends results, and re-invokes the model; this repeats **until the model emits a response with no further tool calls** (`code.claude.com/docs/en/agent-sdk/agent-loop`). There is no published hard cap on tool calls per turn — depth is governed by **effort settings** (`/effort low|high|xhigh|max`; default is `high` for Opus 4.6 on Max/Team plans as of June 2026, per Datacamp's 2026 slash-commands guide) rather than a fixed step budget. Parallel tool calls are grouped into a **batch**; a `PostToolBatch` hook fires after the batch resolves and before the next model call — a deterministic pause point between rounds of parallel work, not just a single-call gate.

**Plan Mode** is the one harness-level workflow state: entered via `Shift+Tab` or `/plan`, it doesn't just prompt against writes — write-capable tools (`Edit`, `Write`, destructive `Bash`) are gated off outright, so the loop can only read/search/reason and must converge on a plan artifact rather than a code change. Exiting Plan Mode is itself a permission-mode transition the user must approve (`code.claude.com/docs/en/permission-modes`).

**Extended thinking** (`platform.claude.com/docs/en/build-with-claude/extended-thinking`) can run alongside tool use but has strict harness-contract rules: thinking blocks must round-trip back to the API unmodified across a multi-tool turn, and thinking cannot be toggled mid-turn — the harness must decide once, upfront, whether the final assistant turn starts with a thinking block.

**Autonomous chain depth is mode-dependent, not fixed**: in `acceptEdits`, file edits and common filesystem commands (`mkdir`, `touch`, `rm`, `mv`, `cp`, `sed`) execute without prompting, so chains can run long and uninterrupted; in `default` or `plan`, most write/side-effect calls interrupt the loop for a permission prompt. This makes "how deep can it go autonomously" a configuration question the operator answers, not a property of the harness itself.

### 2. Extension surfaces

**Skills** (`.claude/skills/*/SKILL.md`) use progressive disclosure — not loaded upfront, triggered by description match or `/name` (`platform.claude.com/docs/en/agents-and-tools/agent-skills/overview`).

**Subagents are three distinct tiers, not one feature.** (a) In-session subagents via the `Task`/`Agent` tool — fresh context, only the summary returns to the parent. Built-ins: **Explore** (read-only; as of **v2.1.198** its model *inherits from the main conversation, capped at Opus* — before that it always ran on Haiku; supports `quick`/`medium`/`very thorough` depth), **Plan** (research feed for Plan Mode; inherits model), **general-purpose** (all tools; inherits model), plus fixed-model helpers (`statusline-setup`→Sonnet, `claude-code-guide`→Haiku). Explore/Plan skip CLAUDE.md and git status for speed; every other subagent loads both. **Custom subagents can pin an explicit model** (e.g., `model: haiku` in frontmatter) independent of the parent's model — confirmed directly (`code.claude.com/docs/en/sub-agents`), resolving the ambiguity Perplexity's own synthesis had flagged as uncertain. (b) **Background agents** (`/en/agent-view`) — many independent parallel sessions monitored from one place. (c) **Agent teams** (`/en/agent-teams`) — sessions that *communicate with each other*, explicitly distinct from subagents ("subagents work within a single session"). Disable surfaces: `permissions.deny` on the `Agent` tool, `CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1` (v2.1.198+), or (headless-specific) `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1`.

**MCP**: stdio/SSE/Streamable-HTTP; `claude mcp add --transport sse|http <name> <url>`. Claude Code can also *act as* an MCP server (`claude mcp serve`), making the integration bidirectional (`code.claude.com/docs/en/mcp`).

**Output styles** (introduced August 2025, Shipyard blog): a full system-prompt swap, distinct from and one tier below CLAUDE.md. Created via `/output-style:new`, stored in `~/.claude/output-styles/`, switched via `/output-style <name>`. Pure persona layer — doesn't touch tool selection, permissions, or hooks.

**Slash commands**: built-ins spanning context/planning/focus/navigation/cost (`/compact`, `/plan`, `/goal`, `/diff`, `/cost`, `/sandbox`, `/effort`…) plus custom commands as Markdown in `.claude/commands/` (project) or `~/.claude/commands/` (personal), shareable via version control.

### 3. Enforcement points

**Hooks** are the harness's deterministic-code layer, and the surface is large and mature: **~26 canonical lifecycle events** across eight categories (session, user-input, tool-execution, agent/task, stop/completion, context/config, worktree, compaction, MCP-elicitation, display/notification) per `code.claude.com/docs/en/hooks`. The blocking/observational split matters more than the raw count:

| Deterministically blocking | Observational only |
|---|---|
| `PreToolUse`, `PermissionRequest`, `UserPromptSubmit`, `UserPromptExpansion`, `Stop`, `SubagentStop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`, `PreCompact`, `PostToolBatch`, `WorktreeCreate`, `Elicitation`, `ElicitationResult`, `ConfigChange` (except managed policy) | `PostToolUse`, `PostToolUseFailure`, `SessionStart`/`SessionEnd`, `Notification`, `CwdChanged`, `FileChanged`, `InstructionsLoaded`, `PostCompact`, `MessageDisplay`, `SubagentStart`, `PermissionDenied`, `StopFailure` |

The house rule practitioners converge on: *if you need to stop something, use `PreToolUse`; if you need to react to something, use `PostToolUse`* — the latter cannot undo a side effect, only shape the next turn.

**Permission modes** (`default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`) are consistent across CLI/IDE/web and map to distinct prompt behaviors: prompted, auto-approved-for-a-subset, denied-outright, routed-to-a-classifier, or allowed-immediately. `settings.json` permission rules (allow/deny by tool+pattern) layer under modes; **managed/org-level settings cannot be overridden locally**.

**Sandboxing** is OS-level (Seatbelt on macOS, built-in; Bubblewrap+socat on Linux/WSL2, opt-in install), toggled via `/sandbox` and **off by default** until first invoked. Default policy: deny writes outside the working directory, restrict outbound network to localhost. Two sub-modes (auto-allow vs. regular-permissions-as-safety-net) and an escape hatch (`dangerouslyDisableSandbox`) that managed deployments can disable entirely. **Documented gap** (claudecodecamp.com, 2026): `sandbox.denyRead` does **not** stop the `Read` tool — only a `permissions.deny Read(...)` rule does; the sandbox is write-focused, and secrets protection requires configuring both layers together.

**Rules files** (`.claude/rules/`) are **advisory, not enforced** — this is explicit in first-party framing and independently corroborated (José Parreño's Substack, 2026): rules shape model behavior but "do not themselves block tool calls or enforce permissions"; a scoped rule the agent never reads may never load at all. The operative three-tier model that emerges: **advisory** (rules, CLAUDE.md, output styles) → **deterministic guardrail** (hooks, permission rules, sandboxing) → **model reasoning** (extended thinking, effort, tool selection).

### 4. Scheduling & headless operation

`-p`/`--print` is the non-interactive primitive; reads stdin (10MB cap as of **v2.1.128**), supports `text`/`json`/`stream-json` output. `--bare` mode skips auto-discovery of hooks/skills/plugins/MCP/auto-memory/CLAUDE.md for cross-machine determinism in CI — "will become the default for `-p` in a future release" per current docs. Background Bash tasks get a 5-second exit grace; background **subagents/workflows** get a full wait, capped at 10 minutes by default as of **v2.1.182** (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, 0 = unlimited). `--output-format json` carries `total_cost_usd` for scripted cost tracking; `stream-json` tags subagent messages via `parent_tool_use_id` (full subagent transcripts via `--forward-subagent-text`, v2.1.211+).

**There is no native cron/scheduled-trigger primitive inside Claude Code itself.** The documented and practitioner-confirmed pattern is external wrapping — cron jobs, systemd timers, webhook handlers, queue workers around `claude -p` ("the `--print` flag is the door," per a 2026 headless-automation tutorial). First-party CI integration guides exist and are real (`/en/github-actions`, `/en/gitlab-ci-cd`). The practitioner rule for going unattended is unambiguous: hooks are "non-negotiable" — interactive prompts must be replaced with deterministic pre-approved decisions *before* removing the human, not after.

### 5. Memory attach points (mechanics only — see companion dossier for quality/architecture)

The attach points **are** hooks: `SessionStart` is the harness's own injection point for CLAUDE.md/rules/auto-memory before turn one, and a builder gets the same hook to inject `additionalContext`. `PreCompact`/`PostCompact` are the deterministic boundary a custom memory layer can observe or veto — this is the one place Claude Code gives a memory-system builder a literal lifecycle intercept, not just a config toggle (contrast Codex, §5 below). Per-subagent `memory:` scoping (companion dossier) rides on the subagent-definition layer, orthogonal to the Task-tool's default no-persistent-memory subagents.

### 6. Build-on-top contract

The **Agent SDK** is explicitly "the same tools, agent loop, and context management that power Claude Code" (`code.claude.com/docs/en/agent-sdk/overview`) — the harness, packaged as a library (Python 3.10+, TypeScript with a bundled native binary). Three concentric rings define how much a builder owns:

| | Client SDK | **Agent SDK** | Managed Agents |
|---|---|---|---|
| Tool loop | You write it | Harness runs it, in your process | Anthropic runs it |
| Infra | Yours | Yours | Anthropic's (hosted sandbox per session) |
| Session state | You design it | JSONL on your filesystem | Anthropic-hosted event log |
| Best for | Full control | Local/self-hosted agents on your infra | Production without operating sandbox/session infra |

What a builder gets for free with the Agent SDK: the full built-in toolset, the hooks system (`PreToolUse`/`PostToolUse`/`Stop`/`SessionStart`/`SessionEnd`/`UserPromptSubmit`…), subagents (`Agent` tool + `AgentDefinition`), MCP, permission gating, session resume/fork, and filesystem-based config loading (skills/commands/CLAUDE.md/plugins), selectively via `setting_sources`. What a builder must still supply: orchestration **across** multiple independent agent processes (the SDK gives you one agent's loop plus its subagents, not a supervisor of peers), persistent state beyond a session, custom UI, and deployment infra (unless trading control for Managed Agents). Anthropic's own "harness for every task" framing (`claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code`) goes one step further: Claude Code can now **author its own dynamic sub-harnesses at runtime** via JS orchestration to fight "agentic laziness," "self-preferential bias," and "goal drift" — a capability a from-scratch build-on-top system inherits only if it deliberately replicates it. There's also a hard branding constraint: a product built on the SDK may not call itself "Claude Code" or mimic its UI.

### 7. Practitioner sentiment (dated)

The 2026 blog consensus (smartscope.blog, ofox.ai, boringbot.substack.com, hidekazu-konishi.com) converges on one mental model: **"Skill teaches the how, Hook enforces the rule, Subagent isolates the work"** — and the most common practitioner mistake is using the wrong layer (a behavioral constraint that should be a hook gets written into a system prompt instead). A sharper, more specific claim from the same wave: **"setting sensitive files to deny makes them invisible to Claude, which is more secure than blocking with hooks"** — a denied/invisible file never enters the model's option set at all, versus a hook reactively blocking an attempt already formed. A concrete mechanical gotcha several sources flag: **subagents cannot present interactive permission prompts** — an `ask` rule inside a subagent's context is auto-denied, not deferred to the user.

On unattended operation specifically: the sandbox `denyRead`-vs-`Read`-tool gap (§3) is a named, dated 2026 footgun. Microsoft's security blog (**2026-06-05**) documents a Claude Code GitHub Action security issue Anthropic mitigated in **Claude Code 2.1 on 2026-05-05** — a real, vendor-acknowledged incident in the CI/headless surface. On economics: Anthropic announced (**2026-05-14**) that Agent SDK / `claude -p` usage would exit the Pro/Max/Team/Enterprise subscription pools starting **2026-06-15**, moving to a separately-metered full-API-rate pool — then **paused** that change before it took effect, per digitalapplied.com. As of this survey (2026-07-16), the headless/unattended surface is billed under the same pool as interactive use, but that is an actively renegotiated, not settled, fact. One practitioner framing worth carrying forward: **"unattended, the only record is whatever you captured — if you did not capture it, it did not happen as far as incident review is concerned."**

## OpenAI Codex

### 1. Loop ownership & turn structure

Same shape as the class generally: model decides, harness executes, repeats until no further tool calls. Codex has no dedicated "Plan Mode" *tool* the way Claude Code and opencode do; the equivalent effect is composed from two orthogonal axes instead (§3): **`read-only` sandbox** (blocks edits/exec/network outright) plus **`untrusted` approval** (auto-runs known-safe reads, asks on anything state-mutating). Three **named built-in subagents are load-bearing parts of the loop itself**, not an optional extension: **default** (general work), **worker** (execution-heavy implementation/fixes), **explorer** (read-heavy exploration) — these fan out in parallel and the parent consumes the consolidated result. OpenAI's own framing for why: protection against "context pollution and context rot in the parent thread" — the identical rationale Anthropic gives for subagent context isolation, independently converged on by both vendors.

### 2. Extension surfaces

**Skills**: `SKILL.md`, progressive disclosure, the `openai/skills` repo plus a `skill-creator` system skill for agent-assisted authoring — structurally the same open Agent Skills standard Claude Code implements (also used by Cursor; per the companion memory dossier).

**Subagents**: default/worker/explorer as above; a custom agent config can carry its **own `mcp_servers` block**, so one subagent holds web access via MCP while siblings stay code-only — real per-agent configuration divergence, though explicit "pin a cheaper model per subagent" support is less directly documented than Claude Code's `model: haiku` frontmatter field.

**MCP**: a 2026 release added an MCP submenu in the composer and `/mcp install` shortcuts **explicitly matching the syntax of Claude Code and Cursor** — a rare case of one vendor documenting convergence with competitors' UX. A `supports_parallel_tool_calls` flag lets declaring MCP servers run tools in parallel.

**Output-style equivalent**: not a first-class, dedicated feature. Persona/behavior customization runs through AGENTS.md prose plus per-subagent `prompt:` overrides on the three built-ins — no single command swaps the whole system prompt the way Claude Code's `/output-style` does.

**Hooks (beta, newly shipped)**: user-defined shell scripts in the agentic loop, reading JSON on stdin and answering via exit codes/stdout/stderr — mechanically similar to Claude Code's model but a visibly smaller and younger surface: `UserPromptSubmit` maps to CLI **v0.116.0**; `PreToolUse`/`PostToolUse` map to **v0.117.0**; plus `SessionStart`, `SubagentStart`/`SubagentStop`, `PermissionRequest`, `PreCompact`/`PostCompact`, `Stop` — roughly **10 events** against Claude Code's ~26. `PreToolUse` intercepts Bash, `apply_patch` file edits, and MCP tool calls; a block uses `permissionDecision: "deny"` or exit code 2. `PostToolUse` cannot undo a side effect but can replace what the agent sees with stderr feedback. Two first-party-adjacent sources fetched in this pass disagree on whether `UserPromptSubmit` is blocking or purely observational — a small but telling sign the system is still stabilizing (GitHub issue `openai/codex#14882`, a feature *request* for `PreToolUse`/`PostToolUse` hooks, is itself evidence of how recently this shipped).

### 3. Enforcement points

Two **orthogonal, composable axes** — cleaner in practice than the count of named modes suggests:

| Sandbox (what's technically possible) | Approval (when permission is asked) |
|---|---|
| `read-only` — no edits, exec, or network | `on-request` (default) — asks when an action exceeds sandbox bounds |
| `workspace-write` (default) — r/w within workspace; network blocked unless `network_access=true` | `never` (`--ask-for-approval never`) — fully autonomous within sandbox bounds |
| `danger-full-access` / `--yolo` — "[Elevated Risk] No sandbox; no approvals" (explicit doc self-warning) | `untrusted` — auto-runs known-safe reads, asks on state mutation |

Sandboxing is **kernel-level, not application-level**: Seatbelt (`sandbox-exec`) on macOS, Landlock+seccomp on Linux — "the kernel rejects disallowed syscalls before Codex even sees them" (multiple 2026 sources, e.g. codex.danielvaughan.com). Debuggable directly: `codex debug seatbelt|landlock [--full-auto] [COMMAND]`.

**AGENTS.md enforcement status is the single sharpest, best-evidenced finding in this entire survey.** It is documented as advisory, and field evidence shows the failure mode is worse than the docs imply. GitHub issue `openai/codex#25884` (**2026-06-02**, already surfaced in the companion memory dossier but directly harness-relevant): the filer explicitly ruled out discovery, truncation, and rule precedence as causes — the model could correctly *summarize* the rule early in a session — and isolated the failure to **application drift across turns**: *"AGENTS.md behaves more like a soft hint than a durable operating constraint."* This is direct, dated, first-hand evidence that "the agent read and understood the rule" does not imply "the agent keeps applying the rule" — a distinct and more dangerous failure mode than the truncation/precedence bugs that are at least legible.

### 4. Scheduling & headless operation

`codex exec` is the direct analog to `claude -p --bare`: one task, non-interactive, progress to stderr, final output to stdout — the CI/cron primitive.

**Codex Cloud "Automations" is the standout, class-differentiating capability.** It is a first-class, product-level, cloud-hosted persistent background worker: an automation = a **trigger** (time-based cron, webhook, or app event) + a **thread template** (starting prompt/context) + an **output action** (post to Slack, update Notion, send email) — and it runs "even when your Mac is closed" (`developers.openai.com/codex/app/automations`). This is a qualitatively different posture from Claude Code and opencode, both of which require the *operator* to supply an external OS-level scheduler around a headless CLI call — Codex natively owns the trigger. Separately, **Cloud tasks** run async/fire-and-forget, queue independently of the local machine, execute in parallel, and can open PRs on completion.

Community-proposed (**not shipped**, treat as aspirational): in-session `CronCreate`/`CronList`/`CronDelete` plus `ScheduleWakeup` tools — a self-wakeup/loop primitive letting the *agent itself* schedule its own future turns, tracked in `openai/codex` issues `#25466` and `#22310`. This is a distinct, more granular ask than the shipped Automations product and signals live practitioner demand for finer-grained self-scheduling.

### 5. Memory attach points (mechanics only)

The companion dossier's Memories pipeline (extract/consolidate, 6-hour idle gate) is a **background-batch process the harness runs**, not something a builder hooks into at a lifecycle event. The attach surface a builder actually gets is coarse: independent `memories.generate_memories` / `memories.use_memories` toggles and a `memories.disable_on_external_context` flag — config knobs, not intercepts. This is a structural difference from Claude Code: Claude Code gives a memory-system builder a literal hook (`SessionStart`, `PreCompact`/`PostCompact`); Codex gives a config surface with no comparable lifecycle event into the memory pipeline itself.

### 6. Build-on-top contract

`codex exec` is the headless primitive any wrapper builds on. The Automations/Cloud-tasks split mirrors Claude Code's Agent-SDK-vs-Managed-Agents choice: run it yourself (own the scheduling, unless adopting Automations) or let OpenAI host the trigger→thread→action pipeline (more managed, less yours). **AGENTS.md is a genuinely open, cross-vendor standard** (Agentic AI Foundation / Linux Foundation, per the companion dossier) — a system built on Codex inherits a portable semantic-instruction layer shared in spirit with Claude Code's CLAUDE.md and opencode's own AGENTS.md. What a builder does *not* inherit: the depth of deterministic scaffolding Claude Code's mature hook/subagent/permission surface provides — Codex's equivalents are newer and thinner, so a builder compensates with more of its own verification rather than leaning on a rich `PostToolBatch`-equivalent gate.

### 7. Practitioner sentiment (dated)

Session-length shapes the verdict more than raw capability does. morphllm.com (**July 2026**) scores the harness matchup 3–2 in Codex's favor on "steadiness, delegation, and more use for the same tokens" for **short/many** tasks, while conceding Claude Code wins "when set up properly with its harness" on **long single sessions** — a genuinely balanced, harness-specific split by workload shape, not a blanket verdict either way. Composio's "100+ Hours With Both" (**2026-06-04**, companion dossier): Codex handles large tool outputs via "head/tail truncated, middle completely dropped" versus Claude Code's practice of externalizing to files — directly costs Codex a 26-hour cross-session bug-fix recall the author documents losing.

Three dated GitHub issues in a five-week window (**May–June 2026**) point at instability specifically in the persistence/compaction substrate, independent of the sandbox/approval layer which reads as comparatively more settled: `#25884` (**2026-06-02**, AGENTS.md drift, above), `#29426` (**2026-06-22**, Desktop auto-compacts a resumed session under budget, contradicting the documented trigger), `#24089` (**2026-05-22**, post-upgrade token-accounting corruption breaks remote compaction outright). Reddit's r/codex (via a Developers Digest aggregator roundup, imprecise date within 2026): the dominant complaint is **mid-stream usage-limit cuts** — a rate-limiting issue that directly competes with both the Memories eligibility gate *and* the newer Automations/Cloud-task scheduling surface for the same rate-limit budget. A cross-cutting 2026 security note (TheHackerNews, VentureBeat, and others): a "Friendly Fire" exploit hides malicious instructions inside AGENTS.md/CLAUDE.md-style files that agents "treat with extra trust" — surfaced in Codex coverage but structurally a risk for every harness whose instruction file is auto-trusted and auto-injected.

## opencode

opencode's mechanics below draw primarily on direct source-level analysis already on file (`watched-libraries/analysis/opencode-analysis.md`, dev HEAD `34e5809`, 2026-07-11) — cited inline as "internal analysis" — supplemented with 2026 field evidence (headless/CI confirmation, MCP usage, and practitioner sentiment) gathered for this dossier.

### 1. Loop ownership & turn structure

`runLoop` (`packages/opencode/src/session/prompt.ts:1081`, internal analysis) is a `while(true)`: reload post-compaction messages → exit-check (last assistant finished non-tool-calls, no pending calls, postdates last user message) → pop in-history tasks (`subtask`/`compaction`) → overflow check (queue auto-compaction if tokens ≥ usable budget) → assemble context → call model → process the event stream → repeat. On the final step of an `agent.steps` budget, `MAX_STEPS_PROMPT` is injected **as an assistant message** — visible content the model reasons over, not a silent truncation.

opencode's most structurally distinctive design choice: **mode = agent = permission ruleset.** Plan vs. build isn't a separate code path, it's a named agent whose ruleset denies `edit:*` except plan-file globs and denies `task.general`. `plan_enter`/`plan_exit` are themselves **callable tools** whose effect is asking the user to switch agents — mechanically, entering plan mode is a tool call with a human-consent side effect, not a hardcoded flag. Plan mode runs a five-phase built-in prompt (`plan-mode.txt`): Understand (≤3 parallel Explore subagents) → Design → Review (`question` tool) → Write plan file (`.opencode/plans/*.md` only) → `plan_exit` (user gate), followed by a `build-switch` system-reminder on return. A **doom-loop breaker**: 3 consecutive identical tool calls (same name + JSON-identical input) escalate to `permission.ask("doom_loop")` rather than erroring — pathological loops become a human gate, not a crash.

### 2. Extension surfaces

**Skills**: `.opencode/skills/*/SKILL.md`, names+descriptions always in system context, bodies load via a permission-checked `skill` tool.

**Subagents (`task` tool)**: spawns a **fresh child session** — no history inheritance, only the prompt string with `@file`-references resolved. A `task_id` parameter can **resume** a prior child session — "persistent subagent identity," a design point neither Claude Code's nor Codex's subagent systems documented as explicitly. Background subagents (flag-gated) run as a `BackgroundJob`; completion is injected into the parent **as a synthetic user message**, re-triggering the loop — architecturally distinct from Claude Code's stream-tagged (`parent_tool_use_id`) approach. Plan mode caps parallel Explore subagents at **≤3**; nested `task` (a subagent spawning a subagent) is **denied by default** — a hard, explicit recursion cap the other two harnesses don't document as a fixed number.

**MCP**: local and remote servers via the `mcp` config key, merging into the model's tool list alongside built-ins (confirmed both by internal analysis and 2026 field sources, e.g. composio.dev's opencode MCP guide). Unofficial third-party wrappers also expose opencode itself as an MCP server (e.g. a 70-tool community package) — but unlike Claude Code's first-party `claude mcp serve`, this isn't vendor-shipped.

**Output-style equivalent**: no dedicated feature. The closest analogs are (a) switching to a different **named agent** — since agent = permission ruleset + optional prompt/model override, switching agents changes persona *and* capability simultaneously, an entangled design versus Claude Code's deliberately decoupled output-style/permission-mode split — or (b) the `experimental.chat.system.transform` plugin hook for programmatic system-prompt mutation.

**Plugin hook API**: `permission.ask` (override verdicts), `tool.execute.before/after`, `tool.definition` (rewrite what the LLM sees), `chat.message`/`chat.params`/`chat.headers`, `shell.env`, `command.execute.before`, plus experimental transforms for messages, system prompt, and compaction prompt/auto-continue — comparable in breadth to Claude Code's hook surface, expressed as JS/TS callbacks in-process rather than external stdin/stdout scripts.

### 3. Enforcement points

The permission engine (internal analysis, `packages/opencode/src/permission/index.ts`) is **allow/ask/deny per permission-key × wildcard pattern**, last-match-wins, with unmatched patterns defaulting to `ask` — a safe default by construction. Verdicts are richer than binary: allow / allow-once / allow-always (session-persisted) / deny-by-rule / reject / **reject-with-feedback** (`CorrectedError`, injected back as steering — unifying the permission gate and the correction channel in one mechanism). Bash governance uses a real AST parser plus an **LLM-generated arity dictionary** so "always allow `git checkout main`" generalizes to the command family `git checkout *`, not the literal string — the generating prompt is checked into the repo as provenance. A blanket `deny` **removes the tool from the model's advertised list entirely** (deny shrinks the toolset, not just gates it) — the same practitioner-endorsed pattern Claude Code users apply manually to sensitive files, but opencode does it structurally by default. Subagent permission inheritance is **asymmetric**: deny rules and `external_directory` restrictions flow parent→child; allow rules do not — a child's positive capabilities come from its own config only.

**Sandboxing is explicitly none.** No bwrap/seatbelt/seccomp/landlock anywhere in the codebase (internal analysis, confirmed via direct source read); "sandboxes" in the code are just extra permitted directories. Isolation is delegated entirely to the permission layer and the operator's own OS environment. This is the sharpest **negative** finding relative to the other two harnesses — Codex in particular enforces at the kernel syscall level (§3 above).

**AGENTS.md is explicitly labeled "Soft (advisory to agents) except where CI mirrors them"** in opencode's own governance-model classification (internal analysis) — converging exactly with Claude Code's rules and Codex's AGENTS.md (§3 in both sections above). Three independent teams landed on the same design point.

**Practitioner reality check — a genuine gap between designed and delivered enforcement.** Despite Plan Mode being architecturally a hard permission ruleset in source, multiple **2026** GitHub issues on `anomalyco/opencode` report it leaking in practice: subagents bypass Plan Mode's read-only restriction (`#26514`), Bash commands execute during Plan Mode (`#20938`), files get edited despite "plan" mode being active (`#32793`), and Plan Mode's hardcoded system-prompt reminder ("CRITICAL: Plan mode ACTIVE… STRICTLY FORBIDDEN… ZERO exceptions") conflicts with the user's actual permission settings (`#28127`, `#28130`). The enforcement is delivered through *two* mechanisms — a permission-ruleset deny and an absolutist prose reminder layered on top — and per these reports the two don't always agree, and subagents specifically can slip through the prose layer's blast radius. **This means source-level "hard enforcement" is necessary but not sufficient evidence of delivered behavior** — a caution directly relevant to how this survey itself was conducted (see class-level implications, below).

### 4. Scheduling & headless operation

`opencode run` is the non-interactive primitive and drops directly into a crontab line or CI step — confirmed via a documented real-world pattern: `0 9 * * 1-5 cd /path/to/repo && opencode run -m anthropic/claude-sonnet-4 "..." >> /var/log/opencode-cron.log 2>&1`. `OPENCODE_PERMISSION` forces a deny on `question` prompts specifically for scheduled runs so jobs never hang waiting on an ask — the same problem Claude Code solves with `--bare`+`--allowedTools` and Codex solves with `--ask-for-approval never`.

**No native scheduler ships inside opencode itself** — same posture as Claude Code, and notably *less* native than Codex's Automations. The gap is filled by external OS cron or a **third-party community plugin** (`opencode-scheduler`: launchd/systemd/Windows Task Scheduler with cron fallback; **v1.2.0** adds workdir-scoped jobs and supervision — no-overlap plus optional timeout) — community-built, not vendor-shipped. A documented operational pattern: run `opencode serve` once as a persistent server and point cron at `opencode run --attach http://localhost:4096`, avoiding an MCP cold-start on every fire — a workaround that exists only because the default headless invocation pays that cost each time.

CI usage is natively dogfooded in opencode's own repo (internal analysis): `opencode run --agent triage` fires on issue-opened, and a duplicate-PR agent fires on PR-opened — both single-tool, deny-all-else CI agents, a real shipped example of the headless pattern. Real, dated friction: `anomalyco/opencode#13851` ("Unable to use opencode cli in a non-interactive pipeline") and `#28407` ("`opencode run` returns Session not found in headless mode, **v1.15.5**, Windows").

### 5. Memory attach points (mechanics only)

opencode wasn't in the prior Track B memory survey, so this is the first pass at its memory mechanics specifically. Per internal analysis: `/learn` **is** the memory write path — session learnings distilled into the *deepest applicable* nested AGENTS.md, 1–3 lines, explicit include/exclude criteria. `Instruction.resolve` (read-triggered lazy chain-loading of nested AGENTS.md, zero-token until the agent touches that subtree, triple-deduped) is the injection mechanism. The attach point for a builder is structural, not event-based: nested AGENTS.md files **are** the memory substrate, and the harness's own file-read logic re-injects them — the same "hooks are the attach point" pattern as Claude Code, just built directly into core loop code (`instruction.ts`) rather than exposed as a separately-named lifecycle event. No cross-session consolidation pass exists (no Auto-Dream, no Memories-style pipeline) — memory only grows by explicit `/learn` invocation, making opencode's the most manually-gated of the three memory-adjacent designs.

### 6. Build-on-top contract

opencode is client/server from the ground up: `packages/server` exposes a typed HTTP API (session/event/permission/question/pty/tui/provider/config/mcp/project/workspace/global/sync/control-plane/experimental route groups) with websocket event streaming and mDNS discovery — TUI, desktop, web, Slack bot, enterprise, *and plugins* are all peers on **one wire-protocol seam** (internal analysis; `plugins-as-sdk-clients`, already promoted to the KB). This makes opencode the most build-on-top-friendly of the three by default: a system built on it inherits a real API server, not just a CLI to shell out to. A builder gets for free: the full permission engine, the agent-loop/compaction/doom-loop machinery, the MCP client, an 11+-provider LLM abstraction, SQLite-backed session persistence, and per-step snapshot/revert. A builder must still supply: **any OS-level sandboxing** (opencode ships none — exactly the gap omnigent fills externally, see below), **any native scheduling** (external cron or the community plugin), and **cross-session memory consolidation** (no native equivalent to Auto-Dream or Memories — only manual `/learn`). Governance note: opencode's enterprise package is "structurally thin" (internal analysis) — self-hosted share/storage, org policy delivered via a remote `.well-known/opencode` config channel rather than a dedicated policy service — so a build-on-top system does not inherit a vendor-hosted control plane the way Claude Code's Managed Agents or Codex's Automations would supply; an operator owns the whole stack or none of it.

### 7. Practitioner sentiment (dated)

r/opencode praise centers on UX: *"Opencode TUI experience is so much better than others"* (81 upvotes, cited via morphllm.com's **July 2026** comparison). The driving community sentiment is explicitly **anti-lock-in**: "the appeal of an agent you own outright, pointed at whatever model you choose, with no subscription tether" — morphllm.com frames the axis as "Open Source Freedom vs. Anthropic Polish."

**The sharpest, most dated vendor-dependency finding in this entire survey belongs here.** On **2026-01-09**, Anthropic blocked opencode from using Claude via consumer OAuth tokens; opencode removed Claude Pro/Max support from its codebase, citing "anthropic legal requests." This split the community — developers who valued provider freedom rallied around opencode, developers who wanted the tightest model integration stayed with Claude Code. The finding matters beyond opencode itself: it demonstrates that a model vendor can sever a build-on-top relationship **at the authentication layer**, unilaterally, regardless of how well-designed the harness's own architecture is — no hook, permission rule, or sandbox insulates against a policy change one layer up.

## Class-level: LLM-first harnesses as a category

### What defines the class

The mechanical core is genuinely uniform across all three, independently confirmed in first-party or source-level terms for each: **the model decides the next tool call; the harness executes it, appends the result, and re-invokes the model; this repeats until the model stops calling tools.** Even the most control-flow-like harness feature in each system is implemented as something the model reaches through ordinary tool-calling, not an external state machine outside its reach: Claude Code's Plan Mode is a permission-mode gate the model's own tool calls trip against; opencode's plan mode is literally entered and exited via **callable tools** (`plan_enter`/`plan_exit`) whose side effect is a user-consent dialog; Codex composes its plan-like state from sandbox+approval axes the model's calls are evaluated against. This is the strongest evidence *for* the LLM-first hypothesis: even the harness's own meta-controls are things the model requests through, not top-down script.

**But the hypothesis needs a real qualification, and the evidence for it is consistent and repeated across all three vendors independently.** Every safety-critical enforcement mechanism in every harness surveyed lives **outside** the model's control entirely, and every vendor's own practitioner community converges on saying so explicitly: Claude Code's own docs state that hooks are "code, not judgment" and that rules alone "do not themselves block tool calls"; opencode's governance model labels its instruction file "Soft… except where CI mirrors them"; Codex's sharpest field evidence (`#25884`) shows a rule the model **correctly summarized** simply stopped being applied a few turns later. Hooks (external processes or in-process callbacks the model cannot argue with, only receive a `deny` from), sandboxing (kernel syscall rejection in Codex's case — the model's "decision" is moot once the kernel intervenes), and deny-by-default permission rules (which make disallowed tools **invisible**, never entering the model's option set) are all explicitly designed to sit *outside* the loop's reach. So: **LLM-first describes control flow — what happens next, in what order, with what tools. It does not describe enforcement — what's allowed to happen at all.** All three vendors converged on this same two-tier split independently, which is stronger evidence than any one of them alone.

The second convergent, best-evidenced finding: the advisory instruction-file layer (CLAUDE.md / AGENTS.md / rules) is **universally non-deterministic**, confirmed three independent ways — Claude Code's first-party docs say so directly, Codex's GitHub issue `#25884` shows it empirically with a precise, ruled-out-alternative-explanations methodology, and opencode's own internal governance-model classification labels it "Soft" in its own source. Three teams, building independently, reached the identical design point, and real usage confirms the practical consequence: a model can read and even correctly explain an instruction and still not keep applying it later in the same session.

### Where the three differ most

1. **Scheduling maturity — a genuine product-level gap, not just a maturity gap.** Codex's cloud-hosted **Automations** (cron/webhook/app-event triggers, survives the operator's machine being off) has no equivalent in Claude Code or opencode, both of which stop at "here's a headless CLI call, bring your own external scheduler." opencode's best answer is a *community* plugin; Claude Code's is a first-party CI *integration guide* (GitHub Actions/GitLab CI/CD) that still requires the operator to own the trigger.
2. **Sandboxing — a full spectrum, not a binary.** Codex: mandatory-feeling, kernel-syscall-level (Seatbelt/Landlock+seccomp). Claude Code: opt-in, OS-primitive-based, write-focused with a documented read-tool gap. opencode: **none**, by explicit design choice, isolation fully delegated to the permission layer and the operator's own environment. This is the single largest risk-posture spread among the three for a security-conscious deployer, and it directly explains why omnigent (below) had to build its own sandbox layer to wrap opencode workers safely.
3. **Vendor/ecosystem dependency risk.** opencode's 2026-01-09 OAuth block is the sharpest illustration that single-vendor harnesses (Claude Code, Codex — the harness *is* the model vendor) carry concentration risk but aligned incentives, while multi-vendor harnesses (opencode) carry diversification but are exposed to any one provider revoking access unilaterally, on their own schedule, for their own reasons.
4. **Hook-surface maturity.** Claude Code (~26 canonical events, stable, exhaustively first-party-documented) > opencode (~15 plugin-hook points, stable, source-verified) > Codex (~10 events, self-labeled "beta," version-mapped to two specific June-2026 releases, with at least one event's blocking status inconsistent across sources fetched in the same research pass). Codex is visibly earliest in its hook-system lifecycle.
5. **Memory-attach granularity.** Claude Code exposes fine-grained hook-level intercepts (`SessionStart`, `PreCompact`/`PostCompact`) a memory-system builder can literally hang logic on. Codex exposes only coarse config toggles (`generate`/`use` booleans, an idle-time gate) with no lifecycle event into its own memory pipeline. opencode exposes neither a hook nor a toggle — memory only happens via the explicit, human/agent-invoked `/learn` command, the most conservative and most manual of the three.

### Omnigent: a boundary case, not a fourth harness

Omnigent is **not** itself an LLM-first harness in the sense researched here — it is a **meta-harness** that wraps the three above (plus ~8 more: cursor, goose, hermes, kimi, kiro, pi, qwen, antigravity) and imposes its own six-phase policy engine (request/tool_call/tool_result/response/llm_request/llm_response; ALLOW/ASK/DENY plus transform verdicts; fail-closed on pre-execution phases) on top of each wrapped harness's *native* permission channel — and it does this through **exactly the hook surfaces this dossier documents** (Claude Code's `PreToolUse`/`UserPromptSubmit` hooks, a native hook bridge for Codex), not a control loop of its own for those integrations. This is independent, third-party confirmation of this dossier's central finding: hooks are the one deterministic surface every LLM-first harness exposes, and they are exactly the surface a third party reaches for when it needs guarantees the wrapped harness's own advisory layer can't provide. Where omnigent *does* run its own model-driven loop (its native `omnigent`-type executor, used by its onboarding agent and some example agents) it is LLM-first by the same definition as the other three — so the honest classification is **hybrid**: an LLM-first harness in its own right for natively-executed agents, and a policy-and-orchestration layer sitting astride other LLM-first harnesses for everything bound to `claude-native`/`codex-native`/`opencode-native`. Tellingly, omnigent ships mandatory-feeling OS-level sandboxing (bwrap/seatbelt/JobObject) as a first-class concern — filling exactly the gap this survey found in opencode, and going further than Claude Code's opt-in posture — which is itself a market signal about where the native harnesses are perceived as insufficient for production/multi-tenant use.

### Implications for a single-operator engine that builds governance INTO the harness

The single clearest, best-evidenced instruction from this survey: **do not put governance rules in the advisory layer and trust the model to keep following them across a session.** All three vendors' own documentation and/or field evidence say this doesn't reliably hold — Codex's `#25884` is the sharpest piece of direct evidence (correctly summarized, then silently unapplied), but Claude Code concedes rules are "not enforced" and opencode's own governance-model table labels its instruction file "Soft." The engine's existing posture — DDs immutable, human gate mandatory, hooks preferred over prose — is already aligned with this finding; this survey supplies strong, independent, cross-vendor confirmation that the posture is *correct*, not merely cautious. Concretely, anything the engine needs to hold **regardless of session length, compaction, or subagent delegation** belongs in a `PreToolUse`-equivalent hook (deterministic gate) or a deny-by-default permission rule (so the disallowed action never enters the model's option set), never in CLAUDE.md prose alone — and because the engine's harness is Claude Code, its ~26-event canonical hook surface is already the richest, best-documented attachment set among the three, requiring no external tooling to reach.

A second, subtler lesson comes from opencode's plan-mode leak reports: **a source-verified "hard" permission ruleset is necessary but not sufficient evidence of delivered enforcement.** Multiple 2026 GitHub issues show the gap between opencode's architecturally-hard plan-mode ruleset and its actual shipped behavior, specifically through unanticipated paths like subagent delegation. A governance-first engine should treat "the source shows a deny rule" as a hypothesis to verify against the exact paths practitioners have repeatedly found leak elsewhere — subagent delegation, background/resumed sessions, mode transitions — not as a closed case. This is a direct methodological caution for the engine's own harness-epic work: reading Claude Code's hook/permission architecture (as this dossier does) establishes what's *designed*; it doesn't establish what's *delivered* without independent testing of the same leak-prone paths.

Two forward-looking, lower-urgency notes for E4: (1) the engine currently has no native scheduling primitive available from its own harness — Claude Code requires the same external-cron pattern Codex's practitioners use, and any future unattended/autonomous-run design has to budget for building or adopting that layer explicitly, while watching the still-unsettled headless-billing question (paused May–June 2026, not resolved) as a cost-planning risk, not a stable given; (2) the engine currently has no OS-level sandbox in play, compensated today by the human review gate rather than kernel enforcement — acceptable at the engine's current autonomy level, but the Codex/omnigent precedent (kernel-level sandboxing as a first-class, not opt-in, concern) is the relevant bar to eventually meet if the engine's stated "Nick-extricated system" trajectory ever increases unattended operation beyond what a human gate alone can respond to in time.
