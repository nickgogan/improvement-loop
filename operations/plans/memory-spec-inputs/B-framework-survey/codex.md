# OpenAI Codex (CLI + Cloud) — Native Memory Architecture

Dossier for the E1 memory-architecture spec's cross-framework survey (Track B). Scope: the Codex CLI + Codex Cloud product line's own built-in memory mechanisms (2025–2026) — not the deprecated 2021 code-completion model, and not third-party memory add-ons (Mem0, Hindsight) layered on top, though their gap analyses are cited as practitioner sentiment. Written 2026-07-16; every mechanism below is version/date-stamped where the source gives one, per the recency rule. Internal KB grounding was thin (Codex appears mostly as a co-mentioned harness in cross-platform findings, not as a dedicated subject) — this dossier is external-research-heavy, per the assignment.

---

## 1. Snapshot

Codex is OpenAI's terminal-first coding agent (CLI + desktop app + IDE extension + cloud sandbox execution), positioned by OpenAI and by practitioners as the direct competitor to Claude Code. It carries **four native, mostly file-backed memory surfaces**:

| Surface | What | Who writes | Scope |
|---|---|---|---|
| **AGENTS.md hierarchy** | Static, human-authored instructions (global `~/.codex/AGENTS.md` → project-root → nested per-directory) | Human | Global → repo root → cwd, concatenated with override |
| **Memories** (`~/.codex/memories/`) | Agent-generated summaries of prior sessions, auto-written in the background | Codex, autonomously (async, idle-triggered) | Per Codex-home, machine-local |
| **Skills** (`SKILL.md`, `.agents/skills/`) | Procedural workflows, progressively disclosed | Human (or Codex via skill-creator) | Repo-local → repo-shared → user → admin |
| **Session rollouts** (`~/.codex/sessions/*.jsonl`) + **cloud task containers** | Working-memory substrate + resumable transcripts; cloud-side container state | Codex (automatic) | Per session / per cloud task, 12hr container cache |

**Currency note:** AGENTS.md discovery/merge rules and the 32 KiB size cap are current first-party doc state as fetched 2026-07-16 (`developers.openai.com/codex/guides/agents-md`, redirects to `learn.chatgpt.com/docs/agent-configuration/agents-md`). **Memories** is the newest and least-settled surface — official docs (`developers.openai.com/codex/memories`) describe it as live and configurable via `[memories]` in `config.toml`, but geographic restrictions (not available in the EEA, UK, or Switzerland) and cloud-Codex retention specifics are, per third-party analysis (Mem0, 2026-07-16), still underspecified. The Codex changelog shows active, weekly-cadence churn on the persistence layer through July 2026 — e.g. 2026-07-08 (CLI 0.143.0): "core: persist world state in rollouts," "core: make AGENTS.md react to environment changes," "Project executor skills through World State" — indicating OpenAI is mid-build on a unifying internal "World State" representation that AGENTS.md, skills, and compaction all read/write into. Treat the exact mechanics of World State as **actively moving** rather than stable — this dossier reports the shipped, documented behavior around it, not its unfinished internals.

## 2. Memory model by type

### Working / short-term memory
**Substrate:** the model's context window for the active turn/session — system context, injected AGENTS.md chain, invoked skill bodies, conversation history, tool call/results. Persisted turn-by-turn to a local rollout file (`~/.codex/sessions/*.jsonl` per CLI; Desktop stores an equivalent rollout format) so the working-memory substrate survives process restarts even before any explicit "memory" feature engages.

**Write path:** every turn appends to the rollout automatically; no separate write step, same as any harness's conversation log.

**Injection/recall:** automatic and total until compaction intervenes. `codex resume --last` (or `codex resume <SESSION_ID>`, or interactive picker) reopens a saved rollout and reinjects its full history for continued work in the same repo/session.

**Consolidation/reflection — context compaction:** token-threshold-based, not percentage-based at the trigger layer: compaction fires when accumulated tokens exceed `model_auto_compact_token_limit` (documented defaults vary by model — reported figures include ~180K and ~244K for different Codex models), with a 95% `effective_context_window_percent` safety margin as final backstop (source: `codex.danielvaughan.com`, 2026-03-31/04-14, cross-checked against `github.com/badlogic` comparative gist). Mechanically: Codex appends a summarization prompt to the full history, collects the model's summary, then reconstructs the session as **initial context + ~20K tokens of recent user messages + the generated summary** — replacing, not appending to, the prior history. Compaction fires at two moments: (a) before sending a new user message, if the pre-send token count already exceeds threshold; (b) at a tool-call-chain loop boundary, if the chain pushed usage over threshold mid-task, without waiting for the next user turn. The comparative gist (badlogic, cross-referencing Claude Code/Codex/OpenCode/Amp) flags the same documented risk Anthropic states for its own compaction: **"long conversations and multiple compactions can cause the model to be less accurate"** — quality degradation compounds across successive compactions, and Codex implements retry-with-backoff for failed compaction calls rather than a hard stop.

**Decay/forgetting/supersession:** everything before the compaction boundary is discarded except what the summary captures; the ~20K-token tail of literal recent messages is the only guaranteed-verbatim survivor. Two 2026 GitHub issues document this substrate as **less reliable than the spec implies**: `openai/codex#29426` (2026-06-22) — Codex Desktop auto-compacts a short *resumed* session even when usage is far below the model's context window (a 50K/258K-token session triggered compaction on resume before the first new message was even processed); `openai/codex#24089` (2026-05-22) — old Desktop rollouts, after a CLI/Desktop version upgrade, resumed into internally-inconsistent token counts (e.g. `4.28M used / 570K window` — i.e. a persisted `last_token_usage.total_tokens` value literally exceeding `model_context_window`), causing remote compaction to fail outright with `context_length_exceeded`. Both are corruption/edge-case bugs in the persisted token-accounting state that backs compaction decisions, not steady-state behavior — but both were reproducible enough to file, and both implicate the same "World State"/rollout persistence layer the July 2026 changelog shows is under active rework.

### Episodic memory (specific past events/sessions)
**Substrate:** two layers. (1) Raw session rollouts (`~/.codex/sessions/*.jsonl`) — full transcripts, resumable verbatim via `codex resume`, the closest Codex has to a literal episodic log. (2) **Memories** (`~/.codex/memories/`) — the genuinely novel piece: Codex **auto-summarizes prior sessions in the background and writes the summaries to disk**, without the user copying anything into a file by hand. Per official docs (`developers.openai.com/codex/memories`) and corroborated by third-party technical analysis (Mem0, 2026-07-16), the store contains multiple files — a `memory_summary.md`-style rollup, a durable-facts file (reported as `MEMORY.md`), and a `raw_memories.md`-style evidence/detail file.

**Write path:** eligibility-gated and asynchronous, not real-time. A session must go idle for a default **6 hours** before it's eligible for consolidation — active sessions never trigger it, and short-lived sessions are skipped. Generation uses a **two-model split**: `memories.extract_model` performs per-task extraction (deciding what from *this* session is worth remembering) and `memories.consolidation_model` merges that extraction into the existing global store (deduplicating, updating, presumably superseding stale facts — exact merge/conflict-resolution logic isn't detailed in fetched docs). Generation also pauses below a configured `min_rate_limit_remaining_percent`, and can be scoped off for tasks that used external context (MCP calls, web search, tool search) via `memories.disable_on_external_context`. Codex applies **automatic secret redaction** on generated memory content, though docs recommend manual review before sharing a Codex-home directory.

**Injection/recall:** governed by `memories.use_memories` (a separate on/off switch from generation, `memories.generate_memories`) — the asymmetry lets an operator run read-only (validate the memory layer without adding noise) or write-only (a deliberate onboarding session that seeds memory without recalling anything mid-task) independently. Per Mem0's technical read: recall is **wholesale-summary + grep**, not embedding/semantic retrieval — the summary file loads in full, and the agent falls back to literal text search (`grep`-style) over the detail file for specifics. This is a materially different recall mechanism from vector-similarity memory systems and inherits grep's precision/recall tradeoffs (misses paraphrases, catches exact terms).

**Consolidation/reflection:** the two-model extract→consolidate pipeline described above **is** the consolidation step — there is no separate distillation pass on top of it in the fetched documentation (contrast Claude Code's "Auto Dream," which is a *second*, later reflection pass over already-written memory; Codex's consolidation happens inline at write time).

**Decay/supersession:** Mem0's analysis reports **30-day pruning of unused memories** — memories that go unaccessed age out; this figure was not independently corroborated in the first-party docs fetched, so treat as third-party-sourced pending direct confirmation. Per-task control is available via the `/memories` slash command (CLI TUI and ChatGPT desktop), letting a user decide, per session, whether it may read existing memories or contribute to future ones. Official guidance explicitly frames memories as **"a helpful recall layer, not the only source for rules that must always apply"** — i.e., OpenAI itself does not position Memories as a substitute for AGENTS.md's guaranteed-injection semantic layer.

**Explicit gaps (per Mem0's 2026-07-16 competitive analysis, corroborated by the geographic-restriction note in search results):** no cross-machine sync (memories are local to the Codex-home directory, don't follow a user to a new device); no team/multi-user sharing (each operator's store is isolated); not hand-editable by design (generated-only, unlike AGENTS.md); unavailable entirely in the EEA, UK, and Switzerland (users there get the AGENTS.md layer only); Codex Cloud's memory retention and config specifics are undocumented as of the fetch date.

### Semantic memory (general facts/rules about the codebase, world, conventions)
**Substrate:** AGENTS.md hierarchy — the primary, human-authored semantic store, and (per official docs) explicitly the layer that **cannot be edited autonomously by the agent**. Three scope levels, checked in this order: **global** (`$CODEX_HOME`, default `~/.codex` — checks `AGENTS.override.md` first, falls back to `AGENTS.md`, uses only the first non-empty file); **project** (walks from the Git root down to the current working directory, checking `AGENTS.override.md` → `AGENTS.md` → any names in `project_doc_fallback_filenames` at each directory level, including at most one file per directory).

**Write path:** entirely human-authored. No `/init`-equivalent auto-generation flow surfaced in fetched docs (contrast Claude Code's reviewable `/init` proposal flow) — AGENTS.md is conventionally hand-maintained, though the open-standard status of the format (adopted by the Agentic AI Foundation under the Linux Foundation, per search results) means many projects' files are copy-adapted from templates rather than written from scratch per-repo.

**Injection/recall:** files merge **root-to-leaf with later files overriding earlier ones** — "guidance closest to your working directory takes precedence," the inverse-priority convention of a cascading stylesheet. Codex "rebuilds the instruction chain on each run" (no manual cache-clearing needed on edit). Combined guidance is capped at **32 KiB by default** (`project_doc_max_bytes`), and per Mem0's analysis this truncation is **silent** — no explicit doc statement that a user is warned when the cap is hit. Recommended content split by scope (persistent working agreements — testing conventions, approval workflows — at global; repo norms — linting, doc standards — at project root; specialized/security-sensitive rules via nested `AGENTS.override.md`) is prescriptive guidance, not enforced structure.

**Consolidation/reflection:** none native — same posture as Claude Code's CLAUDE.md (human-maintained, no auto-summarization). The 2026-07-08 changelog entry "core: make AGENTS.md react to environment changes" suggests some dynamic re-evaluation is being added, but the mechanic isn't documented in the fetched pages — flagged as moving, not settled.

**Decay/supersession:** no built-in expiry; AGENTS.md persists until a human edits it. The empirically documented failure mode is not decay but **reliability of application within a session** — see §4; multiple GitHub issues report AGENTS.md rules being read correctly early in a session and then not consistently re-applied on later turns, independent of the size-cap/truncation mechanism.

### Procedural memory (how to do things — skills, workflows)
**Substrate:** Skills — `SKILL.md` files with YAML frontmatter (`name`, `description` required) plus optional bundled scripts/references/assets, an implementation of the cross-platform open Agent Skills standard (also used by Claude Code, Cursor, and others). Four discovery scopes, ascending: repo-local (`.agents/skills`), repo-shared (`$REPO_ROOT/.agents/skills`), user (`$HOME/.agents/skills`), admin/system (`/etc/codex/skills`).

**Write path:** human-authored by default; a `skill-creator` system skill ships in `openai/skills` for agent-assisted authoring, mirroring Claude Code's equivalent. No native pipeline converts a Memories entry into a Skill — same "no learning-to-procedural graduation" gap the Claude Code dossier notes for CLAUDE.md/auto-memory, meaning Codex's two memory-adjacent layers (Memories and Skills) don't feed each other automatically either.

**Injection/recall:** progressive disclosure — at session start Codex loads only skill *metadata* (name/description/path), budgeted at **2% of the context window or 8,000 characters**, whichever is the binding constraint; only on selection does it read the full `SKILL.md` body. Activation is explicit (`$skill-name` syntax) or implicit (task description matches metadata). Launched as an experimental feature (reported December 2025), matured into the current form through 2026.

**Explicitly not natively handled:** no automatic memory→skill promotion; no versioning/rollback mechanism surfaced in fetched docs beyond ordinary file edits; no cross-repo skill sync beyond manually placing files at the user/admin scope.

## 3. Lifecycle trace — one memory item end-to-end

Trace a single fact: *"this repo's test suite requires `pnpm test --filter=changed`, not plain `pnpm test`, or CI times out."*

1. **Turn 1 (working memory):** the operator corrects Codex mid-session after it runs the slow full suite. The correction lands in the active context window and is appended to the session's rollout JSONL automatically — no explicit save action.
2. **Session end, idle 6+ hours:** the session is not actively resumed. Per the Memories eligibility gate, it becomes a consolidation candidate.
3. **Extraction:** `memories.extract_model` runs in the background over the idle session, judges the correction "worth remembering," and produces a per-task memory input. Secrets (if any were in scope) are redacted at this stage.
4. **Consolidation:** `memories.consolidation_model` merges the new extraction into the existing global store at `~/.codex/memories/` — updating the summary file and appending to the raw-evidence file, deduplicating against any prior related fact.
5. **Next session, weeks later:** if `memories.use_memories` is on, Codex loads the memory summary wholly at session start. If the operator asks something touching test commands, Codex either finds the fact already in the loaded summary or falls back to a grep-style search over the raw-evidence file for the specific command string. The fact is surfaced as **recall, not a guaranteed rule** — official docs explicitly caution it's not to be relied on for must-always-apply constraints.
6. **Parallel, permanent path:** if the operator instead (or additionally) writes the same fact into the project's `AGENTS.md`, it becomes part of the deterministically-injected instruction chain on *every* session from then on, subject only to the 32 KiB combined cap and to the empirically-documented mid-session application-reliability issue (§4) — i.e., even the "guaranteed" layer has observed drift.
7. **Compaction interaction:** if the session in which the fact was first stated runs long enough to hit the auto-compact threshold before ending, the correction survives only if it falls within the ~20K-token verbatim tail retained post-compaction, or if the compaction summary judged it important enough to include — there's no compaction-specific guarantee that a stated correction persists to session end, independent of the Memories pipeline.
8. **Decay:** per Mem0's third-party account, if the memory entry goes unaccessed, it's pruned after ~30 days. The AGENTS.md copy, if made, does not decay — it persists until a human edits or deletes it.

This trace surfaces the core architectural split: Codex has **exactly one durable, deterministic, human-controlled memory path (AGENTS.md)** and **exactly one probabilistic, agent-controlled, self-pruning memory path (Memories)** — with no automatic promotion between them, and both independently vulnerable to different failure modes (silent truncation / mid-session drift for AGENTS.md; eligibility-gate delay / grep-based imprecision / 30-day decay for Memories).

## 4. Practitioner sentiment (works / doesn't-work, dated)

**AGENTS.md reliability degrades within a session — three corroborating GitHub issues across 9 months:**
- `openai/codex#4466`, **2025-09-29**: "Agents.MD being ignored" — a rule that previously worked ("always begin your first response by reading the changelog and readme") stopped firing after an update; filer's framing: "this seemed to have broken for me recently."
- `openai/codex#6502`, **2025-11-11**: an explicit, repeated TDD instruction in AGENTS.md ("tests must turn green before committing") was ignored even after the user forced Codex to re-run the failing suite and confirm the failure — Codex still suggested committing.
- `openai/codex#25884`, **2026-06-02**: the most precise diagnosis — filer explicitly rules out discovery/truncation/precedence as the cause (files were small, Codex could correctly *summarize* the rules early in the session) and isolates the failure to **application drift across turns**: "later turns may stop applying those rules reliably... AGENTS.md behaves more like a soft hint than a durable operating constraint." This is the most load-bearing practitioner claim in this dossier — it says the semantic-memory layer's failure mode isn't the documented 32 KiB cap, it's silent behavioral decay of a nominally "always injected" instruction over the course of a single session.

**Context compaction has shipped user-visible bugs, June 2026:**
- `openai/codex#29426`, **2026-06-22**: Desktop auto-compacts a resumed session well under its context budget, before the first new message — described by the filer as compaction "before the new user message was processed," contradicting the documented threshold-based trigger.
- `openai/codex#24089`, **2026-05-22**: post-upgrade, old rollouts carry internally-impossible token counts (`4.28M used / 570K window`), and the built-in remote-compact recovery path itself fails with `context_length_exceeded` — a documented case of the persistence layer's own accounting corrupting the compaction it's supposed to enable. Filer's manual recovery (hand-editing the rollout JSONL to drop impossible token-count events) is a workaround, not a supported path.

**Long-session/large-output memory loses unfavorably to Claude Code, June 2026 head-to-head:** Composio's "100+ Hours With Both" comparison (**2026-06-04**) states Codex handles large tool outputs via "head/tail truncated, middle completely dropped," versus Claude Code's practice of writing substantial outputs to files and pulling from them on demand. The article's central anecdote: in a 26-hour macOS session, Claude/Opus 4.7 recalled and re-applied a bug fix across an overnight gap and heavy context reduction; the author states directly, **"Codex does not hold that for me. The middle disappears, and the architectural memory goes with it."** No comparable positive Codex anecdote for long-session recall appears in the piece.

**Steadiness and token efficiency favor Codex on other axes, July 2026:** morphllm.com's comparison (dated **July 2026**) scores the overall matchup 3-2 in Codex's favor on "steadiness, delegation, and more use for the same tokens," while conceding Claude Code wins "when set up properly with its harness during long sessions" — i.e., practitioner sentiment splits by session length: Codex is reported as the steadier, cheaper choice for shorter/more numerous tasks; Claude Code is reported as the better choice specifically when memory/context durability over a long single session matters. This is a directly relevant signal for a spec choosing between "many short delegated tasks" vs "one long-running thread" architectures.

**A persistent working thread — not a formal memory feature — is what made Codex "click" for at least one high-volume practitioner (internal KB, sourced from Nate B Jones, video dated 2026-06-12):** the KB finding `chief-of-staff-home-base-thread.md` documents Jones naming a single persistent thread (not AGENTS.md, not Memories — this predates the Memories feature's documentation) as the pattern underpinning his reported 300–500M-tokens/day delegation practice. His explicit caveat, carried in the finding: **"not magic memory — the operator still supplies sources, corrections, and demands receipts."** This is a positive-sentiment data point for continuity-via-persistent-session over continuity-via-generated-memory-artifact, from a named, highly active practitioner — but it's a workflow habit, not a claim about a Codex feature working well.

**No reliable in-harness cost/usage surface (internal KB, dated to the underlying source's session):** the KB finding `harness-cost-readout-unreliability-independent-log-accounting.md` reports "Codex offered no findable session-cost surface at all," forcing the same practitioner to an external log-based accounting tool. Not memory per se, but adjacent observability debt in the same persistence layer.

**Third-party vendors are actively building on top of the gaps, confirming them as real (Mem0, published 2026-07-16 — today):** Mem0's own competitive-positioning post lists six specific gaps in native Memories as its value proposition: no cross-machine sync, no team sharing, read-only/no hand-editing, EEA/UK/Switzerland unavailability, the 32 KiB AGENTS.md ceiling with silent truncation, and underspecified Cloud-Codex retention. Read with the appropriate discount for vendor self-interest, but the gaps themselves (especially the geographic restriction and the read-only design) are stated as fact about the native feature, not competitive spin.

**Reddit sentiment (r/codex), imprecise date, 2026, secondhand via aggregator:** per a Developers Digest roundup, "the dominant complaint on r/codex is mid-stream usage-limit cuts" — a rate-limiting/availability complaint, not directly a memory complaint, but relevant because usage-limit cuts interact with the Memories eligibility gate (`min_rate_limit_remaining_percent`) — i.e., the same scarcity that frustrates users mid-session is also what suppresses background memory generation.

**Security note, dated 2026 (multiple outlets, e.g. TheHackerNews, VentureBeat), tangential but relevant to any human-gated design:** AGENTS.md's status as an auto-trusted, auto-injected context source is itself an attack surface — a "Friendly Fire" exploit reported mid-2026 hides malicious instructions inside AGENTS.md/CLAUDE.md-style files that agents "treat with extra trust." Not a memory-quality finding, but a governance-relevant one: any human-gated engine adopting an AGENTS.md-equivalent must treat write-access to that file as a privileged action, not passive documentation.

## 5. Verdict — strengths, failure modes, transferability

**Strengths:**
- **Genuine, agent-native cross-session semantic/episodic memory (Memories) is a real capability gap Claude Code doesn't ship natively** — the closest Claude Code analog ("Auto Dream") is, per the companion dossier, undocumented first-party and possibly unreleased/feature-flagged. Codex's Memories is documented, configurable (`[memories]` in `config.toml`), and has explicit read/write independence — a genuinely useful design (validate before trusting; seed without polluting).
- **The two-switch (generate/use) + eligibility-gate (idle 6hr, rate-limit floor) design is a disciplined take on "when should the system write to itself."** It avoids writing memory from active/incomplete work, which is a real risk other ambient-memory designs don't always guard against.
- **AGENTS.md's merge model (root-to-leaf, later-overrides-earlier, override-file convention) is clean and matches the CSS-cascade mental model** developers already have — genuinely portable design, and it's now a cross-vendor open standard (Agentic AI Foundation / Linux Foundation), which is direct evidence the convention generalizes.
- **Progressive-disclosure skill loading (2%/8,000-char metadata budget) is a concretely specified, resource-bounded procedural-memory design** — more precisely quantified in fetched docs than Claude Code's skill-budget figures.

**Failure modes (evidenced, not speculative):**
- **Semantic-memory application drift within a single session** (`#25884`, 2026-06-02) is the most serious finding here: an instruction can be correctly read and even correctly *summarized* by the model, and still not be reliably *applied* several turns later. This is a subtler and arguably worse failure than truncation — truncation is at least legible (hit the cap, know it), drift is invisible until a violation is caught.
- **Compaction/persistence-layer bugs corrupting the token-accounting state itself** (`#29426`, `#24089`) show the substrate underneath both working memory and Memories' eligibility gate is not yet fully hardened as of mid-2026 — and the July 2026 changelog's heavy "World State" rework activity is corroborating evidence that OpenAI itself is still stabilizing this layer, not that it's settled.
- **No memory→procedure promotion path**, mirroring the gap noted for Claude Code — a fact learned via Memories doesn't become a Skill without a human (or a future feature) doing the conversion by hand.
- **Grep-based (not semantic) recall over the Memories detail store** means recall quality is bound by literal term overlap — a real architectural choice with a real precision/recall cost, not yet independently benchmarked in any source found here.
- **Geographic and cross-machine limits** (EEA/UK/Switzerland exclusion; no sync) make Memories a partial, not universal, solution even where available.

**Transferability notes for a markdown+git, single-operator, human-gated engine (MetaSystem/IL):**
- The **AGENTS.md precedence model is directly transferable** and validates the engine's own layered-file philosophy (global → system → local, later overrides earlier) — nothing here contradicts the design already implicit in the engine's CLAUDE.md/rules structure; it's independent convergent evidence for the pattern.
- The **generate/use independent-toggle design for auto-memory is a strong candidate primitive** for any self-improve-style pipeline the engine builds: being able to run "read-only" (validate what the memory layer would surface, without trusting it yet) or "write-only" (a deliberate capture session that doesn't pollute live recall) maps directly onto the engine's existing generator/assessor-separation rule and its human-gate discipline — a scan-mode-only or capture-mode-only posture is exactly this pattern.
- The **application-drift failure mode (`#25884`) is the single most important cautionary transfer**: it demonstrates that "the agent read the rule" is not evidence "the agent will keep applying the rule" — a distinction the engine's own governance rules (which rely on an agent reading CLAUDE.md/rules once per session and holding them for the whole session) should treat as a live risk, not a solved problem, especially for long single-session work.
- **Memories' idle-triggered, background-batch consolidation (6hr gate) is a workable transferable pattern for a git-committed engine**: rather than writing memory synchronously mid-session (risking incomplete/premature capture), gate consolidation on session-idleness and run it as a discrete, reviewable batch step — this is compatible with the engine's human-gate requirement in a way real-time ambient writing is not, since a batch step can be surfaced for review before commit.
- **The grep-vs-semantic recall tradeoff is directly relevant to E1's retrieval-mechanism choice**: Codex's own vendor chose literal search over embeddings for its native memory layer, which is evidence (not proof) that a markdown+grep-native engine's existing retrieval substrate (ripgrep over frontmatter, per this workspace's Process Rule 1) is a legitimate, vendor-precedented design point — not a compromise forced by lacking a vector database.
- **The AGENTS.md-as-attack-surface finding is a governance transfer**, not a memory-mechanics one: any engine mechanism that lets an agent write to a file that a *future* agent session will auto-trust and auto-inject (which describes the engine's own governance/rules files) should be held to the same "privileged write, not passive documentation" standard — reinforces, rather than introduces, the engine's existing human-gate-on-governance-writes posture.
