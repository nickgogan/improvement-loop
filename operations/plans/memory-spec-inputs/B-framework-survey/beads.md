# Beads (`bd`) — Git-Backed Graph Issue Tracker as Agent Memory

Dossier for the E1 memory-architecture spec's cross-framework survey (Track B). Scope: Beads (Steve Yegge, `bd` CLI) as a memory substrate for coding agents, read explicitly through the "process memory" lens — is the state of *whether the work is on track* a distinct memory type from *what the agent knows*, and is Beads the strongest infrastructure case for that thesis. Written 2026-07-16. Internal grounding: `watched-libraries/beads.md` and `watched-libraries/analysis/beads-analysis.md` (analyzed 2026-04-19 against v1.0.2) plus the KB findings that cite Beads (`database-as-shared-memory-coordination.md`, `semantic-memory-decay-compaction.md`, `agent-state-machine-with-witness-monitoring.md`, `zero-framework-cognition-zfc.md`, `cross-repo-issue-routing.md`, `memory-decay-compaction-convergence.md`, `issue-based-agent-orchestration-replacing-markdown-plans.md`). External research: `gh` CLI against `steveyegge/beads` (repo, CHANGELOG, live Docusaurus docs under `docs/`), Perplexity search/ask, WebSearch/WebFetch against HN, Reddit, dev.to, and independent blogs.

**Load-bearing currency correction, made explicit up front:** the task brief's assumed architecture — "JSONL-in-git as canonical store + SQLite cache" — describes Beads' **pre-v0.55 (pre-2026-03) design**, not its current one. Beads migrated to an embedded Dolt (versioned SQL) backend starting v0.55.0, and v1.0 (2026-04-03) completed that migration: "the Dolt migration that began in v0.55.0 is complete: embedded Dolt is the default on all platforms" (CHANGELOG, v1.0 entry). As of the latest stable release, **v1.1.0 (2026-07-04)**, Dolt is the sole canonical datastore; `.beads/issues.jsonl` is an **optional, opt-in export** for viewers/interchange/backup, explicitly demoted from its earlier default-on, git-tracked role as of v1.0.5 (2026-05-28): *"Dolt is the primary datastore. `.beads/issues.jsonl` is now treated as an optional export for viewers such as `bv`, interchange, and issue-level migration. It is not the canonical git-tracked source of truth, not cross-machine sync, and not a full database backup"* (CHANGELOG). The internal `beads-analysis.md` (2026-04-19, v1.0.2) already had this right — Dolt-based, not JSONL-based — so this dossier's correction is aimed at the task brief's premise, not at internal drift. Separately: `gastownhall/beads` and `steveyegge/beads` resolve to the same underlying repo (identical star count and push timestamp on 2026-07-16 lookups) — the org name in URLs is historical, not a fork.

## 1. Snapshot

Beads is a CLI (`bd`) that gives coding agents a persistent, queryable, dependency-graph-structured task tracker instead of markdown TODO files, positioned explicitly by Yegge as "a memory upgrade for your coding agent" (repo tagline, current as of 2026-07-16). It is not a knowledge base — it stores almost no facts about the codebase itself. It stores **work items** (issues/"beads") with typed dependency edges, status, ownership/claims, and a small separate key-value **persistent-memory** sidecar (`bd remember`/`bd recall`). 25.4k GitHub stars, latest stable v1.1.0 (2026-07-04), actively developed on a roughly weekly release cadence through July 2026 (an `[Unreleased]` CHANGELOG section already has three more entries queued as of the fetch date). Currency of this dossier: repo state, CHANGELOG, and live Docusaurus docs (`docs/`) as fetched 2026-07-16 via `gh api`; practitioner sentiment sourced 2025-10 through 2026-07 and dated per claim below.

**Does the process-memory thesis hold?** Yes, and cleanly. Beads' actual differentiated contribution is not compaction or fact-retention — the KB already corrected an earlier misattribution of "semantic decay" to Beads (`memory-decay-compaction-convergence.md`: *"Beads is actually an issue-based agent orchestration system, not a compaction strategy"*). What Beads ships is a first-class **state machine for is-the-work-on-track**: status (`open/in_progress/blocked/deferred/closed/pinned/hooked`), a dependency graph that computes a claimable frontier (`bd ready`), atomic claim/lease semantics for who owns what right now, and typed close-reasons for why something ended. None of that is "what the agent knows" — it is orthogonal to and separately stored from Beads' own semantic-memory feature (`bd remember`). The clean separation of these two stores *inside the same tool* is itself evidence for the thesis: even a system built by someone motivated to unify "agent memory" under one product still ended up with two structurally different subsystems for "facts" vs. "work state."

## 2. Memory model by type

### Working / short-term memory
**Substrate:** the live Dolt database (`.beads/embeddeddolt/` in the default embedded mode, or `.beads/dolt/` in server mode) plus the active session's context window. There is no separate "working memory" table — the current state of an issue (whoever claimed it, its notes/design/acceptance-criteria fields) *is* the working-memory substrate, queried fresh each turn via `bd show`/`bd ready`.

**Write path:** every `bd create`/`bd update`/`bd close` auto-commits to Dolt history (each write is a Dolt commit — "Every write auto-commits to Dolt history," architecture doc). Agents write mid-task via CLI or MCP; humans write the same way.

**Injection/recall:** `bd prime` at session start (via a `SessionStart` hook for Claude Code/Codex/Cursor) emits AI-optimized workflow context — brief (~50 tokens) in MCP mode, fuller (~1-2k tokens) in CLI mode — plus persistent memories appended. A `PreCompact` hook fires `bd dolt push` before Claude Code's own context compaction, so in-flight Dolt state is never lost to a *context*-window compaction event (distinct from Beads' own `bd compact`/`bd admin compact`, which act on the Dolt *history* and *closed-issue content*, not the live conversation).

**Consolidation/reflection:** none at this layer — it's live state, re-read every turn.

**Decay/forgetting:** none while an issue is open/in_progress; see process memory below for what happens after close.

### Episodic memory (specific past events/sessions)
**Substrate:** the `events` table (audit trail) plus per-issue `comments` (threaded, `bd comment add`) and Dolt's own commit history (every mutation is a commit, queryable via `bd history`/`dolt diff`). `bd show <id>` surfaces "task details and audit trail."

**Write path:** automatic on every state transition (Go code writes the event row); comments are explicit agent/human writes.

**Injection/recall:** on-demand via `bd show`/`bd history`/`dolt diff` — not injected wholesale; an agent pulls a specific issue's episodic trail only when it needs it.

**Consolidation/reflection:** `bd compact` (note: distinct command from `bd admin compact`) squashes old Dolt *commits* older than N days into one, cherry-picking recent commits forward — this is history-size hygiene, not semantic summarization: *"For semantic issue compaction (summarizing closed issues), use 'bd admin compact'. For full history squash, use 'bd flatten'"* (`docs/cli-reference/compact.md`).

**Decay/supersession:** commit-level squash only prunes *how* history is stored, not issue content; issue-level decay is handled separately (process memory, below).

### Semantic memory (facts/rules about the codebase, world, conventions)
**Substrate:** a small, explicit key-value store — `bd remember "<insight>" [--key K]` / `bd recall <key>` / `bd forget <key>` / `bd memories [search]`. This is genuinely separate from the issue graph; Beads does not conflate "a fact I know" with "a task I'm tracking." AGENTS.md/CLAUDE.md files (written by `bd init`) are the other semantic layer, conventional and human/agent-editable, not Beads-managed at runtime.

**Write path:** agent- or human-initiated `bd remember`, any time. Auto-generated key from content unless `--key` given; re-storing to an existing key updates in place (supersession by overwrite, not versioning).

**Injection/recall:** wholesale injection at `bd prime` time — *all* memories are appended to the session-start context by default. This was flagged as a real practitioner pain point (see §4) and has since been addressed with **injection caps**: `--max-memories N` / `--max-memory-chars N` (or `prime.max-memories`/`prime.max-memory-chars` config), which cap at whole-memory boundaries, always emit at least one memory, and print an elision banner pointing to `bd memories` for the rest. This is a live example of practitioner-complaint → shipped-fix inside the same tool's lifecycle.

**Consolidation/reflection:** none automatic — no summarization pass merges related memories; `bd forget` is the only cleanup lever, fully manual.

**Decay/forgetting:** none by default — memories persist until explicitly `bd forget`-ten. No TTL, no LRU eviction observed in fetched docs.

### Procedural memory (how to do things — skills, workflows)
**Substrate:** the "chemistry" system — **formulas** (TOML templates with `{{variables}}` and `needs` dependencies, the reusable recipe) → **protos** (compiled templates) → **molecules** (real, live beads instantiated from a proto, `bd mol pour`) → **wisps** (ephemeral, ungraphed instantiations for transient work, excluded from cross-machine sync by default, `bd purge`-able). Plus conventional Skill files (`SKILL.md`) shipped via the Claude/Codex/Cursor plugin integrations for the `bd` workflow itself (not user-workflow procedural memory).

**Write path:** a human or agent authors a `.formula.toml`; `bd cook` compiles it; `bd mol pour` instantiates it as real graph-tracked work whenever the same repeatable process (a release checklist, a review pipeline) needs to run again.

**Injection/recall:** `bd ready --mol <id>` surfaces which steps of an in-flight molecule are unblocked right now — the same ready-work query mechanism used for ordinary issues, reused for procedure execution.

**Consolidation/reflection / decay:** none observed — formulas are hand-authored and stable; no automatic promotion from "a task pattern that recurred three times" into a formula (no learning-to-procedural graduation, the same gap the sibling Codex/Claude Code dossiers note for their own memory-adjacent layers).

### Process memory (is-the-work-on-track state — the fifth-type thesis)
**Substrate:** the issue graph itself. Status field (`open/in_progress/blocked/deferred/closed/pinned/hooked`); typed dependency edges (`blocks`, `parent-child`, `related`, `discovered-from`, plus knowledge-graph edges `relates-to`/`duplicates`/`supersedes`/`replies-to`); ownership via `assignee` + atomic claim.

**Write path:** `bd update <id> --claim` is a compare-and-swap — atomic, collision-safe claim. As of the `[Unreleased]` CHANGELOG (fetched 2026-07-16, schema v54, migration `0054`), claims now carry a **lease**: `lease_expires_at = now + TTL` (default 5 min) plus `bd heartbeat <id>` to extend it and `bd reclaim --older-than <dur>` to revert an abandoned claim back to `ready` — explicit dead-worker recovery, layered on top of the Dolt cell-level-merge conflict handling (a shared `row_lock` cell forces racing heartbeat-vs-reclaim writes into a serialization conflict the retry layer replays, "instead of silently cell-merging into a zombie claim"). This is infrastructure built specifically for the process-memory problem — not memory-of-facts, memory-of-*whose turn it is and whether they're still alive*.

**Injection/recall:** `bd ready` — "the GetReadyWork API which applies blocker-aware semantics to find truly claimable work," explicitly excluding `in_progress`/`blocked`/`deferred`/`hooked` issues. This is the single most load-bearing read in the whole system: it converts a dependency graph into "the one query an agent needs to know what to do next," which is exactly the process-memory function (not "what do I know," but "what state is the work in, and what can move now").

**Consolidation/reflection:** `bd close --reason <text>` (aliased `done`) records why work ended — a typed, queryable close-reason, not a free-text afterthought; batch closes map `--reason` flags positionally to IDs. Close reasons plus the `supersedes` link type give Beads an explicit vocabulary for *how* work concluded (done / superseded / duplicate / abandoned), which most markdown-plan or flat-TODO systems don't capture at all.

**Decay/forgetting — the actual "memory decay" feature:** `bd admin compact` (not `bd compact`, a genuinely confusing near-duplicate command name that both this dossier and a practitioner's writeup flag): *"Compact old closed issues using semantic summarization... This is permanent graceful decay — original content is discarded"* (`docs/cli-reference/admin.md`). Two tiers are defined: Tier 1 (30 days closed, ~70% reduction, semantic compression) is implemented; Tier 2 ("ultra compression," 90 days closed) is **documented as planned, not yet implemented** — an honest, dated admission of an unfinished decay path. Compaction has three human/agent-mediated modes (`--analyze` exports candidates for review, `--apply` accepts an agent-provided summary, no API key needed for either) and one fully automatic legacy mode (`--auto`, requires an Anthropic API key) — i.e., the *current* recommended path keeps a human or agent explicitly in the loop on what gets thrown away, rather than trusting a background job to summarize-and-delete unsupervised.

## 3. Lifecycle trace — one issue end-to-end

Trace: an agent discovers a bug mid-implementation, tracks it, and the fact survives to a much later session.

1. **Mid-session discovery:** the agent is implementing feature X and hits a bug. It runs `bd create "Auth token refresh race condition" -t bug -p 1 --deps discovered-from:bd-a3f8` — this auto-commits to the local Dolt database immediately (every write is a Dolt commit) and receives a collision-free hash ID (`bd-7x2f`), with no coordination needed against any other agent that might be writing concurrently.
2. **Context compaction mid-session:** Claude Code's own context window fills and triggers compaction. The `PreCompact` hook fires `bd dolt push` first, publishing the new issue (and any claim/notes state) to the Dolt remote (`refs/dolt/data`, layered on the same git remote as `origin` by default) *before* the in-context conversation history is summarized away. The issue's existence does not depend on anything surviving in the LLM's context — it already lives in the database.
3. **Session ends:** "Landing the plane" protocol (per the internal `beads-analysis.md` workflow trace) requires `git pull --rebase && git push` to succeed as a hard gate before the session is considered closed — Dolt state and source-code state are pushed together, though on separate refs.
4. **Gap (days to weeks):** no agent is running. The issue sits `open`, unblocked or blocked per its dependency edges, doing nothing — this is the resting state of process memory: inert until queried, unlike a context window which actively decays.
5. **New session, different machine or agent:** `bd bootstrap` (fresh clone) or `bd dolt pull` (existing clone) fetches the latest Dolt history. `bd prime` fires via the `SessionStart` hook, giving the agent workflow context plus any `bd remember`-stored facts. The agent runs `bd ready` and sees `bd-7x2f` in the claimable frontier (assuming its blockers, if any, are closed) — full title, description, notes, and audit trail available via `bd show bd-7x2f --json`, with **zero loss of fidelity** relative to the moment it was created, because nothing about the issue was ever context-window-dependent.
6. **Resolution:** the agent (same or different one) claims it (`bd update bd-7x2f --claim` — atomic compare-and-swap, now lease-backed with a 5-minute default TTL and heartbeat renewal per the `[Unreleased]` work-lease feature), fixes the bug, and closes it with a typed reason: `bd close bd-7x2f --reason "fixed in bd-8a1c, added retry-with-backoff"`.
7. **30+ days later, closed and unreferenced:** `bd admin compact` becomes eligible to summarize it (Tier 1: 30 days closed, ~70% size reduction) — in `--analyze`/`--apply` mode, a human or agent reviews the summarization candidate before the original content is permanently discarded. If the issue is still actively referenced (e.g., another open issue's `discovered-from` edge points to it), it is presumably excluded from compaction eligibility per the "no longer actively referenced" qualifier in the docs, though the exact reference-liveness check isn't detailed in the fetched pages — flagged here as an open question rather than a confirmed guarantee.

The trace's key property: steps 1–6 involve **zero dependency on the LLM's context window** for the issue's survival — the failure modes that *do* threaten it are entirely at the sync/infrastructure layer (Dolt merge conflicts, daemon/version mismatches, remote misconfiguration), which is exactly where §4's practitioner complaints cluster.

## 4. Practitioner sentiment (works / doesn't-work, dated)

**Early positive trial reports, late 2025:**
- Reddit r/ClaudeCode, **2025-11-12/19** ("Update: I tried beads for 3 weeks..."): *"This tool has addressed my primary annoyance with AI coding—Claude's tendency to forget everything after compaction... Claude now logs bugs and issues as they arise during implementation... I don't need to interact with the CLI anymore."* Strongly positive, but note: this predates the Dolt migration (pre-v0.55, so the underlying store was still JSONL/SQLite at the time of this review) and is a 3-week trial, not longitudinal.
- HN, **2025-11-28** ("Beads – A memory upgrade for your coding agent," id 46075616): mixed launch reception. Skeptics: unclear differentiation from markdown files ("kept wondering what problem the system aims to address"); a sharp "dogfooding chaos" critique noting the repo's own README referenced a `.beads/beads.jsonl` "source of truth" file that didn't exist in the main branch amid "hundreds of commits in the past few days"; open questions about merge conflicts and whether agents would actually keep the tracker current or let it go stale like markdown; anthropomorphization skepticism toward "agents report enjoying" using it.
- HN, **2026-01-02** (id 46463757, comment thread on the same launch): a commenter predicts Beads is "clearly going to develop the same problem" it was meant to solve — i.e., skepticism that structured tracking avoids the staleness/drift failure mode of the markdown plans it replaces, rather than just relocating it.

**Operational fragility, Q1–Q2 2026 — the dominant complaint cluster:**
- HN, **2026-01-23** ("Gas Town's agent patterns..."): under high concurrency (17+ agent sessions), every `gt`/`bd` command spawning a `bd version` check triggers 5–7 git subprocesses each, producing 85–120+ concurrent git processes and blowing a 2-second timeout — a scaling failure specific to multi-agent fleets, not single-operator use.
- Reddit r/ClaudeCode, **2026-02-17** ("Am I an idiot for using Beads rather than PROJECT.md?"): *"The initial promise was that your updates would sync through regular merges, but that hasn't been the case... It creates an additional worktree within your working directory and relies on direct updates to that git branch, yet it fails miserably at managing that internal worktree."* Direct, dated complaint about sync/worktree failures — this is mid-migration-era Beads (v0.6x line), before the v1.0 Dolt-completion stabilization.
- Reddit r/codex, **2026-03-05** ("Using beads with Codex"): concrete embedded-Dolt operational failures — a version shipped with embedded Dolt that failed to build on macOS (missing C header), followed by a version that removed embedded Dolt and forced a self-hosted Dolt instance, plus port conflicts, unwanted auto-push of backups, and `bd dolt status` losing its connection and spawning a duplicate instance on another port. *"None of this should happen... I'm fed up with it. I stopped using beads."*
- dev.to, **2026-04-30** ("Beads Is Dead. Long Live the Linear CLI"): the most detailed abandonment writeup. Reports a background daemon managing SQLite-and-git sync throwing `DATABASE MISMATCH DETECTED` on every session start, silent divergence between local SQLite and git ("issues both exist and don't exist at the same time"), and a `bd sync` that silently stopped working when the tool picked the wrong git remote among several configured — discovered only when issues had already "vanished" between sessions. Concludes with a two-line retirement (`rm -rf .beads/`) in favor of Linear CLI + Claude Code's native ephemeral tasks. Note: this account's daemon/SQLite framing indicates it was using the pre- or early-Dolt-migration build, not current (v1.1.0) architecture — but it is a real, dated account of the exact "cache-vs-canonical-store divergence" failure mode the task brief asked about.
- GitHub, `steveyegge/beads` issue **#4259**, opened **2026-05-29**: `bd dolt pull` becomes unmergeable after a multi-machine upgrade — migration `0043` forked the `dependencies` table's primary key across clones because it used a per-clone-random `DEFAULT (UUID())`, so two clones that created the same edge diverged irreconcilably ("cannot merge because table dependencies has different primary keys"). This is a first-party-acknowledged, real merge-safety defect — and per CHANGELOG entries dated through **2026-06/07**, it was subsequently fixed with deterministic edge-derived primary keys, a remote-migrate prevention gate, and per-migration content-hashing for skew detection, landing in the v1.1.0 line. A textbook case of a JSONL/Dolt-adjacent "merge conflict" complaint that was real, dated, and then engineered away — not evidence the architecture is unfixable, but strong evidence it needed real fixing.
- GitHub issues list snapshot, **2026-05-30**: multiple concurrent open bugs in the v1.0.4/1.0.5 window — auto-import from JSONL overwriting live Dolt data on every server-mode write, a JSONL-fallback write leak when the Dolt marker file was missing, and reentrant Go-runtime crashes during search — consistent with a tool still shaking out real bugs in its production-hardening phase, not a mature, settled substrate.

**A more settled, mixed-but-positive picture by mid-2026:**
- Note.com (Japanese), **2026-05-13**: v1.0.4-era review frames Beads as "an external brain for the agent," positioning `bd ready` as the核心 (core) mechanism and arguing structuring beats growing MEMORY.md indefinitely — "the more text-based external memory grows, the more the agent has to read." Reports 23.6k GitHub stars at the time.
- LinkedIn writeup, cited via Perplexity, **2026** (exact date not independently pinned but corroborated as recent): praises `bd remember`/`bd dep add`/`bd prime` for restoring "the agent's brain after a context reset," but flags real friction — raw pasted content can produce ugly auto-generated titles requiring `bd lint`, and `bd prime` loads *all* saved memories up front "whether or not they are relevant" (the exact gap the `--max-memories`/`--max-memory-chars` caps, confirmed live in current docs, were built to address).
- llbbl.blog, **2026-06-27** ("Six months with git-native issue..."): the most considered longitudinal account. Verdict: Beads is "not bad, it's specialized" — still the right tool for personal/local-only repos with no remote and no ceremony, and the v1.0 embedded-Dolt move strengthened the git-for-your-database model as intended, but for the author's broader day-to-day agent work it lost out to Claude Code's built-in ephemeral session tasks (for short checklist-style work) plus direct GitHub/GitLab issue writes via custom skills (for durable tracking, on the theory that "the remote tracker is the source of truth" beats a separate local system). This is the closest thing in the evidence base to a calm, non-adversarial "graduated off it" account rather than an angry abandonment.
- CHANGELOG, v1.1.0 release notes, **2026-07-04**: Yegge's own team frames the release as explicitly reliability-focused — "it repairs the v52/v53 drift classes that broke real-world rc.1/rc.2 upgrades, makes an interrupted migration recoverable in-tool instead of a dead end" — a first-party, dated admission that recent migrations had been breaking real deployments.
- Yegge's own framing, talk dated **2026-07-06** (per secondary summary, "You'll Never Write Code the Same Way Again"): argues forgetting is a *feature requirement*, not a bug — memory "has to be growing constantly" but also "forgetting constantly," using a "dementia" metaphor for what happens to agent memory that never prunes. The same secondary source paraphrases him conceding the (now-superseded) "Git + JSONL + SQLite" description as "architecturally sound" while the implementation "has been plagued by critical bugs requiring constant fixes" — consistent with the GitHub issue and CHANGELOG evidence above, and a rare case of a tool's own creator publicly corroborating the practitioner complaints about it.

**Does the "issue tracker solves agent memory decay" claim hold up in third-party use?** Partially, and with a clear pattern across the dated evidence: the **process-memory value proposition holds up well** — no practitioner account in this survey disputes that a queryable, dependency-aware issue graph beats a markdown TODO file for tracking long-horizon work state, and several (2025-11, 2026-05 Japanese review, 2026-06 llbbl) explicitly credit it with reducing repeated re-explanation after compaction. What repeatedly *doesn't* hold up, dated across five separate independent accounts spanning **2026-02 through 2026-05**, is the **infrastructure underneath it** — Dolt embedding, sync/merge correctness, and daemon reliability — which is exactly the kind of complexity a genuinely simpler (e.g., plain-git-diffable-markdown) substrate would not introduce in the first place. Whether agents keep the tracker updated without nagging gets a genuinely positive, if thin, answer (2025-11 and 2026-03 accounts both report agents proactively logging discovered work); the friction is not "agents won't use it," it's "the sync layer under it breaks."

## 5. Verdict — strengths, failure modes, transferability

**Strengths:**
- **The process-memory thesis is real and Beads is the strongest evidence for it in this survey.** It cleanly separates "what state is the work in" (issue graph, status, claims, close-reasons) from "what do I know" (`bd remember`), and the fact that even a tool marketed monolithically as "memory for coding agents" ended up needing two structurally different subsystems is itself a validating data point for treating process memory as its own type in the E1 spec, not a special case of episodic or semantic memory.
- **`bd ready`'s blocker-aware ready-work query is the single most portable idea here.** Converting a dependency graph into "here is the exact claimable frontier right now" is a genuinely different and more useful read than "list all open items" — it does the blocked/unblocked reasoning so the agent (or a script) doesn't have to re-derive it from a flat list every session.
- **Typed close-reasons and typed graph edges (`supersedes`, `duplicates`, `discovered-from`) give process memory a real vocabulary for *how* work concluded**, not just that it did — directly analogous to, and a validating cross-reference for, MetaSystem's own DD-44 supersession semantics already in place for Design Decisions.
- **The compaction design's human/agent-in-the-loop default (`--analyze`/`--apply` over `--auto`) is the right instinct** — Beads' own docs steer away from unsupervised summarize-and-delete, which matches this engine's human-gate posture more than it might first appear.

**Failure modes (all dated above, §4):** the overwhelming majority of practitioner pain traces to the **Dolt/sync infrastructure**, not the issue-graph model itself — daemon/database mismatches, embedded-Dolt build failures, port conflicts, unmergeable primary-key forks across clones, and multi-agent-scale process explosions under concurrent `bd version` checks. Notably, **every severe complaint in this survey comes from a multi-writer or multi-machine context** (multiple agents, multiple clones, a shared remote); no account describes the single-writer/embedded-mode path failing in this way. That is the load-bearing distinction for transferability.

**Transferability to a markdown+git, single-operator, human-gated engine:**
- **The E1/E2 boundary this implies:** Beads' own internal split (issue graph = process/task state; `bd remember` = semantic facts) maps directly onto MetaSystem's existing separation of `project-management/implementation-backlog/` + `project-management/design-decisions/` (E2 — task/governance layer, already status-bearing markdown with frontmatter, already has DD-44 supersession) from `knowledge/` and `research-findings/` (E1 — the knowledge layer). Beads doesn't argue these should be unified into one physical store; it argues they should be **conceptually distinct with different write/decay rules**, which the engine already has. The one gap Beads highlights that the engine doesn't yet have an equivalent for is `bd ready`'s computed-frontier query — IB items currently don't have a scripted "what's unblocked right now" read distinct from a human/agent scanning frontmatter status fields by hand. That's a legitimately portable, low-cost idea (a ripgrep/frontmatter-filter script, not a database) worth flagging for E2 design, independent of adopting anything else from Beads.
- **Git-as-sync-substrate does not straightforwardly fit a single-operator system, and Beads' own evidence says so.** Beads treats git only as a transport for opaque Dolt refs (`refs/dolt/data`), not as the diffable medium for the data itself — the opposite of MetaSystem's markdown+frontmatter-directly-in-git approach, where every governance write is a plain, human-readable git diff. Every severe Beads failure mode in §4 originates in that opaque-sync layer (daemon/database mismatch, unmergeable clones, remote misconfiguration) — exactly the class of problem a directly-git-diffable plain-file store structurally avoids, because there is no separate database to fall out of sync *with* git. Given DD-44/DD-55/DD-56's existing commitment to markdown-in-git as the governance substrate, and that this is explicitly a **single-operator** system (no concurrent-agent-write contention that Dolt's cell-level merge and work-leases exist to solve), adopting Beads' storage substrate would import its dominant failure mode to buy concurrency guarantees the engine doesn't need. The lesson to take is the **query pattern** (ready-work, typed edges, typed close-reasons), not the **plumbing** (Dolt, embedded databases, sync daemons).
- **The decay mechanism doesn't transfer cleanly either, and arguably shouldn't.** Beads' `bd admin compact` performs *permanent, lossy* summarization of closed issues to control local database size and prime-time token cost — a real constraint for a tool that wholesale-injects state at every session start. MetaSystem's git history and `archive/` folders already provide effectively free, lossless scrollback, because nothing in `archive/` is loaded into context unless a query specifically asks for it (Librarian-style on-demand retrieval, not wholesale injection). The cost Beads is solving for (bounded local-DB size + bounded `bd prime` token budget) doesn't apply the same way to a system that reads on demand rather than injecting wholesale — so the "permanent graceful decay" pattern is a Beads-specific answer to a Beads-specific constraint, not a general lesson for this engine's process-memory design.
