# Archon — Workflow-Engine Memory Architecture

Dossier for the E1 memory-architecture spec's cross-framework survey (Track B). Scope: `coleam00/archon`, the watched-library agent framework tracked in `watched-libraries/archon.md` — a self-hostable, multi-provider workflow engine for AI coding agents (YAML DAGs, git worktree isolation, Slack/Telegram/GitHub/Discord/Web/CLI adapters). Written 2026-07-16. Internal grounding (repo-analysis + registry entry) is current as of the 2026-07-13 v0.5.0 refresh; external grounding is GitHub issues/discussions dated April–July 2026, per the recency rule.

---

## 1. Snapshot

Archon is **not** a conversational-agent memory framework — it is a durable workflow orchestrator whose "memory" is almost entirely **run/session state**, not long-term agent knowledge. This matters up front because it reframes what "memory" even means here relative to the other Track-B dossiers.

**Critical scope fact, external-only (not in the internal analysis):** the project's original identity, before the name and codebase were repurposed, *was* a knowledge-base/RAG memory tool — a Python agent (Supabase + pgvector) that crawled documentation and answered questions about frameworks like Pydantic AI and LangGraph. On **2026-04-07**, maintainer Cole Medin announced a complete rewrite (GitHub issue [#957](https://github.com/coleam00/Archon/issues/957)): *"The Python-based Archon (task management + RAG tool) has been archived... Is this a breaking change? Yes — this is an entirely different product... There is no migration path between them."* The old code survives read-only on the `archive/v1-task-management-rag` branch. **The version this dossier and the internal repo-analysis describe (v0.3.2 → v0.5.0) has no RAG/semantic-retrieval/knowledge-base layer at all.** Anyone approaching Archon expecting vector-search agent memory (a reasonable expectation given the name and prior reputation) will find none — this is a load-bearing fact for the survey, not a gap in the internal analysis.

What Archon v0.5.0 *does* carry, memory-wise: in-run session continuity across DAG nodes, an event-sourced/immutable run-history database, typed output artifacts for cross-node handoff, and one concrete two-layer (committed-constitution + personal-rolling-memory) pattern for a scheduled autonomous agent (the maintainer-standup). All of it is DB- or file-backed state management, not retrieval-augmented recall.

**Currency:** internal analysis (`archon-analysis.md`) fresh at v0.5.0 / commit `dad62d8`, dated 2026-07-13. External research below draws on GitHub issues filed 2026-04-07 through 2026-07-14 (two days before this dossier), plus the registry's own change log.

## 2. Memory model by type

### Working / short-term memory (in-run DAG/session state)
**Substrate:** the DAG executor's in-process state — a single linear cursor `lastSequentialSessionId` that tracks "the most recent sequential AI node's session," `$nodeId.output` variable substitution (schema-strict when the producing node declares `output_format`), and typed output sidecars (`$ARTIFACTS_DIR/nodes/<id>.md` + `<id>.meta.json`) written when a node declares `output_type`.

**Write path:** automatic on every node completion; the cursor is overwritten unconditionally by any completed sequential AI node — including `context: fresh` ones, which is itself a bug class (below). Loop nodes additionally bridge `$LOOP_PREV_OUTPUT` (the prior iteration's cleaned output) into each fresh-context iteration.

**Injection/recall:** the next sequential AI node resumes `lastSequentialSessionId` automatically unless it declares `context: fresh`. This is a *blind* resume — until mid-2026 it did not check whether the upstream node used the same AI provider.

**Consolidation/reflection:** none. It is a raw pointer, not a merged or summarized state.

**Decay/forgetting/supersession — two dated, verified bugs:**
- **Provider-blind cursor, closed [#2072](https://github.com/coleam00/Archon/issues/2072), filed 2026-07-10.** "DAG sequential session threading is not provider-aware — nodes crash with 'No conversation found with session ID' at provider boundaries." Root cause: the cursor is set without recording which provider produced it and consumed without comparing providers, so a `codex → claude` edge crashes (Claude rejects the foreign session id) while `claude → codex` silently "works" (Codex ignores the foreign id) — an asymmetric failure that makes the bug hard to localize. Contrast: the **persisted** cross-run session lookup (`workflow_node_sessions`, below) already keys on provider and was unaffected — only the in-run cursor lacked the guard.
- **Stale interactive-loop session, closed [#1208](https://github.com/coleam00/Archon/issues/1208), filed 2026-04-14.** Interactive loop nodes crashed with `error_during_execution` on the human-approved iteration 2+ because the resumed session had gone idle (minutes to hours) while waiting for a human gate and had expired server-side by the time the loop resumed it. Maintainer coleam00's own partial-repro comment (2026-04-17) notes the session he tested against was "not yet expired — only ~10 minutes old" and succeeded — i.e., the bug is timing/environment-sensitive, not deterministic, which is exactly the kind of failure mode that's hard to catch in CI.
- **Unshipped fix for the underlying design gap, open [#2099](https://github.com/coleam00/Archon/issues/2099), filed 2026-07-14 (two days before this dossier).** A contributor proposes an *addressable* cursor (`context: resume: <nodeId>`) because the current linear model makes a natural pattern — build context in node A, fork a fresh isolated side-quest to node B, then **return to A's session** with B's result folded in — inexpressible: "Today prompt1-continue resumes B (the fresh node stole the cursor)." Workarounds cited as currently necessary: routing the interrupt through a non-AI node (accidental workaround, since code nodes don't carry a session id), reordering nodes, or splitting into two runs with `persist_session` (heavyweight).

### Episodic memory (specific past runs/events)
**Substrate:** SQLite/Postgres. Sessions are event-sourced and **immutable** — a session is never mutated in place; state transitions (e.g., planning → execution) deactivate the current session and create a new one linked by `parent_session_id`. A `workflow_events` table records every event in a run (including `loop_iteration_started/completed/failed`). A separate `workflow_node_sessions` table implements opt-in **cross-run** session persistence, keyed `(workflow_name, node_id, scope_key, provider)` — this is provider-aware, unlike the in-run cursor above.

**Write path:** `persist_session` (node-level) or `persist_sessions: true` (workflow-level) opts a node's session into cross-run continuity; otherwise sessions are scoped to a single run. All writes are appends to the event/session chain, never overwrites.

**Injection/recall:** a later run of the same workflow (matching scope key + provider) resumes the persisted session automatically; explicit reset is available via `/workflow reset-sessions`.

**Consolidation/reflection:** none automatic — the immutable chain is the raw audit log, not a summarized memory. Reconstructing "what happened" means walking the chain.

**Decay/forgetting/supersession — the DB-state-vs-execution-truth gap, one dated incident with real production impact:**
- **False-orphan mass-failure, closed [#1216](https://github.com/coleam00/Archon/issues/1216), filed 2026-04-14.** Every `archon serve` startup unconditionally flipped **all** `status='running'` rows to `status='failed'` via `failOrphanedRuns()` — including runs actively executing in a different process — with no PID filter, no liveness check, no scope filter. The between-layer status check in the DAG executor then detected the flip and aborted the still-successfully-running workflow with exit code 1, even though every node had completed. The report notes this was "the same class of bug already fixed for the CLI side" (a code comment at the CLI call site documents the CLI's own startup orphan-cleanup being deliberately removed because "running it on every CLI startup killed parallel workflow runs") — the server side simply hadn't received the same fix. **This incident is the cited precedent (issue #1216) behind Archon's own codified CLAUDE.md governance principle**, captured in the internal KB as [[no-autonomous-lifecycle-mutation-principle]]: a process that cannot distinguish "running elsewhere" from "orphaned" must not mark work failed on a staleness guess — it must surface the ambiguity to a human with a one-click action.
- **Silent local-state destruction, closed [#1516](https://github.com/coleam00/Archon/issues/1516), filed 2026-05-01.** For repos registered under `~/.archon/workspaces/` (chat-driven, non-worktree mode), `syncWorkspace` hard-resets the shared `source/` clone to `origin/<default>` on **every chat message**, on the assumption that `source/` is a passive mirror. But `archon-fix-issue` commits directly to `source/` in that same mode. The two collide: a fix branch gets created and committed, then erased by the next chat-triggered sync — reflog evidence in the report shows five consecutive silent resets destroying a real fix commit, recovered only because it happened to have been pushed already. This is episodic memory (a git commit representing completed work) destroyed by an unrelated subsystem's stale assumption about ownership of that state.

### Semantic memory (facts, rules, direction)
**Substrate:** `CLAUDE.md` (979 lines — absorbed a formerly separate 11-file path-scoped `.claude/rules/` layer between v0.3.2 and v0.5.0) plus a near-mirror `AGENTS.md` (964 lines) for non-Claude harnesses; `.archon/maintainer-standup/direction.md`, a committed north-star document ("what Archon IS / IS NOT") consumed by a scheduled workflow.

**Write path:** entirely human-authored, git-committed. `direction.md` is explicitly framed as a constitution: any automated decline recommendation from the standup workflow must **cite a specific clause** (e.g., "cite `direction.md §single-tenant-per-install`") — changing direction is a reviewable diff, not a prompt edit.

**Injection/recall:** `CLAUDE.md`/`AGENTS.md` load in full at session start per harness; `direction.md` is read by the maintainer-standup workflow to classify open PRs into P1–P4 priority bands.

**Consolidation/reflection:** one deliberate, human-directed consolidation event — the rules-layer collapse (11 files → 1) — but no ongoing automatic sync between the two mirror files it produced.

**Decay/supersession — drift is already observable, and recurring:** the internal analysis flags that `CLAUDE.md` was updated to a new "governed agentic automation engine" product positioning while `AGENTS.md` still opens with the superseded "single-developer tool" framing — drift that appeared within the same three-month window as the consolidation meant to reduce duplication-maintenance cost. External confirmation this is not a one-off: **open issue [#2103](https://github.com/coleam00/Archon/issues/2103), filed 2026-07-14** (the same day as #2099, two days before this dossier) — "docs: stale engine claims in CLAUDE.md, docs-web, and the workflow-builder default" — a fresh instance of the identical drift class, still unresolved as of writing.

### Procedural memory (skills, workflows, agents)
**Substrate:** 14 skills (`.claude/skills/`), 13 Claude agent definitions + 3 Copilot mirrors, 20 default YAML workflows, 36 `.archon/commands/` prompt files, a provider registry.

**Write path:** entirely human-authored and git-versioned, same posture as `CLAUDE.md`. One meta-layer exception: `archon-workflow-builder` is a shipped default *workflow* that scans a codebase, extracts an intent JSON, generates a new YAML workflow, and validates it — a workflow that authors workflows. But its output is a reviewable artifact saved to disk, not an autonomously deployed change; this is user-invoked meta-authoring, not the run history teaching itself a new procedure.

**Explicitly not handled:** no native mechanism was found (internal analysis or external search) for repeated run outcomes, events, or session history to automatically graduate into a new skill, workflow, or agent definition. The closest analog, `archon-workflow-builder`, still requires a human to invoke it and review the output.

**Decay/consolidation:** none — procedural artifacts are git-versioned and human-governed, structurally identical to the semantic layer above.

## 3. Lifecycle trace — one AI-node session id, end to end

1. **Node N executes** (a sequential AI node, provider = Claude). On completion, the executor sets the in-run cursor: `lastSequentialSessionId = <N's session id>` — unconditionally, with no record of which provider produced it (working memory, §2).
2. **Node N+1 executes**, depends on N, does not declare `context: fresh`. It resumes `lastSequentialSessionId` automatically. If N+1 also runs on Claude, this works. If N+1 runs on Codex, it silently starts fresh instead of resuming (Codex ignores the foreign id) — no crash, but the "resume" silently didn't happen. If a later node N+2 switches *back* to Claude and tries to resume a Codex-produced cursor value, it crashes with `error_during_execution — No conversation found with session ID` (this exact asymmetry is [#2072](https://github.com/coleam00/Archon/issues/2072), closed after being filed 2026-07-10).
3. **If the workflow also declares `persist_session: true` on this node**, the session additionally gets written to `workflow_node_sessions`, keyed `(workflow_name, node_id, scope_key, provider)` — this copy *is* provider-safe (episodic memory, §2), unlike the in-run cursor.
4. **If the node is inside an `interactive: true` loop and pauses for human approval**, the session sits idle server-side while waiting on `/workflow approve`. If the human takes long enough (observed: session valid at ~10 minutes, invalid by the time of the reported crash), resuming on approval fails with the same `error_during_execution` symptom, for a different root cause (staleness, not a provider mismatch) — [#1208](https://github.com/coleam00/Archon/issues/1208), filed 2026-04-14.
5. **Meanwhile, at the run level**, the row for this workflow run sits at `status='running'` in the DB for the run's duration. If any `archon serve` process restarts anywhere during that window, pre-fix behavior (issue [#1216](https://github.com/coleam00/Archon/issues/1216), filed 2026-04-14) would unconditionally flip the row to `'failed'`, and the DAG executor's next between-layer status check would then abort the still-succeeding run. Post-fix, this class of ambiguity is meant to surface to a human via a one-click action rather than auto-resolving — the codified [[no-autonomous-lifecycle-mutation-principle]].
6. **An operator can force a reset** of persisted (not in-run) session state via `/workflow reset-sessions` if a workflow needs to start clean.
7. **What's still missing, as of 2026-07-14:** there is no way for a *later* node to explicitly say "resume node N's session, not whatever the linear cursor currently points to." Issue [#2099](https://github.com/coleam00/Archon/issues/2099) proposes `context: resume: <nodeId>` to fix exactly this — open, unshipped, filed the same day as the CLAUDE.md drift report (#2103), i.e., two live, unresolved gaps in the memory/context layer as of this dossier's writing.

## 4. Practitioner sentiment (dated)

**2026-04-07 — the RAG/knowledge-base identity is deliberately cut, no ambivalence expressed by the maintainer.** Cole Medin's own rewrite announcement (issue [#957](https://github.com/coleam00/Archon/issues/957)) frames it as a clean break: *"this is an entirely different product... There is no migration path."* No dated user pushback specifically mourning the loss of RAG/knowledge-base memory was found in this pass — the visible discussion (#952, #957) is about migration mechanics, not about missing the memory feature itself.

**2026-04-14 — a same-day cluster of two session/run-state reliability bugs.** [#1208](https://github.com/coleam00/Archon/issues/1208) (stale interactive-loop session) and [#1216](https://github.com/coleam00/Archon/issues/1216) (false-orphan mass-failure) were both filed the same day, both squarely in the session/state-liveness space, both later closed with fixes. This cluster lands right at the point the internal registry's upstream-delta tracking (v0.3.2→v0.5.0) marks loop nodes as newly "first-class" — consistent with state/session reliability being a rough edge that surfaced as loop functionality matured, not a long-standing background issue.

**2026-04-17 — maintainer partial-repro signals the bug is timing-sensitive.** coleam00's own comment on #1208 reports a session that was "only ~10 minutes old" and succeeded, i.e., the staleness window is environment/timing-dependent — the kind of bug that under-reproduces in quick manual testing and over-reproduces in real deployments with slower human response times.

**2026-05-01 — a deployment-mode-specific data-loss report.** [#1516](https://github.com/coleam00/Archon/issues/1516) comes from a user running Archon as a background chat-driven service (not interactive CLI), where the collision between `fix-issue`'s direct commits and `syncWorkspace`'s per-message hard-reset destroyed work. The report explicitly frames this as "the deeper problem behind #1273" (an earlier, narrower patch that only redirected the reset target without fixing the underlying ownership conflict) — i.e., a recurring class of bug, not a one-off.

**2026-06-30 through 2026-07-10 — a recurring six-week tail of the same session-threading root class.** [#2050](https://github.com/coleam00/Archon/issues/2050) ("Inter-node session: a later AI node fails with 'No conversation found with session ID'"), [#2064](https://github.com/coleam00/Archon/issues/2064) (Pi provider: extension-registered models fail on 2nd+ DAG node), and [#2072](https://github.com/coleam00/Archon/issues/2072) (the provider-blind-cursor root cause, filed 2026-07-10) all recur in the same six-week window — all closed, but the recurrence suggests the session-threading model is being hardened incrementally, case by case, rather than fixed structurally in one pass.

**2026-07-14 — two live, open gaps acknowledged by the project itself, two days before this dossier.** [#2099](https://github.com/coleam00/Archon/issues/2099) is a contributor-filed feature request that explicitly names the linear-cursor working-memory model as insufficient for a "natural" multi-agent context-choreography pattern. [#2103](https://github.com/coleam00/Archon/issues/2103) independently reports the CLAUDE.md/AGENTS.md/docs-web drift the internal repo-analysis had already flagged structurally. Both are still open as of this writing — the most current available signal is that Archon's own contributors see both the working-memory cursor model and the dual-file semantic layer as unfinished.

**General reception (positive, but not about memory specifically).** Growth and framing are strongly positive: ~17,906 GitHub stars reported in April-2026 coverage (AgentConn blog review, Medium coverage), rising to ~22.9k by 2026-07-13 per the internal registry — and the "deterministic harness" pitch (raw AI PR acceptance ~6.7% vs. harnessed ~70%, per widely-repeated framing) drives most of the enthusiasm found. No dated practitioner praise specifically calling out Archon's session/memory architecture as a strength was found in this pass; the dated evidence that exists in that specific area skews toward the reliability bug reports above.

## 5. Verdict

**Strengths — transferable patterns:**
- **Typed, schema-strict handoff contracts.** `$nodeId.output.field` is validated against the producer's declared `output_format`, and `output_type` sidecars (`$ARTIFACTS_DIR/nodes/<id>.md` + `<id>.meta.json`) let downstream consumers locate artifacts by declared type instead of filename convention. Directly portable to any markdown+git pipeline (e.g., the engine's own research-loop → identify-artifacts → extract-artifacts chain) that currently relies on filename guessing.
- **direction.md + profile/state/briefs, the two-layer memory for a scheduled autonomous agent.** A committed, versioned constitution (`direction.md`, decline recommendations must cite a clause) paired with personal, gitignored, rolling memory (`profile.md`, `state.json`, last-3 `briefs/` read back into the next run). This is the single most directly reusable pattern in this dossier — it is structurally close to the engine's existing PROGRESS.md (forward control) + HISTORY.md (episodic ledger) split, and validates that shape for any future scheduled/autonomous IL skill that needs consistent judgment across unattended runs.
- **The no-autonomous-lifecycle-mutation principle**, codified with a cited real incident (#1216), generalizes cleanly: *a process that cannot tell "still running elsewhere" from "abandoned" must surface the ambiguity to a human rather than auto-resolve it.* Directly relevant to any future MetaSystem mechanism that infers liveness from stored state (e.g., a lock file for an in-flight `/self-improve` promotion) rather than an actual liveness check.
- **Event-sourced, immutable run/session history** (deactivate-and-replace via `parent_session_id`, full `workflow_events` log) is a clean audit-trail pattern, though largely redundant with what git commit history already provides at MetaSystem's single-operator scale.

**Failure modes — cautionary evidence:**
- **A single unaddressable linear cursor for cross-node working memory is a recurring, multi-month bug source** (3+ distinct incidents, April–July 2026) and the project's own contributors now consider it a design gap, not just implementation bugs (open #2099). Caution against any design that threads "the current session/context" through a pipeline via one mutable pointer without provenance (which provider/actor produced it) or addressability (which upstream step to resume).
- **Inferring liveness from stored state alone caused real false-forgetting** (#1216) — DB truth and execution truth diverged, and the DB was trusted. Any MetaSystem mechanism that persists "in progress" state to a file/frontmatter field needs the same caution: don't auto-expire or auto-fail based on staleness heuristics alone.
- **Duplicated semantic-memory files drift within months, even when the duplication was a deliberate, reasoned decision.** The CLAUDE.md/AGENTS.md split was chosen specifically to serve two harness audiences, and it still drifted enough to generate its own bug report (#2103) roughly three months later. Direct cautionary evidence for MetaSystem's own hard constraint against duplicated context (workspace token-economy rule) — even a well-intentioned second "source of truth" file needs an explicit sync mechanism, not good intentions.
- **No RAG/semantic-retrieval layer exists in the current architecture at all** — and this was a deliberate subtraction (the April 2026 rewrite), not an oversight. Weak but real evidence that a popular, actively developed framework found structured workflow/file state sufficient for its memory needs once the problem was reframed away from "search over a knowledge base" — consistent with, and mildly corroborating for, the engine's own local-first, markdown+git-over-vector-DB posture. Not proof this generalizes, but a relevant data point for E1's own DB-vs-files decision.

**Bottom line for E1 transferability:** Archon has almost nothing to offer on *semantic/long-term* memory (it deliberately has none) but is a rich, dated, incident-grounded source on the failure modes of *working/episodic* memory in a multi-step, multi-provider, human-gated pipeline — exactly the shape closest to what E1 needs to get right for a markdown+git, single-operator engine. The direction.md/profile/briefs pattern and the no-autonomous-lifecycle-mutation principle are the two pieces worth carrying forward directly; the linear-cursor and dual-file-drift failures are worth carrying forward as things to avoid.
