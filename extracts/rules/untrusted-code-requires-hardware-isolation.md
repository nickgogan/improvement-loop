# Untrusted Code Requires Hardware Isolation

**Source:** [[sandbox-architecture-by-threat-model-microvm-vs-container]]
**Form:** rule
**Extraction date:** 2026-07-19

## Condition

A code-execution sandbox is being designed, provisioned, or selected for an agent (or any automated process) that will run code the operator did not author and has not reviewed — most commonly, code generated on the fly by a language model. This rule fires whenever the isolation mechanism backing such an environment is chosen or re-evaluated.

## Action

**Required:** Route untrusted, model-generated code execution to an isolation mechanism that provides a hardware-enforced boundary — a dedicated guest with its own kernel, running in a separate CPU privilege context from the host — not a boundary implemented purely inside the host kernel's namespace/cgroup layer. Reserve shared-kernel container isolation for code the operator actually trusts (human-authored, reviewed, or otherwise not exposed to adversarial or unpredictable input), where the lower cost, faster startup, or easier persistence is worth the reduced isolation guarantee.

**Forbidden:** Choosing an isolation mechanism based on cost or latency before explicitly answering "is this code untrusted?" Routing untrusted, model-generated code to a shared-kernel container — or to a user-space kernel layer alone — on the assumption that it is "good enough," when the code's origin is adversarial or unreviewed.

## Boundary

Enforced at sandbox architecture and provisioning time — the point where the isolation mechanism backing a code-execution environment is chosen and implemented. Not a runtime check on individual executions; a design-time architectural constraint. Re-enforced whenever the trust classification of the code a given environment is scoped to run changes — for example, an environment originally provisioned for human-reviewed code that is later repurposed to also execute raw model output.

## Enforcement

- **Mechanism:** The sandbox architect or reviewer answers the diagnostic question — does this environment execute code that is untrusted (model-generated, unreviewed, or otherwise adversarial-source)? If yes, the environment's isolation mechanism must be a hardware-virtualized guest with its own kernel.
- **Check (observable):** Inspect the provisioning configuration for the environment: is the guest boundary a hardware-privilege boundary (separate kernel, separate CPU privilege context) or a namespace/cgroup boundary (shared host kernel)? Cross-reference the answer against the trust classification of the code the environment is scoped to run.
- **Violation response:** An untrusted-code workload found running in a shared-kernel sandbox is a security defect — a container escape from that boundary is a realistic compromise path — and must be re-routed to hardware isolation rather than accepted as a cost tradeoff.

## Rationale

The choice between isolation mechanisms is a threat-model decision, not a pricing or performance decision. Progressively cheaper isolation mechanisms remain reachable in ways that matter once code is adversarial: an unisolated forked process can attack the host kernel directly; namespace/cgroup containers isolate resources but every container still shares the host kernel, so a single kernel exploit compromises every co-located workload; a user-space kernel implementation raises the bar by requiring a two-step compromise chain, but its own supporting processes still run on top of the shared host kernel and remain a chainable target. Only a hardware-virtualized guest — its own kernel, running in a separate CPU privilege context from the host — keeps the host protected even if the guest is fully compromised. Independent production teams converge on this same threat-model framing rather than optimizing for cost or cold-start latency first, and report that starting with a cheaper isolation mechanism and upgrading only after it proves insufficient is a common but costly path.

## Failure Modes

- **Latency- or cost-first selection.** Choosing the cheaper, faster isolation mechanism first and only upgrading after an incident makes the threat-model question implicit instead of explicit, and defers a security decision to whichever mechanism looked cheapest at provisioning time.
- **Hardware isolation applied where it isn't required.** Applying this rule to trusted, human-authored code that needs to persist state across many interactions produces unnecessary cost and complexity — sessions may need to restart from scratch, breaking the persistence the workflow depends on. This rule applies only when the code is untrusted; trusted workflows should choose their isolation mechanism based on their own requirements (persistence, cost, speed).
- **Assuming an intermediate isolation layer is sufficient.** A user-space kernel implementation narrows, but does not close, the gap to hardware isolation — it still ultimately depends on the shared host kernel underneath it and can itself be chained through in a compromise.
- **Mis-scoped trust classification.** An environment originally provisioned for trusted, human-reviewed code that is later repurposed — without re-evaluation — to also execute raw model output inherits an isolation mechanism that no longer matches its actual workload.

## Contract

### Preconditions
A code-execution sandbox is being designed, provisioned, or selected for an agent or automated process that will run code the operator did not author and has not reviewed — most commonly code generated on the fly by a language model. The provisioning system supports more than one isolation mechanism (at minimum, shared-kernel containers and some form of hardware-virtualized or dedicated-kernel guest).

### Invariants
Untrusted or model-generated code execution is never routed to a shared-kernel isolation mechanism (namespace/cgroup containers, or anything lighter) as its sole boundary. Untrusted code execution is routed to a hardware-enforced isolation boundary — a dedicated guest kernel running in a separate CPU privilege context from the host. Trusted, human-authored or human-reviewed code that needs persistent state across turns may use shared-kernel containers; this rule does not require hardware isolation for code the operator actually trusts.

### Governance
Owner: whoever designs or provisions the code-execution sandbox architecture for a given environment. The threat-model question — is the code this environment will run untrusted? — is answered explicitly at design time and documented alongside the isolation mechanism chosen, not inferred after the fact from cost or latency preferences.

### Recovery
If untrusted code execution is found already routed to a shared-kernel sandbox: treat this as a security defect — a container escape from that boundary is a realistic compromise path, not a hypothetical one — and re-route to hardware isolation rather than accepting the exposure as a cost tradeoff. If a stateful workflow is forced onto hardware isolation and loses needed persistence: re-examine whether the code is actually untrusted; if it is not, move the workflow to a container; if it is, accept the persistence cost as a consequence of the safety requirement rather than relaxing the isolation boundary.
