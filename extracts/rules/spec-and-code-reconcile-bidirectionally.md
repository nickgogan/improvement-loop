# Spec and Code Reconcile Bidirectionally on Every Change — Drift-Prevention Rule

**Source:** [[specification-as-governance-fourth-enforcement-philosophy]]
**Form:** rule
**Extraction date:** 2026-04-27

## Condition

The project maintains specifications alongside implementation code — architectural decisions, behavioral contracts, conformance tests, design documents, or equivalent. The project has stated (in policy, convention, or skill definition) that the spec is the source of truth, or at minimum that spec and code must not silently disagree.

A change is being prepared that touches the spec, the code, or both.

Scope of application: any change that crosses the boundary between authored work and shared state — a commit, a merge, a deploy. Pre-merge experimentation on a personal branch is out of scope; the rule fires at the gate where the change becomes shared.

## Action

**Required:** Every change that touches the spec must reconcile the code in the same change (the code now conforms, or carries a tracked, time-bounded reconciliation marker). Every change that touches the code in a way that diverges from the spec must reconcile the spec in the same change (the spec is updated to reflect the new authoritative behavior). When a change is purely on one side (spec-only or code-only), the change must include an explicit assertion that the other side is provably unaffected — otherwise it counts as a divergence.

**Forbidden:** Merging or deploying a change where spec and code disagree without an explicit reconciliation marker. Carrying "we'll reconcile later" as an unwritten convention. Treating spec drift as a maintenance task to be done someday — drift compounds, and "later" arrives never.

## Boundary

Enforced at every gate where a change becomes shared — commit-to-shared-branch, merge-to-main, deploy. Applies project-wide to any surface area that has a corresponding specification.

Out of scope: surface areas with no specification (the rule fires only where a spec exists), purely mechanical changes that touch neither logic nor spec (formatter output, lockfile regeneration), and pre-merge personal-branch experimentation.

## Enforcement

- **Mechanism:** A change-record check (PR review, pre-commit hook, CI step) reads the change's spec touches and code touches together. If both sides change, verify they resolve to a coherent state. If one side changes, verify the other side is unaffected (test coverage, conformance suite passes, or explicit assertion in the change record). If a reconciliation marker is used, verify the marker has a stated deadline and is tracked.
- **Check (deterministic):** For every change `C` reaching a shared-state gate: `spec_touched(C) ⟹ code_state_after_C conforms_to spec_state_after_C`, and vice versa, OR `C` carries a marker `M` such that `M.deadline > now AND M.tracker_id != null`. Pure-spec or pure-code changes pass iff the unchanged-side proof is present (test pass, conformance run, or explicit assertion).
- **Violation response:**
  - *Spec-and-code disagreement at the gate, no marker:* gate blocked; the change must reconcile or add a marker before merge.
  - *Marker without deadline or tracker:* gate blocked; the marker is theater, not a real reconciliation plan.
  - *Marker accumulation past cap:* feature work on the affected surface halted until markers are retired; treat the cap as a load-bearing signal of accumulated drift.
  - *Already-merged drift discovered later:* open a reconciliation change immediately; freeze further edits to the affected surface until reconciled; log the drift event so audit can detect frequency.
- **Cannot be silently exempted:** A change where the author asserts "spec is fine; trust me" without producing the unchanged-side proof is a violation. The rule does not require excessive ceremony for trivial changes — but the proof must exist somewhere reviewable, even if it's a one-line assertion in the commit message.

## Rationale

The rule exists because specifications drift from code by default. Every change to the code without a corresponding spec update widens the gap; every change to the spec without a code update creates an aspirational document disconnected from reality. After enough drift, the spec stops being a source of truth and becomes governance theater — present, formal, and false.

The bidirectional invariant prevents the asymmetry that makes drift accumulate. Treating spec and code as a pair at every gate forces the drift cost to be paid at change time (when both sides are fresh in the author's head), not at audit time (when reconstructing intent across many commits is expensive and often impossible).

The rule is the positive-space restatement of the spec-drift anti-pattern. Rather than enumerating ways drift can occur (spec-only edits without code follow-through, code-only edits without spec updates, "we'll fix the spec later," conformance tests that fall behind interface changes), the positive invariant is "spec and code reconcile every change, or a tracked deviation explains why not." One rule, deterministic check.

The rule respects the legitimate need for incremental work. Time-bounded reconciliation markers are first-class — they are how the rule accommodates "the spec changes today, the code lands tomorrow" or "this code change requires a spec update across three modules; track them." The rule's teeth are at the marker layer: untracked, undated, or expired markers are violations.

## Failure Modes

- **Marker theater.** Reconciliation markers proliferate without deadlines or owners; the rule's enforcement degrades to "did you add a TODO?" Mitigation: enforce the marker schema (deadline, owner, tracker ID) at the change-record level; markers without all three fields are violations; periodic audits retire stale markers.
- **Asymmetric authority.** The spec is treated as immutable and the code is bent to fit; or the code is treated as ground truth and the spec is rewritten after the fact. Mitigation: the rule requires reconciliation, not deference — when spec and code disagree, the resolution is a deliberate choice (which side is correct) recorded in the change. Avoid policies that always-favor one side without a reasoning step.
- **Bypass via "we'll reconcile in a follow-up PR."** A change merges with the promise of a follow-up that never lands. Mitigation: a tracked reconciliation marker IS the follow-up commitment; it has a deadline and a tracker; "we'll reconcile later" without a marker is a violation, not a deferral.
- **Spec coverage gaps.** Some surface areas have specs and some don't; the rule applies inconsistently. Mitigation: the rule fires only where a spec exists, but a separate audit identifies surface areas that have code without a spec and treats those as a distinct backlog (not a violation of this rule, but a candidate for a different one).
- **Over-specification brittleness.** Every code change requires a corresponding spec edit even for trivial implementation details. Mitigation: scope the spec to architectural and behavioral contracts, not implementation choices; the rule fires on changes that touch the spec's stated scope, not on every line of code.
- **Conformance test treadmill.** When the spec is a conformance test suite, every interface change requires test updates, slowing cadence. Mitigation: this is the cost the rule is buying — drift prevention is not free; if the cost exceeds the benefit, scope the conformance suite (cover the contracts that matter; let implementation details be tested locally).

## Contract

### Preconditions
The project maintains specifications (architectural decisions, behavioral contracts, conformance tests, or equivalent) alongside implementation code, with a stated convention that the spec is the source of truth (or at minimum, must remain in sync with the code).

### Invariants
Every change that touches either the spec or the code reconciles the other in the same change. A spec edit must be paired with code that conforms (now or via a tracked TODO that does not survive merge); a code edit that contradicts the spec must be paired with a spec update that reflects the new behavior. No commit, no merge, no deploy crosses a gate where spec and code disagree without an explicit, time-bounded reconciliation marker.

### Governance
Owner: any policy that establishes the spec's authority — the convention file declaring the spec layout, the skill or workflow that enforces spec-driven development, or the change-management policy. Audit tooling reads each change and verifies (a) spec touches and code touches resolve to a coherent state, or (b) the change carries an explicit reconciliation marker (a TODO with a deadline, a tracked deviation, or equivalent) and the marker is closed before the next merge to the affected surface. Pure-spec or pure-code changes are allowed only when the other side is provably unaffected.

### Recovery
If a commit lands with spec and code disagreeing without a reconciliation marker: open a reconciliation change immediately, freeze further edits to the affected surface until reconciled, record the drift event in the project's change history. If a long-standing drift is discovered (spec and code have disagreed for many changes): treat the spec as suspect, audit which side is correct on each disagreement, then resync — do not blanket-trust either side. If reconciliation markers (TODOs, deviations) accumulate beyond a stated cap: halt new feature work until the markers are retired; the cap is a load-bearing signal, not a vibe.
