# Visual Recap — Post-Execution Mirror of the Visual Plan

## What It Is

The post-execution counterpart to the visual plan, using the same reusable MDX
component library. After the agent finishes, /visual-recap generates an interactive
recap of what was actually built: wireframes of the resulting UI, interactive API specs
and diffs, schema changes, annotated code. Three usage modes:

1. **Reviewing your own agent's work** — a glanceable, drillable snapshot instead of
   hand-testing every path ("it's tedious to hand-test every single thing every time").
2. **Reviewing someone else's PR** — a middle altitude between "a small summary" and "a
   super granular line-by-line mess."
3. **CI artifact** — a GitHub Action runs it on every pull request and posts an
   interactive snapshot in the PR comments.

Recaps are shareable; others comment on them, and the comments/feedback are passed back
to the agent to improve the work. Plan and recap form a symmetric pair: catch
mis-specification before execution, catch mis-implementation after — both before
production.

## Why It Matters

The reviewer's real question after agent execution is "is this what I meant?" — which
React/Tailwind diffs answer poorly. A recap in the *plan's own visual grammar* lets the
human compare intent against outcome at the altitude they reasoned at. For the engine,
the generalization is that post-execution reports at gates (extraction runs, audits,
milestone closes) could mirror the structure of the plan/spec they executed, making
plan-vs-outcome drift visually obvious.

## Why People Are Using It

Builder.io's author uses it on his own work and on others' PRs, and reports catching
mismatches "way sooner" — both pre-execution (wireframe reveals a misunderstanding the
prose hid) and post-execution (recap reveals the built thing differs from intent before
production). Open-sourced alongside /visual-plan. Same problem as Derrick's per-PR HTML
explainer (Anthropic), but with bounded components rather than freeform HTML, and
extended into an automatic CI artifact.

## Potential Improvements

- Explicit plan↔recap diffing: render the recap against the plan and highlight deltas,
  turning "is this what I meant" into a generated report.
- Recap-comment routing: structured mapping from reviewer comments on recap components
  back to agent follow-up tasks.

## Potential Failure Modes

- **Recap trust replaces verification.** A recap is generated by the same class of
  system being reviewed; a wrong recap that looks right is worse than a diff.
- **Stale recaps** on revised PRs, same as any generated review companion.
- **Overhead on small changes** — a one-file fix doesn't need a wireframe recap.
