## What It Is

A deployment architecture where the agent runs entirely on managed infrastructure (Anthropic's hosted environments) and applications interact with it through a thin pass-through layer. The complete stack:

1. **Managed agent** (Anthropic infrastructure) -- system prompt, tool config, credential vault, environment permissions
2. **Agent API** -- stateless endpoint that accepts user messages and returns agent responses
3. **Thin frontend** -- web app, CLI, Slack bot, or other interface that sends user input to the API and renders responses

The frontend contains zero business logic. All intelligence, tool orchestration, and credential management lives in the hosted agent. The frontend is literally a chat window connected to an API endpoint.

**The workflow demonstrated:**
1. Build and test agent on Anthropic's platform
2. Click "integrate" or ask the platform "how do I connect this to a frontend?"
3. Platform generates a prompt for Claude Code to build the frontend
4. Claude Code scaffolds the frontend in ~30 seconds
5. Deploy to production (e.g., Netlify)

The practitioner explicitly contrasts this with "hardcore mode" -- "actually going out grabbing the ENV, the API keys, the credentials, setting up our own environment, all that stuff."

## Why It Matters

This pattern fundamentally changes who can ship agent-powered applications. The frontend is so thin that it can be generated by another AI tool (Claude Code) from a prompt generated by the managed agent platform itself. This is a meta-automation: the agent platform generates the instructions for building its own client.

For harness builders, the implication is that agent deployment should be as simple as "give someone an API endpoint." The agent's entire configuration (prompt, tools, credentials, permissions) is the deployment artifact -- the frontend is disposable and regenerable.

This also demonstrates a clean build/operate separation: the builder configures the agent on the platform, and the operator (end users) interact through the thin frontend. The frontend never needs to know about credentials, tool configurations, or system prompts.

## Why People Are Using It

The practitioner (who builds automations for clients) describes this as useful for sharing agent capabilities with teams: "that way I can share it amongst my team and anybody can quickly paste in a transcript to very quickly set up ClickUp tasks." The pattern enables non-technical team members to use agents without understanding the underlying configuration.

## Potential Improvements

- Pre-built frontend templates per use case (chat bot, form submission, Slack integration)
- Frontend generation as a first-class platform feature (not requiring a separate Claude Code session)
- Embeddable widget that drops into existing apps
- Multi-agent frontends that route to different agents based on input type

## Potential Failure Modes

- Latency: pass-through adds network hops (user -> frontend -> Anthropic API -> tool APIs -> back)
- Vendor lock-in: the thin frontend is easy to rebuild, but the agent definition and credential vault are platform-specific
- No offline capability: the frontend is completely dependent on the managed agent being available
- UX limitations: the chat interface may not be the right interaction pattern for all agent capabilities (some tasks need structured forms, progress indicators, or multi-step wizards)
- Cost opacity: frontend users have no visibility into token costs per interaction
