# Oz Multi-Agent Room Model

## Pattern

A multi-agent coordination architecture built on rooms as bounded contexts:

**Rooms:**
- Chat channels where humans and agents collaborate on a topic
- The coordination boundary — agents only interact within assigned rooms
- Multiple agents can be assigned to the same room

**Agents:**
- Configurable: system prompt, skills, MCP servers, associated repo
- Run via the Oz harness (external process)
- Report results back via agent callback URL
- Authenticated via token-based auth

**Communication:**
- @mention syntax for agent-to-agent messaging within rooms
- SSE (Server-Sent Events) for real-time updates
- Agents see each other's messages and can respond

**Work artifacts:**
- **Tasks**: Per-room kanban board (backlog → in progress → done) that agents self-manage
- **Artifacts**: Documents, PRs, plans generated by agents during work
- **Notifications**: Inbox alerts from agents (async coordination with humans)

## Why It Matters

Provides a structured coordination model for multi-agent systems that's more sophisticated than simple orchestrator→worker delegation:
- Agents can coordinate peer-to-peer (via @mentions) without a central orchestrator
- Rooms provide natural scope boundaries (one topic/project per room)
- The kanban gives both humans and agents shared visibility into work state
- Typed artifacts (PRs, plans, docs) give concrete output, not just chat

## How It Could Fail

- Room scope too broad (too many agents, too many topics → noise)
- @mention routing complexity (how does an agent know which other agent to invoke?)
- SSE scalability for many concurrent rooms/agents
- Coordination overhead if agents need to agree rather than just inform
