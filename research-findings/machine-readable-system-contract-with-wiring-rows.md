# Machine-Readable System Contract — Agent Card with Embedded Wiring Rows

## What It Is

A single canonical `system-contract.yaml` that describes an installable multi-file agent
system as one composed agent. The outer card carries `identity` (product-vs-domain split,
objective, hard/process constraints, autonomy, stop rules), `trust` (permissioning
boundary, threat non-goals, declared absences), `end_user_value` (capability list, the
A2A `skills[]` analog), and `skills_rollup` (exportable skill packages plus the union of
their required capability IDs). The inner layer is the installer's manifest:
`composition` (component inventory with roles) and `wiring` — one row per
harness-integration concern (always-on entry, path-scoped rules, governance registry,
memory scopes, skill registry, cold-start chain, invocation context, operational quirks).

## Why It Matters

Plain English: if you ever want to move an agentic system to a different harness — or let
someone else install it — you need a machine-readable statement of what the system
*requires from a harness* versus what it merely prefers. Without it, every port is
archaeology. The contract turns "install this system" into a checklist with pass/fail
semantics, and the per-row invariant turns "did the port work?" into a testable question.

## How It Works

- Each wiring row carries five fields: `tier` (**required** = do not install without a
  satisfier, checked before any adaptation cost is paid; **optional** = install and
  record the degradation), `capabilities` (IDs from a controlled wiring vocabulary, e.g.
  `always-on-instruction-injection`, `path-scoped-rule-injection`, `scoped-memory-store`,
  `human-approval-channel`), `purpose`, `degradation` (always names its prose fallback so
  the worst-case host still preserves the invariant), and `invariant` — the property that
  must survive *any* adaptation, however the target platform satisfies the row.
- Example row: `always-on-entry` is required with no acceptable degradation ("a host with
  no unconditional injection point cannot run the system; the agents.md convention is the
  minimum satisfier"); `path-scoped-rules` is optional, degrading to folding the rules
  into the always-on file with the weaker guarantee recorded.
- A prose companion (`system-contract.md`) exists but is explicitly derived: "when the
  two disagree, the YAML wins and this page is stale." The YAML is regenerated by a
  gated meta-skill, never hand-edited.
- A separate `wiring-manifest.json` records SHA-256 hashes of every wired file
  (always-on file, registry, path-scoped rule files, AGENTS.md, PRD, ARCHITECTURE). An
  audit checks hashes; a mismatch means the wiring canon may be stale and triggers a
  gated regeneration — drift detection between documented wiring and live wiring.
- Two consumption routes, one contract: a source-side staged adapter (pre-built
  INSTALL-MAP per platform), or a target-side receiving agent following an adaptation
  protocol. Neither route may weaken an invariant.
- The contract model mirrors the same pattern at skill scale (per-skill
  `capability-contract.yaml` sidecars with required/optional tiers) — two controlled
  vocabularies split by scale, each owned by a gated authoring skill.

### Card-over-manifest fusion (the framing verdict)

The shape is a deliberate fusion, settled at CareerBuddy's MV21 Phase R design gate and
queued by that system as a corpus contribution to this engine: **treat a harness install
as one composed agent**. The Phase R field-level survey (A2A, MCPB, MCP server.json,
OASF, agents.md, Archon) found the two halves always live apart — agent cards (A2A,
OASF) describe a callable agent's identity, trust, and `skills[]` but carry no
realization manifest saying how to *install* it; installer manifests (MCPB, MCP
server.json) describe packages and user_config but have no agent-level identity or trust
declaration. Fusing them — outer card (identity, trust, `end_user_value` as the A2A
`skills[]` analog, skills rollup) over inner realization manifest (composition + wiring
rows) — is what lets one artifact serve both audiences: a foreign agent deciding whether
to trust and adopt the system, and an installer computing whether the host can run it.
Two headline novelties fell out of the same survey: the per-row invariant column (no
prior art anywhere) and the observation that capability negotiation across the ecosystem
is declare-and-adapt, never a live handshake — see the related findings for each.

## How It Could Fail

Hand-editing the YAML breaks the single-source-of-truth guarantee — regeneration must be
the only write path. An over-detailed vocabulary invites classification debates instead
of installs. The contract is only as honest as its trust section; omitting a declared
absence (e.g. prose-only permission guards) produces installs that assume enforcement
that does not exist.
