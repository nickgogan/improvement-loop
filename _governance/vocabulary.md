# Cross-System Vocabulary

Authoritative definitions for terms used across all systems. When terms conflict with system-specific definitions, these govern.

---

## System & Architecture

| Term | Definition |
|------|------------|
| **Household OS** | The running operational system — Notion schema, Custom Agents, workflows, and human rituals in Notion + Slack. Formerly S1 (Notion Schema) + S2 (Notion Operations), merged per DD-58. |
| **Claude Build** | The builder system — vault architecture, bootstrap skills, and schema modifications via Claude Code / Cursor. Formerly S3: Claude Code Build. |
| **Meta-System** | The top-level layer that governs, designs, builds, and improves all other systems. Formerly "System Documentation" (DD-43). |
| **Improvement Loop** | Self-improvement subsystem — researches, proposes, evaluates, enhances, and codifies improvements to Household OS, Claude Build, and itself. |
| **Target System** | Property indicating which system a DD or IB item applies to. Values: Household OS, Claude Build, Improvement Loop, Cross-System. |

## Decision & Tracking

| Term | Definition |
|------|------------|
| **Design Decision (DD)** | A binding architectural choice, scoped to one question from one scope category. Numbered sequentially. |
| **Implementation Backlog (IB)** | A work item needed to realize a DD or system improvement. Tracked by priority, status, and target system. |
| **Scope Category** | Classification of what question a DD answers: Principle, Component, Structure, Domain, or Flow. |
| **Human Gate** | A point where human review and approval is required before proceeding. No autonomous modification of live systems. |
| **Codified Practice** | A best practice validated through research, approved, and formalized as governing knowledge. |
| **Door Type** | Reversibility classification: one-way door or two-way door. Used in the Proposal Assessment Model (DD-31). |
| **Interface Contract** | Agreement between two systems specifying how they interact and responsibilities (DD-32). |
| **Boundary Rule** | Explicit constraint on what a system can and cannot do relative to other systems (DD-32). |

## Agent & Skills

| Term | Definition |
|------|------------|
| **Cognitive Disposition** | A "how this role thinks" section in a skill file that seeds the agent's analytical personality. |
| **Access Model** | Table defining exactly which databases/resources a skill can read and write. |
| **Scope Boundary** | Explicit limits on what a skill or agent can modify. |
| **Skill Catalog** | Per-system page listing all skills/agent configurations with dispositions and access models. |
| **Skills Layer** | Cross-cutting architectural pattern for how agent behavior is defined across all systems. |

## Pipeline

| Term | Definition |
|------|------------|
| **Research Finding** | A distilled knowledge entry — one pattern/technique with evidence and applicability tracking. |
| **Improvement Proposal** | A proposed change generated by research-proposer, targeting a specific system. |
| **Proposer Priority** | Priority assigned to a Finding indicating urgency for proposal generation. |
| **Design-Time Layer** | Architectural documentation layer (Meta-System) where DDs, governance, and system design live. |
| **Runtime Layer** | Operational layer where humans and Household OS-scoped agents do daily work. |
